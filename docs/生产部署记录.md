## 二、实施要点

### 2.1 端口切换策略（保证 nginx 零改动）

关键设计：**gateway 接管 8080，单体后端退到 8090**。
nginx 仍反代 `127.0.0.1:8080`，因此**无需修改 nginx 配置**。

```
nginx :8089 ──> :8080 gateway
                  ├─ /auth/**         -> wuling-auth-service :8081
                  ├─ /api/v1/files/** -> wuling-file-service :8082
                  └─ /api/v1/**       -> wuling-server       :8090
```

### 2.2 实施中踩到的坑

**坑 1：所有服务共用同一配置目录**

最初把所有 jar 与 `application-prod.yml` 放在 `/opt/wuling/app/`。
Spring Boot 对 `prod` profile 优先加载 `application-prod.yml`，
导致 auth-service 读到了 server 的配置（port 8090），启动报
`Port 8090 was already in use`。

**修正**：改为**每服务独立目录**，各自持有自己的 `application-prod.yml`。

**坑 2：自定义配置文件名不生效**

曾尝试用 `--spring.config.name=application-server-prod` 区分，
但 Spring Boot 对激活 profile 的加载优先级是
`application-{profile}.yml` > `--spring.config.name`，自定义名被覆盖。

**修正**：放弃自定义名，用独立目录 + 标准文件名。

## 三、部署中发现并修复的问题：`WX_APP_SECRET` 位置不当

**现象**：user-service 启动失败

```
IllegalArgumentException: Could not resolve placeholder 'WX_APP_SECRET' in value "${WX_APP_SECRET}"
```

**根因**：`WX_APP_SECRET` 只写在 **server 的 systemd unit** 里：

```ini
# wuling-server.service
Environment="WX_APP_SECRET=cc1c9957..."
```

而共享的 `secrets.env`（`EnvironmentFile`）中**没有**这一项。
user-service 同样需要该密钥，但拿不到。

**修复**：把 `WX_APP_SECRET` 移入共享的 `/opt/wuling/app/secrets.env`（权限 600），
各服务通过 `EnvironmentFile` 统一获取。

**这暴露了一个遗留问题**：密钥分散在「secrets.env + 各 unit 的 Environment」两处，
新增服务时容易漏。**建议后续把 unit 中的明文 `Environment` 全部清空**，
统一收敛到 `secrets.env`。

## 三、部署中发现并解决的问题

### 3.1 `/internal/product` 返回 200 的误判

**现象**：server 更新后，`/internal/product` 仍返回 HTTP **200**，看似未移除。

**排查**：对照实验 —— 请求一个绝对不存在的路径：

| 路径 | 响应 |
|------|------|
| `/internal/nonexistent-xyz` | HTTP 200 `{"code":500,"message":"服务器内部错误"}` |
| `/internal/product` | HTTP 200 `{"code":500,"message":"服务器内部错误"}` |

**两者完全一致** → 证明 `/internal/product` 确已不存在。

**根因**：`GlobalExceptionHandler` 的 `@ExceptionHandler(Exception.class)`
兜底捕获了 Spring 的 `NoResourceFoundException`（路径不存在），
经 `Result.fail` 包装后**以 HTTP 200 返回**。

> 教训：本项目的"接口不存在"表现为 `HTTP 200 + code=500`，
> 而非 404。用状态码判断接口是否存在**会误判**，
> 必须对比响应体或做对照实验。

### 3.2 历史日志导致的假阳性

排查 server 启动时，`grep -iE 'error|exception'` 命中了**上午 11:30 的历史错误**
（Flyway 校验失败、`Public Key Retrieval is not allowed`），
一度误判为本次启动失败。

**正确做法**：以 `Started ServerApplication` 标记 + 时间戳定位本次启动，
不要对整个滚动日志做无时间约束的 grep。

# MySQL 容器口令轮换补全 + healthcheck 修复

> 日期：2026-09-22

## 三、踩坑：MySQL 重建后丢 wuling-net 网络
