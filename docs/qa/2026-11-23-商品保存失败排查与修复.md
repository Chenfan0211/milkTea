# 商品保存失败：存量 base64 图片排查

> 事故：2026-11-23 商品管理保存报 `Data too long for column 'image'`。
> 根因：前端把 base64 图片（约 2.2MB）直接写进 `VARCHAR(255)` 的列。
>
> 代码已修复（前端改用上传接口）。本文档用于排查**是否已有脏数据落库**。
>
> **本文档中的 SQL 均为只读排查，不自动执行。** 清理语句需先确认查询结果再由人工执行。

## 一、为什么可能有存量数据

线上这三次保存都失败了（列宽限制导致 MySQL 拒绝并回滚），理论上库里没有 base64。

但仍需排查两个可能：

1. 早期某次迁移可能把 `image` 列改宽过（如临时改成 TEXT），期间写进去过
2. 其他表（`mall_product`、`mall_category`、优惠券、积分商品）可能也有同类字段

## 二、排查结果（2026-11-23 已在生产执行）

```sql
SELECT 'product.image' col, COUNT(*) cnt, MAX(LENGTH(image)) maxlen FROM product WHERE image LIKE 'data:image%'
UNION ALL
SELECT 'product.gallery_image', COUNT(*), MAX(LENGTH(gallery_image)) FROM product WHERE gallery_image LIKE 'data:image%';
```

**结果：全部为 0 条** —— 脏数据未落库，无需清理。

| 表 / 字段                  | 记录数 |
| -------------------------- | ------ |
| `product.image`            | 0      |
| `product.gallery_image`    | 0      |
| `mall_product.cover_image` | 0      |
| `mall_category.icon_image` | 0      |
| `coupon.image`             | 0      |

原因：`VARCHAR(255)` 的列宽限制让 INSERT 直接被 MySQL 拒绝并回滚，
所以即便前端每次都在传 base64，也没有一条能写进去。

**结论：只需部署代码修复，不需要任何数据清理。** 下文第三节的清理 SQL 保留作参考，
供将来若出现类似问题（如某列被改宽后写入）时使用。

## 三、清理 SQL（本次未使用，留作参考）

**原则：只清图片字段，不删记录。** 商品名称、价格、分账规则等其他数据都保留，运营重新上传图片即可。

### 3.1 先备份

```sql
-- 清理前把待处理记录导出（用于回滚与后续补图）
CREATE TABLE IF NOT EXISTS _bak_base64_image_20261123 AS
SELECT 'product.image' AS src, id, image AS old_value FROM product
 WHERE image LIKE 'data:image%' AND LENGTH(image) > 2000
 UNION ALL
SELECT 'product.gallery_image', id, gallery_image FROM product
 WHERE gallery_image LIKE 'data:image%' AND LENGTH(gallery_image) > 2000;
```

### 3.2 置空图片字段

```sql
-- product 主图
UPDATE product SET image = NULL
 WHERE image LIKE 'data:image%' AND LENGTH(image) > 2000;

-- product 详情大图
UPDATE product SET gallery_image = NULL
 WHERE gallery_image LIKE 'data:image%' AND LENGTH(gallery_image) > 2000;
```

**注意**：若商品 `image` 有 NOT NULL 约束或前端要求必填，置空后该商品在后台列表会显示占位图，运营需重新上传。这是预期行为——比留着无法解析的 base64 更好。

### 3.3 验证

```sql
-- 应返回 0 行
SELECT COUNT(*) FROM product WHERE image LIKE 'data:image%' AND LENGTH(image) > 2000;
```

### 3.4 确认无误后删除备份表

```sql
-- 观察 1-2 天确认商品图片都补齐后再执行
DROP TABLE _bak_base64_image_20261123;
```

## 四、线上验证修复是否生效

部署新前端后，按以下步骤确认：

1. 后台 → 商品管理 → 编辑任一商品
2. 点击图片区域 → 选择一张 JPG/PNG
3. **预期**：出现「图片上传成功，请保存后生效」提示，图片立即显示
4. 点保存 → 应成功

**验证数据落库格式**：

```sql
-- 应看到 /api/v1/files/... 之类的 URL，而不是 data:image
SELECT id, code, LEFT(image, 80) AS image_prefix, LENGTH(image) AS len
  FROM product ORDER BY update_time DESC LIMIT 5;
```

**若仍失败**，查后端日志：

```bash
docker logs --since 10m wuling-product-service 2>&1 | grep -E 'ERROR|保存|Data too long'
```

修复后的报错应当是**可读的**中文提示（如「字段「image」内容过长」），而不是「服务器内部错误」。

## 五、根因回顾（供后续避免同类问题）

| 环节   | 问题                                                                              |
| ------ | --------------------------------------------------------------------------------- |
| 前端   | `type: 'image'` 分支用 `FileReader.readAsDataURL` 存 base64，而不是走文件服务上传 |
| 表结构 | `product.image` 是 `VARCHAR(255)`，装不下任何 base64                              |
| 后端   | `DataIntegrityViolationException` 落到兜底分支，返回「服务器内部错误」            |
| 日志   | 2.2MB base64 全量写入日志，快速撑大日志文件                                       |

**四层已全部修复**：

1. 4 处 `type:'image'` 改为 `uploadImage`
2. 删除 `readAsDataURL` 分支，`type:'image'` 复用上传实现（含历史值提示）
3. `GlobalExceptionHandler` 增加 `DataIntegrityViolationException` 分支，返回可读中文
4. `SensitiveDataMasker` 截断 data URL，日志只留 `data:image/png;base64,***TRUNCATED(2217800)`
