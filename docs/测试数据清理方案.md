# 测试数据清理方案（五零时光 · wuling 库）

> 编制：2026-10-14
> 目标库：`wuling` @ `43.136.91.239`（容器 `wuling-mysql`，MySQL 8.0.46，库体量 3.5MB）
> 状态：**方案待确认，尚未改动任何数据**（本文档中的 SQL 均为待执行稿）

## 一、结论先行

实测盘点后，结论比预想的干净：

1. 全库 **69 张表** = **40 张保留**（账户 / 权限 / 字典 / 配置 / 运营主数据 39 张 + Flyway 历史表）+ **27 张业务流水清空** + **2 张临时备份表建议 DROP**；
2. 这 27 张流水表里的数据 **100% 是联调与演示数据 → 整体清空**；
3. 另有 **6 张保留表里混有演示/探针脏行**（演示商品、探针主体、测试门店、测试会员档、测试分账规则、悬空绑定）→ 定点删除；
4. **账户与权限完全不受影响**（后台 5 个账号、角色菜单关系、小程序账号与其角色授予全部原样保留）；
5. 执行窗口约 **5 分钟**，全库可一次备份、可一键回滚（DB 仅 3.5MB）。

**脚本已在服务器临时副本库演练通过（2026-10-14 14:16）：所有期望值逐条命中，生产库未被触碰**（详见附录 F0）。

附带发现两项需要一并处置的「测试痕迹」：

- 生产服务器上还有 **2 个遗留演练库**：`wuling_v48_rehearsal_20260926_172109`、`wuling_v48_rehearsal_20260926_172126`；
- 库里残留 **2 张临时备份表**：`_bak_super_20260925`(3 行)、`flyway_schema_history_bak_20261010`(70 行)。

## 三、清理原则

| #   | 原则               | 说明                                                                       |
| --- | ------------------ | -------------------------------------------------------------------------- |
| 1   | **白名单保留**     | 账户、权限、字典、区域、配置、运营主数据一律不动                           |
| 2   | **流水全清**       | 订单/支付/退款/核销/积分/券/储值/礼品卡/结算/资金/对账/审批/日志，一律清空 |
| 3   | **账户留、余额零** | 账户行保留，余额与累计值归 0，避免「账户有余额但无流水」                   |
| 4   | **保留表定点洗**   | 演示商品、探针主体、测试门店/会员档，按标记删除                            |
| 5   | **幂等 + 事务**    | 全部用 `DELETE`（不用 `TRUNCATE`），单事务包裹，异常自动回滚，可重复执行   |
| 6   | **先备份后执行**   | 备份成功并校验 sha256 后才允许执行清理                                     |

## 八、执行步骤（维护窗口约 5 分钟）

### Step 0 · 前置（约 1 分钟）

1. 通知停用小程序与后台（避免清理期间产生新下单）；
2. 用附录 D 的盘点 SQL 记录清理前行数基线；
3. **停写**：停掉 8 个后端应用容器（只停应用，不停 MySQL / Redis / RabbitMQ）：

```bash
cd /opt/wuling/app && docker compose stop
```

### Step 1 · 备份（约 1 分钟）

> 实测：MySQL 容器内**没有** `MYSQL_ROOT_PASSWORD` 环境变量，口令在 `/opt/wuling/app/secrets.env`（`deploy/.env` 是它的软链）。因此统一用一个封装脚本读取口令，**口令不进命令行明文、不进 shell 历史**。

在服务器上创建 `/opt/wuling/scripts/db-exec.sh`：

```bash
#!/usr/bin/env bash
# 用库口令执行 SQL：bash db-exec.sh < query.sql
set -euo pipefail
set -a; . /opt/wuling/app/secrets.env; set +a
exec docker exec -i -e MYSQL_PWD="$MYSQL_ROOT_PASSWORD" wuling-mysql \
  mysql -uroot -N -B --default-character-set=utf8mb4 wuling
```

全库备份到既有备份目录（服务器已有每日 03:30 定时备份，本次单独留一份「清理前」快照）：

```bash
set -a; . /opt/wuling/app/secrets.env; set +a
STAMP=$(date +%Y%m%d-%H%M%S)
docker exec -e MYSQL_PWD="$MYSQL_ROOT_PASSWORD" wuling-mysql \
  mysqldump -uroot --single-transaction --routines --triggers --hex-blob wuling \
  | gzip > /opt/wuling/backup/pre-clean-testdata-$STAMP.sql.gz
ls -lh /opt/wuling/backup/pre-clean-testdata-$STAMP.sql.gz
sha256sum /opt/wuling/backup/pre-clean-testdata-$STAMP.sql.gz \
  | tee /opt/wuling/backup/pre-clean-testdata-$STAMP.sha256
```

**闸门**：备份文件存在、大小合理（百 KB 量级）、sha256 已记录，才进入 Step 2。

### Step 2 · 执行清理（约 1 分钟）

```bash
scp scripts/clean-test-data.sql root@43.136.91.239:/opt/wuling/scripts/
ssh root@43.136.91.239 'bash /opt/wuling/scripts/db-exec.sh < /opt/wuling/scripts/clean-test-data.sql'
```

脚本特征：**单事务 + 逐条 DELETE + 末尾 COMMIT**。任何一条报错都会整体回滚（连接断开即回滚），不会留下半清状态。

### Step 3 · 清缓存（约 30 秒）

- RabbitMQ：实测 16 个队列消息数全为 0，**无需处理**（无延迟消息、无死信堆积）；
- Redis：清掉登录态、幂等键、库存锁等业务键（同时会清掉验证码）：

```bash
set -a; . /opt/wuling/app/secrets.env; set +a
for NS_DB in 0 1 2 3; do
  docker exec wuling-redis sh -c \
    'redis-cli -a "$REDIS_PASSWORD" -n '"$NS_DB"' --scan --pattern "wuling:*" \
     | xargs -r redis-cli -a "$REDIS_PASSWORD" -n '"$NS_DB"' del'
done
```

> `REDIS_PASSWORD` 已由 `env_file` 注入 `wuling-redis` 容器，脚本内直接读容器环境变量，无需在宿主机明文传递。
> 如需更彻底，可对 db0-db3 执行 `FLUSHDB`——本项目独占这些库，代价是所有登录态与验证码立即失效。

### Step 4 · 重启与校验（约 2 分钟）

```bash
cd /opt/wuling/app && docker compose up -d
docker compose ps
curl -fsS http://127.0.0.1:8080/actuator/health
bash /opt/wuling/scripts/db-exec.sh < /opt/wuling/scripts/clean-test-data-check.sql
```

按附录 C 逐项核对行数与功能。

### Step 5 · 观察

观察 24 小时日志，确认无「订单不存在」「余额不足」类异常刷屏，定时任务与延迟队列无回写。

## 九、回滚方案

| 场景               | 操作                                                                                                                                       |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------ |
| 清理执行中报错     | 单事务自动回滚，库仍是清理前状态；修脚本重跑                                                                                               |
| 清理完成后发现误删 | 从备份恢复：`gunzip -c /opt/wuling/backup/pre-clean-testdata-*.sql.gz \| docker exec -i -e MYSQL_PWD=... wuling-mysql mysql -uroot wuling` |
| 只想回滚某一段     | 附录 A 脚本按段编号（1~4），可分段执行、就近 `SAVEPOINT` 回滚                                                                              |
| 最坏情况           | 回退应用镜像到上一版本（`IMAGE_TAG`），数据侧以备份为准                                                                                    |

备份文件保留到清理后 7 天无异常，再按既有轮转策略清理。

## 十、防回潮（关键，不能只清一次）

**问题**：演示数据是 Flyway 迁移的一部分（`V3/V4/V6/V9/V16/V17/V21/V22/V27/V32/V41/V45` 等）。已应用的迁移不会重跑，但**新环境部署或重建库时会再次灌入全部演示数据**；`V22` 末尾那段清理 SQL 也不会自动执行。

| 方案                           | 做法                                                                                                                   | 评价                                                                                                                                         |
| ------------------------------ | ---------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| **A 结构治理（推荐后续专项）** | 把演示种子从 `db/migration` 拆到 `db/demo`，用 `spring.flyway.locations` 按 profile 加载（生产不加载 `db/demo`）       | 一次治理长期有效。约束：已应用的 `V*` 不可修改（checksum 会校验失败），因此只对**新增**种子生效，历史种子保持原样、只在头部加 `-- DEMO` 标记 |
| **B 脚本化（本次落地）**       | 清理脚本入仓 `scripts/clean-test-data.sql` + `scripts/clean-test-data-check.sql`，写入部署手册「新环境上线后必跑一次」 | 立刻可用、零风险；依赖流程纪律                                                                                                               |
| C 迁移自清理                   | 新增 `V75` 迁移直接删演示数据                                                                                          | ❌ 会在所有环境（含本地开发库）执行，破坏开发用演示数据                                                                                      |

**推荐：本次用 B 落地，A 作为下一轮结构治理专项。**

- `user-h5/data/mock.js`（2.5KB 兜底，`USE_MOCK` 默认 `false`）与 `utils/request.js` 的 mock 分支——属开发兜底，非线上数据；
- 后台 seed 兜底——前几期已做接口化（见 `docs/mock-data-cleanup.md`、`docs/小程序假数据排查与接口化方案.md`），如需彻底清理，另开一轮。

## 十一、风险与注意事项

1. **不要动 `flyway_schema_history`**：删它会导致重启时 Flyway 校验失败甚至服务中断（09-22 事故同类风险）。
2. **不要改已应用的 `V*` 迁移文件**：Flyway checksum 校验会失败。
3. **备份先行**：全库仅 3.5MB，备份成本极低，没有理由跳过。
4. **删除方式**：一律 `DELETE`（可事务回滚），不用 `TRUNCATE`（隐式提交、无法回滚）。清理后如需重置自增，可另行 `ALTER TABLE ... AUTO_INCREMENT = 1`（可选、非必需，业务单号是日期 + 随机生成，不依赖自增）。
5. **逻辑删除**：65 张表有 `deleted` 列；本次清的是「测试数据本体」，用物理删除；后续业务删除仍走逻辑删除，保持一致。
6. **余额与流水要自洽**：账户行保留但余额必须归零，否则会出现「有余额、无流水」的对账缺口。
7. **空态体验**：清理后小程序的订单 / 积分 / 券 / 储值 / 礼品卡均为空态，需确认空态文案与引导（只影响观感，不影响功能）。
8. **维护窗口**：必须在停写状态下执行；执行前确认 `orders` 行数不再增长。
9. **口令安全**：不打印口令、不写入命令历史，统一走 `secrets.env` 封装脚本。
10. **不可逆项**：两个演练库 `DROP DATABASE` 与两张临时表 `DROP TABLE` 不可回滚，建议本次备份完成且**单独确认**后再执行。
