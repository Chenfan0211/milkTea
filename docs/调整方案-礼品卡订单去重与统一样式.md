# 调整方案：礼品卡订单页去重 + Tab 页统一为「购买订单」样式

> 日期：2026-09-28
> 现象：礼品卡订单页同时展示「我的礼品卡」与「购买订单」两块，同一笔购买出现两次（重复数据）
> 需求：订单信息只展示「购买订单」下的数据；其他 Tab 页也统一按这个样式展示；消除重复
> 状态：✅ 已实施（2026-09-28，P1 方案 A）

---

## 一、根因分析

### 1.1 重复的直接原因：同一笔购买被两个接口分别渲染了一次

`pages/gift-card-orders/gift-card-orders.js` 的 `refresh()` 并行拉两个接口，
分别渲染成页面上的两个区块：

| 区块       | 数据来源                    | 过滤                         |
| ---------- | --------------------------- | ---------------------------- |
| 我的礼品卡 | `api.fetchMyGiftCards()`    | 只保留 `status === 'ACTIVE'` |
| 购买订单   | `api.fetchGiftCardOrders()` | 全量订单                     |

两个接口描述的是**同一笔购买**：

```java
// marketing-service GiftCardService.ensureCard(order)
// 支付成功后按下单记录发卡，一单一卡绑定
card.setOrderId(order.getId());      // 与订单 1:1
card.setOwnerUserId(order.getUserId());
card.setStatus("ACTIVE");
```

- `GiftCard` 实体注释即写明「一单一卡绑定；历史卡此字段可为空」；
- `myCards(userId)` 查 `owner_user_id = 当前用户`，`myOrders(userId)` 查 `user_id = 当前用户`，
  两个集合在「自己购买、未核销」场景下完全重合。

因此截图里「限定心意 ¥100 待核销」在「我的礼品卡」和「购买订单」各出现一次 —— 这不是渲染 bug，
是两个数据源在描述同一实体。

### 1.2 为什么两块看起来「信息不同」却仍是同一笔

| 维度 | 我的礼品卡                 | 购买订单                    |
| ---- | -------------------------- | --------------------------- |
| 主键 | `gift_card.id`             | `gift_card_order.id`        |
| 编号 | 卡号 `CARD2026...`         | 订单号 `GC2026...`          |
| 金额 | 面值                       | 实际支付售价                |
| 状态 | 恒为「待核销」（前端写死） | 待支付/待核销/已完成/已取消 |

两侧是同一笔购买的两种视图：卡视图缺「待支付/已取消」等订单状态，
订单视图缺卡号。重复展示既冗余又容易让用户误以为「买了两张」。

### 1.3 结论

按需求保留**购买订单**（状态机完整、可取消/退款/继续支付、有金额与时间），
移除**我的礼品卡**区块，并把卡号并入订单卡片展示，做到「一笔订单一行数据」。

> 卡列表能力不会丢失：`pages/gift-card/gift-card` 页已有独立的「我的礼品卡」Tab，
> 与订单页职责分离（礼品卡页看卡、订单页看单）。

## 二、调整方案

### P0：移除「我的礼品卡」区块，只保留「购买订单」

**改动 1 — WXML 删除卡片区块**

`pages/gift-card-orders/gift-card-orders.wxml`：

- 删除 `wx:if="{{filteredGiftCards.length}}"` 的整个 `gift-held-section` 区块
  （含「我的礼品卡」标题与 `gift-held-card` 列表）；
- 保留 `gift-order-section`（购买订单）区块；
- **去掉「购买订单」这个分组标题**，改为直接以订单卡列表作为整页内容
  （既然只有一个数据源，再留分组标题反而与「订单信息」语义重复）；
- 空态判断从 `!filteredGiftCards.length && !filteredOrders.length` 收敛为 `!filteredOrders.length`。

**改动 2 — JS 移除卡数据源**

`pages/gift-card-orders/gift-card-orders.js`：

- 删除 `giftCardsTask`（`api.fetchMyGiftCards()`）及其在 `Promise.all` 中的参与；
- 删除 `data` 中的 `allGiftCards` / `filteredGiftCards`；
- 删除 `applyFilter()` 中对 `filteredGiftCards` 的赋值；
- 删除 `decorateGiftCard()`、`filterGiftCards()`、`matchGiftCardStatus()` 三个仅为卡区块服务的函数；
- `loadError` 判定简化为只看订单接口：`ordersResult.ok ? '' : '部分礼品卡数据加载失败，请重试'`。

**改动 3 — WXSS 清理**

`pages/gift-card-orders/gift-card-orders.wxss`：删除仅被 `gift-held-*` 使用的样式规则
（`.gift-held-section` / `.gift-held-card` 及其子类）；
`.gift-section-head` 只有在订单区块仍需分组标题时才保留，否则一并删除。

### P1：把卡号并入订单卡片，保证信息不回退

移除卡区块后，卡号 `CARD2026...` 会丢失。为不降低信息密度，
在订单卡的「订单信息」区补一行卡号：

```text
订单号 GC202609220010001003
卡号   CARD202609220010001003     <- 新增（有则展示）
支付时间 2026-09-22 19:05:00
```

实现方式：订单接口不下发卡号，需在前端把「我的礼品卡」按 `orderId` 关联到订单后合并展示。
**两种取法二选一，推荐 A：**

| 方案          | 做法                                                                                         | 取舍                                           |
| ------------- | -------------------------------------------------------------------------------------------- | ---------------------------------------------- |
| **A（推荐）** | 仍调 `fetchMyGiftCards()`，但**不独立渲染**，只作为 `orderId -> cardNo` 的映射表合并进订单卡 | 多一次请求，但卡片编号来源权威、不依赖后端改动 |
| B             | 让后端在 `GiftCardOrder` 上下发 `cardNo`                                                     | 最干净，但要改 marketing 接口，属跨端改动      |

方案 A 的合并逻辑（纯函数，便于单测）：

```js
/** 把「订单 id -> 卡号」映射合并进订单列表，卡号缺失时不渲染该行。 */
function mergeCardNoIntoOrders(orders, cards) {
  const map = new Map();
  (cards || []).forEach(card => {
    if (card && card.orderId != null) map.set(String(card.orderId), card.cardNo || '');
  });
  return (orders || []).map(order =>
    Object.assign({}, order, {
      cardNo: map.get(String(order.id)) || order.cardNo || ''
    })
  );
}
```

> 若确认「卡号不必在订单页展示」，P1 可整段跳过，P0 即满足需求。
> 这一点建议你确认一下，我按你选的口径实施。

### P1：「其他 Tab 页也按这个样式展示」的落地范围

先明确现状，避免改错对象：

| 页面                             | 现状                                    | 是否需要改         |
| -------------------------------- | --------------------------------------- | ------------------ |
| `pages/gift-card-orders`（本页） | 双区块重复                              | **改**（P0）       |
| `pages/orders`（订单 Tab）       | 单列表，分类页签：全部/门店/储值/礼品卡 | 已是单列表，无重复 |
| `pages/stored-value`（储值）     | 充值页，非订单列表                      | 不涉及             |
| `pages/gift-card`（礼品卡）      | 购买 / 我的礼品卡双 Tab                 | 职责不同，不涉及   |

「其他 Tab 页」在订单语境下指的是 **`pages/orders` 的四个分类页签**。
该页当前已经是「一个数据源 → 一个卡片列表」，结构与改造后的礼品卡订单页一致：

- 顶部横向状态/分类页签（`orders-categories`）；
- 中间单列订单卡：门店订单走 `store-order` 卡，储值/礼品卡走 `cover-order` 卡；
- 底部 `tabbar-safe-space`。

因此「统一样式」的实际动作是**对齐视觉与交互口径**，而不是重写页面：

| 对齐项     | 礼品卡订单页（改后）                 | 订单页                 | 动作                       |
| ---------- | ------------------------------------ | ---------------------- | -------------------------- |
| 顶部筛选   | 横向状态页签，选中态 `--brand-green` | 横向分类页签，同 token | 已一致，不动               |
| 卡片信息行 | 订单号 / 卡号 / 支付时间             | 订单号 / 支付时间      | 礼品卡页按 P1 补卡号后更全 |
| 金额样式   | `--font-xl` + `--price-red`          | 同为 `--price-red`     | 已一致                     |
| 操作按钮   | 取消订单 / 继续支付 / 申请退款       | 取消订单 / 立即支付    | 保持各自业务动作           |
| 空态       | `empty-state`                        | `empty-state`          | 已一致                     |

**结论**：订单 Tab 页无需结构改造，只需在验收中确认「无重复区块、单列表、token 一致」即可。
如果你说的「其他 Tab 页」另有所指（例如储值订单也要并入订单页），请告诉我具体页面，我再补方案。

### 必须保持的既有约束

`scripts/gift-card-integration.test.mjs` 已锁定以下行为，改造时不得破坏：

- `giftOrdersJs` 不得出现 `fetchGiftCardDenominations`（不得依赖上架面额接口补全历史卡面）；
- 仍使用 `requestGiftCardPayment(orderNo)`、`refundGiftCard(orderNo`、`cancelGiftCardOrder(orderNo)`；
- 仍识别 `isRefunding` / `isRefundFailed`，退款失败排除退款中、已核销、已取消；
- 订单卡仍带 `data-order-no="{{item.orderNo}}"`；
- 主状态只允许 `CREATED / PAID / COMPLETED / CANCELED`。

> 注意：本次移除的是页面里的**卡区块**，不是删除 `fetchMyGiftCards` 的调用能力；
> P1 方案 A 仍会调用它（仅用于合并卡号），不违反上述约束。

### 验证标准

1. `cd user-h5 && npm run check` 通过（含 `gift-card-integration.test.mjs` 与新增去重测试）；
2. `cd user-h5 && npm run test:acceptance` 通过；
3. 手测：
   - 进入礼品卡订单页 → **只有一份列表**，同一笔购买不再出现两次；
   - 页签「全部/待支付/待核销/已完成/已取消」筛选正常；
   - 搜索卡号/订单号/名称正常；
   - 待支付订单可「取消订单 / 继续支付」；待核销可「申请退款」；
   - 空数据时展示 `empty-state`；
   - （P1）待核销订单卡显示卡号，未发卡订单不显示该行（不留空白）。

### 风险点

| 风险                                  | 处置                                                                          |
| ------------------------------------- | ----------------------------------------------------------------------------- |
| 删除卡区块后「待核销卡」入口消失      | 礼品卡页已有独立「我的礼品卡」Tab，能力不丢失；如需在订单页直达，可加跳转入口 |
| 卡号合并后 `orderId` 对不上导致漏显示 | 按 `orderId` 字符串比对；缺失即不渲染该行                                     |
| 误删 `fetchMyGiftCards` 能力          | 仅删页面渲染与独立 state，接口导出保留                                        |
