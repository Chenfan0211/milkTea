# 授权中心三菜单重构：账号-角色-菜单权限模型调整方案

> 日期：2026-09-25
> 需求方：产品
> 范围：运营后台「授权中心」下的 `角色与权限` / `微信账号绑定` / `角色授权记录` 三个菜单
> 状态：**已实现并验证**，实施细节见 [授权中心重构-实施记录.md](./授权中心重构-实施记录.md)

## 一、先对齐需求（我理解的 7 条目标）

| # | 你的诉求 | 我的理解 |
|---|---------|---------|
| 1 | 角色绑定账号 | 角色 ↔ 后台账号（`sys_user`，可登录运营后台）建立绑定 |
| 2 | 账号是自己手动新建的 | 在后台手填"用户名 + 初始密码"创建，**不是**小程序用户 |
| 3 | 不要把我角色和用户绑定 | 切断 `角色 ↔ app_user`（微信用户）的一切绑定 |
| 4 | 角色可分配菜单权限 | 每个角色勾选可见菜单 |
| 5 | 账号绑定角色后，登录即拥有该角色菜单权限 | 运行时按登录账号的角色动态生成菜单 |
| 6 | 超级管理员不可修改、全局唯一、独享授权中心菜单 | `R_SUPER` 唯一、不可编辑删除、唯一账号、只有它能看见/进入授权中心三个菜单 |
| 7 | 超管账号只能改密码，且只能由超管改 | 该账号不可停用/改角色/删除；改密码入口只对超管开放 |

### 需要你确认的 3 个点（影响改法，见 §5）

1. **「微信账号绑定」是删掉还是保留？**
   按你「不要和用户绑定」的要求，我建议**删除该菜单**；如果你的本意是保留它、只是把角色从中解耦，那就选保留（改为只读）。
2. **超管唯一的判定口径**：按账号唯一（`R_SUPER` 只能绑 1 个账号）还是按角色唯一（`R_SUPER` 角色记录只能有 1 条）？我按**两者都唯一**设计。
3. **其他角色能否给 `R_SUPER` 角色挂账号**：我按"不能，只有超管自己能维护"设计。

## 二、现状盘点（为什么会串味，根因在哪）

### 2.1 三张表名不副实

| 表 | 建表注释 | 实际用途 | 问题 |
|----|---------|---------|------|
| `sys_user` | 后台账号 | 后台登录账号（`admin`/`super`/`operator`/`Finance`/`Audit`） | ✅ 基本正确，但没有"创建人/是否超管账号"等约束列 |
| `sys_role` | 后台角色 | 后台角色（`R_SUPER`/`R_OPERATION`/`R_FINANCE`/`R_AUDIT`） | 没有菜单关联表 |
| `sys_user_role` | 后台用户-角色 | 后台账号 ↔ 后台角色 | ✅ 基本正确 |
| `sys_menu` | 后台菜单 | **建表了但从未使用**：无种子数据、无 `role_menu` 关联表、后端 `RouteController.getUserRoutes()` 恒返回空数组 | ❌ 菜单权限是"半成品" |
| `user_role_grant` | 用户业务角色授权 | **前端「角色授权记录」和「微信账号绑定」实际在写这张表** | ❌ 这是小程序 `app_user` 的经营角色授权，跟后台无关 |

### 2.2 前端菜单权限目前是"硬编码 + 角色码"模式

- `src/constants/admin.ts`：每个路由写死 `roles: ['R_SUPER','R_OPERATION']` 之类的数组。
- `src/router/elegant/routes.ts`（elegant-router 生成）同样写死 `roles`。
- `.env`：`VITE_AUTH_ROUTE_MODE=static` + `VITE_STATIC_SUPER_ROLE=R_SUPER`。
- 于是：**没有登录账号，前端就无法按角色过滤菜单，而且改菜单权限必须改代码重新发版。**

### 2.3 后端 `/route/getUserRoutes` 是个空壳

```java
@GetMapping("/route/getUserRoutes")
public Result<Map<String, Object>> getUserRoutes() {
    return Result.ok(Map.of("routes", List.of(), "home", "home"));
}
```
即使把 `VITE_AUTH_ROUTE_MODE` 改成 `dynamic`，也拿不到任何路由 —— 菜单权限链路根本没通。

### 2.4 「角色与权限」页面其实只有 3 个字段，和"权限"无关

`src/views/auth/role/index.vue` 走通用 CRUD（`CrudRegistry` 的 `roles` 资源，表 `sys_role`），只有：编码 / 名称 / 数据范围 / 创建时间。**没有任何菜单权限分配 UI。**

### 2.5 「微信账号绑定」页现在干的事

- 读 `app_user`（微信用户）列表；
- 「绑定微信账号」按钮 → 写 `app_user`（昵称 / openId）；
- 「查看角色」→ 读 `app_user.business_role` 并弹提示；
- 「解绑」→ 调 `unbindUserRole(userId)` → `DELETE /api/v1/admin/subject/binding/user/{userId}/role/{roleCode}/subject/{subjectId}` → 删 `user_role_grant`。

**结论：这页是小程序经营角色的绑定页，与"后台登录账号"完全无关 —— 正是你说的"把角色和用户绑起来"的地方。**

### 2.6 补充发现（顺手要修的坑，否则改完还是显示不对）

`src/views/auth/grant/index.vue` 里的 `roleLabel()` 把 `STORE` 映射成"门店"，但 `store.normalizeRemoteRow('grants')` 里做了 `roleCode: lowerRole(r.roleCode)`，即前端拿到的是小写 `store`，而映射表的 key 也是小写 —— 这一条是通的。但**该文件注释里说后端返回大写**，说明历史上出现过不一致。本次重构会把这层"前端猜大小写"的耦合彻底去掉。

另外 `AdminAuthQueryController` 的 `roles` 接口返回的 `sys_role` 没有 join 账号数量，无法在列表里显示"已绑定账号"，需要补。

## 三、目标模型（改成什么样）

### 3.1 三个菜单的新定位

| 菜单 | 新定位 | 是否超管独有 |
|------|--------|-------------|
| **账号管理**（替代「微信账号绑定」） | 手动新建 / 编辑 / 停用后台登录账号，并给账号分配角色 | ✅ 是 |
| **角色与权限**（保留原名） | 维护角色 + 给角色勾选菜单权限 + 查看/调整该角色下账号 | ✅ 是 |
| **角色授权记录**（保留原名，改数据源） | 审计流水：谁在什么时候给哪个账号授权/撤销了哪个角色 | ✅ 是 |

> 菜单顺序建议：角色与权限(1) → 账号管理(2) → 角色授权记录(3)。

### 3.2 数据模型改动

```
sys_user ──┐
           ├── sys_user_role ──┐
sys_role ──┘                  ├── sys_role_menu ── sys_menu
                              ┘
（新增）                        （新增）            （启用，补种子）

app_user ──── user_role_grant  ← 保持不动，但后台不再暴露入口
```

- **新增 `sys_role_menu`**：`role_id` + `menu_id`，唯一键 `(role_id, menu_id)`，逻辑删除。
- **启用 `sys_menu`**：补种子数据，把前端 60+ 路由落成菜单记录（`code` = 路由 name，如 `auth_role`，`parent_id` 构成树）。
- **给 `sys_role` 加 `is_builtin`**：标记内置角色（`R_SUPER` 不可删改）。用"角色码白名单"也行，但加列更直白、更好查。
- **给 `sys_user` 加 `is_super`**（可选，也可用"是否绑定 `R_SUPER`"推导）：用于"只能改密码"的强约束与列表标识。

### 3.3 权限判定链路（改动后）

```
登录 → /auth/getUserInfo 返回 roles
     ↓
前端 initAuthRoute → GET /route/getUserRoutes（VITE_AUTH_ROUTE_MODE=dynamic）
     ↓
后端：按登录账号 → sys_user_role → sys_role → sys_role_menu → sys_menu
     ↓
返回菜单树（含 path / component / title / icon）
     ↓
前端按后端返回的菜单树过滤路由并渲染侧边栏
```

**副作用（很重要）**：切到 dynamic 模式后，改菜单权限**不用改代码、不用重新发版**，超管在后台勾一下即可生效。但代价是：前端路由的 `roles` 硬编码数组要清理（否则守卫和菜单会两套逻辑打架）。

## 五、三处待你拍板

### 5.1 「微信账号绑定」菜单
- **方案 A（推荐）**：删除菜单和页面。角色只与后台账号绑定，彻底切断 `app_user` 的绑定入口。
- **方案 B**：保留菜单但改为只读。适合"还想看小程序用户经营角色分布"的场景。
- 我按 **A** 写进计划；若选 B，阶段 3.4 改为"只读化 + 去掉绑定/解绑按钮"。

### 5.2 路由模式
菜单权限要能"后台配、立刻生效"，必须把 `VITE_AUTH_ROUTE_MODE` 从 `static` 改成 `dynamic`，并把前端 `adminRouteMeta` / `routes.ts` 里写死的 `roles` 逐步交给后端菜单表。
- **如果不想动这个**：菜单权限只能做成"前端硬编码 + 数据库记录用于展示"，即**改了不生效**，不满足你的诉求 5。所以我建议必须切。

### 5.3 超管账号是否允许改名
- 我按"**用户名不可改、昵称可改、密码可改**"设计（用户名是登录凭据，改了容易产生"这到底是不是超管"的歧义）。
- 若你希望用户名也能改，我加白名单即可，但需要同步更新所有引用 `super` 硬编码的地方。

## 六、风险与注意事项

| 风险 | 影响 | 应对 |
|------|------|------|
| 切 dynamic 路由 | 现网若已用 `static` 跑通，切换后菜单渲染逻辑整体改变 | 先在测试环境验证 3 个账号的菜单；保留 `static` 作为开关兜底（`VITE_AUTH_ROUTE_MODE` 改回即可回滚） |
| `routes.ts` 是 elegant-router 生成物 | 手工改可能被下次生成覆盖 | 改 `adminRouteMeta` 或生成配置后重跑 `gen-route`，不要只改生成物 |
| 超管唯一性在并发下可能破防 | 两个请求同时绑定 `R_SUPER` 会都成功 | 迁移加唯一索引（如 `(role_id)` 上加"仅 super 生效"部分索引不适用 MySQL，改用应用层锁 + 事务内 `SELECT ... FOR UPDATE`） |
| 现有 `super` 账号口令是弱口令（`123456`） | 安全风险 | 迁移后立刻走「重置密码」流程改掉；登录页移除演示口令 |
| `FieldWriteConsistencyTest` / `DedicatedEndpointConsistencyTest` | 新增页面若漏登记会导致 CI 红 | 新页面走专用接口的，需在 `DedicatedEndpointConsistencyTest.COVERED_PAGES` 与 `BACKEND_IMPLEMENTATIONS` 登记 |

## 八、我不打算动的东西（避免扩大范围）

- `user_role_grant` 表和它承载的小程序经营角色授权链路 —— **保持原样**，只是后台不再暴露入口。
- `小程序端` authorization 代码（`utils/roles.js` 等）—— 与本次需求无关。
- 其他模块的 `roles` 硬编码（商品/交易/营销等）—— 本次只收紧 `auth` 分支；全量迁移到 dynamic 建议单独立项。
