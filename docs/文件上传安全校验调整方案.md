# 文件上传安全校验调整方案（P0：内存防护 + 网关兜底）

> 范围：P0（流式读取 + 网关大小兜底）+ P1（脚本扩展名黑名单补充）。状态：已实施并通过测试（39 个用例全绿）。
> 依据：docs/微服务改造方案.md 第五章；现状代码 file-service + gateway。

## 一、现状与问题定位

### 1.1 现有防护（已具备，勿重复建设）

- Magic Bytes 白名单：只允许 jpg/jpeg/png，扩展名与真实文件头一致才放行（FileTypeValidator）
- 禁用扩展名黑名单：exe/dll/so/sh/bat/cmd/ps1/js/jar/php/jsp/asp/py/rb/pl/html/htm/svg
- UUID 重命名防路径穿越/覆盖（ImageStorageService.store）
- 图片重编码：解码后重新编码，剥离元数据与 Polyglot 载荷
- 双层大小限制：application.yml multipart max-file-size=5MB / max-request-size=6MB
- 网关限流（RequestRateLimiter）+ 熔断（CircuitBreaker）

### 1.2 本次要解决的缺口

| 缺口 | 风险 | 现状 |
|------|------|------|
| 整文件读入堆内存 | 并发大文件上传打爆 JVM 堆（DoS） | `file.getBytes()`、`store(byte[])` 全量读入 |
| 网关无请求体大小硬上限 | 大文件先进入网关内存才被拦 | 网关为 WebFlux，未配 codec 限制 |

## 二、调整方案

### P0-1：file-service 流式读取（核心）

目标：签名/尺寸判断阶段不加载全文件，只有确认尺寸合法后才做全量解码重编码。

改动文件：
- `file-service/src/main/java/com/wuling/file/service/ImageStorageService.java`
- `file-service/src/main/java/com/wuling/file/service/UploadValidationService.java`
- `file-service/src/main/java/com/wuling/file/controller/FileController.java`

做法：
1. `FileController.uploadImage` 由 `file.getBytes()` 改为 `file.getInputStream()`；
2. `ImageStorageService.store` / `UploadValidationService.validate` 增加 InputStream 重载：
   - 先 `readNBytes(16)` 做 magic bytes 判定（此时不读全量）；
   - 用 `ImageIO.createImageInputStream(input)` 流式读 header，`reader.getWidth/getHeight` 判尺寸（不 decode 全图）；
   - 尺寸合法后，才 `reader.read(0)` 全量解码并重编码；
3. 保持现有 `byte[]` 重载兼容（供 validate 接口与测试使用）。

收益：恶意超大文件在前 16 字节即被拒，几乎不占内存。

### P0-2：gateway 网关请求体硬上限

目标：拦截在进入 file-service 之前，超大请求体直接 413。

改动文件：`gateway/src/main/resources/application.yml`

做法：在 `spring` 下新增（WebFlux 用 codec，不是 servlet multipart）：

```yaml
spring:
  codec:
    max-in-memory-size: 6MB
```

说明：与 file-service 的 `max-request-size: 6MB` 保持一致，形成双层兜底。

## 三、验证标准

1. 上传 > 5MB 图片 → file-service 返回「文件超过大小限制（5MB）」；
2. 上传 > 6MB 请求体 → 网关返回 413（先于 file-service）；
3. 上传 5MB 内合法图片 → 正常重编码落盘并返回 URL；
4. 单测反向验证：故意传 16 字节截断文件、空流、超大流，确认均被拒；
5. `cd file-service && mvn test` 全绿，无回归。
