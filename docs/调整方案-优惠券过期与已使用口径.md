# 调整方案：优惠券「已过期」不归档 & 过期券混在「已使用」

> 日期：2026-10-15
> 现象：小程序「我的优惠券」里，有效期已过的券出现在「已使用」Tab；而「已过期」Tab 永远是空的
> 状态：✅ 已实施（2026-10-15，口径经确认后按 P0 → P1 → P2 落地）

---

## 一、排查结论（生产库只读核验）

### 1.1 现场数据

`user_coupon` 状态分布（`deleted=0`）：

| status  | 张数  | 其中已过有效期 |
| ------- | ----- | -------------- |
| UNUSED  | 8     | **6**          |
| USED    | 11    | **9**          |
| EXPIRED | **0** | —              |
| LOCKED  | 0     | —              |

券模板共 4 张，**全部是 `validity_type=DAYS`**（15 / 30 / 7 天；券 `referral-coupon-3` 另带 3 天延迟生效），
即模板没有 `validity_end`，每张券的过期时间 = 领取时间 + N 天（+ 延迟天数）。

11 张 `USED` 券 **全部有 `use_time`**（确实核销过），其中 9 张的「领取 + N 天」已经过去。

复核用 SQL（只读，可直接在生产执行）：

```sql
select uc.status, count(*) as cnt,
       sum(case when c.validity_type = 'DAYS'
                and now() > date_add(date_add(uc.receive_time, interval ifnull(c.effective_delay_days,0) day),
                                     interval c.validity_days day)
                then 1 else 0 end) as expired_now
from user_coupon uc
join coupon c on c.id = uc.coupon_id
where uc.deleted = 0
group by uc.status;
```

```
UNUSED | 8  | 6
USED   | 11 | 9
```

### 1.2 根因 1（P0）：没有任何流程把「过期未用券」落库为 EXPIRED

`marketing-service/src/main/java/com/wuling/marketing/service/CouponService.java`

- `myCoupons(userId, 'EXPIRED')` → `query.eq(status, 'EXPIRED')`（第 91-92 行）**直接按库表状态查**；
- `myCoupons(userId, 'UNUSED' / 不传)` → 取 `UNUSED` 池后在 Java 里用 `validity.usable()` 过滤（第 148 行），
  **把已过期的券丢掉**；
- 全仓只有 `restoreAfterRefund()`（第 603 行，退款恢复）会写 `EXPIRED`，
  **没有定时任务/批处理把过期 UNUSED 置为 EXPIRED**（已全仓 grep `EXPIRED` 写入点确认）。

⇒ 结果：**过期未用的券，既不在「未使用」（被 Java 过滤掉），也不在「已过期」（库里没有 EXPIRED 行）= 凭空消失**。
生产当前就有 **6 张**处于这个状态。

### 1.3 根因 2（P1）：已使用券缺少「过期」展示口径

`USED` 是终态，被用过之后即使有效期过了也留在「已使用」——**这个分类本身是行业惯例，不算错**。
问题在于卡片仍按「这张券还在有效期内」的方式渲染：

- 卡片到期文案直接取 `expireAt`（`user-h5/utils/coupons.js:85` → `2026-10-13 03:41 到期`），
  对已使用的券来说这必然是一个**过去的日期**，渲染在券包里就非常像「已过期」；
- 券包按 Tab 把整张卡置灰（`user-h5/pages/coupon-list/coupon-list.js:78-86`），
  「已使用 + 灰掉 + 到期时间是过去」三者叠在一起，用户自然会问「都过期了怎么还在已使用」。

生产 11 张 USED 里 9 张是这种情况 —— 也就是说**用户看到的现象主要是展示口径造成的，不是数据错了**。

### 1.4 根因 3（P1）：前端把「不可用」当成「已过期」

`user-h5/utils/coupons.js:104`：

```js
expired: source.usable === false || Boolean(source.expired),
```

而 `UserCouponView`（`marketing-service/.../dto/UserCouponView.java`）**根本没有 `expired` 字段**，
`usable` 的语义是「此刻能不能用」——`USED` / `LOCKED` 天然就是 `false`，
于是**每一张已使用/锁定的券在前端都被标成 `expired = true`**。

目前券包列表没有直接渲染这个字段（`coupon-list.wxml` 只用 `usable` / `statusText`），
但 `getUsableCouponCount()`（`utils/coupons.js:126`）依赖它 —— 语义地雷已经埋在「券张数」上。

### 1.5 附带发现（P2）：「券张数」读的是会被其它 Tab 覆盖的缓存

`refreshCouponsFromRemote(status)` 把**当前 Tab 的结果**整体写进同一个缓存键 `milkTea:coupons`
（`user-h5/utils/coupons.js:110-117`），而首页 / 我的页的「优惠券 N 张」用 `getUsableCouponCount()`
读这份缓存。用户只要打开过券包的「已使用」Tab，缓存里就全是 USED 券（且 `expired=true`），
「我的」页首屏会先显示 0，要等 `onShow` 重新拉一次 UNUSED 才纠正。

（工作区里已有在途改动把「我的」页张数统一到券包缓存 —— 方向正确，但没有消除「缓存被别的 Tab 覆盖」这个根因。）

### 1.6 存量数据性质：11 张「已使用」里有 8 张不是真实核销

进一步按「是否有订单」拆开看（`lock_order_id` 是核销时写入的订单标识）：

| 券 id                                         | user      | 来源                      | use_time                       | lock_order_id | 判定                                      |
| --------------------------------------------- | --------- | ------------------------- | ------------------------------ | ------------- | ----------------------------------------- |
| 115 / 137 / 138                               | 7         | RECEIVE / POINTS_EXCHANGE | 各不同                         | 有订单号      | **真实核销**（`orders` 里能查到对应订单） |
| 102 / 103 / 106 / 107 / 108 / 112 / 113 / 114 | 1 / 2 / 7 | RECEIVE                   | **全部 = 2026-09-22 18:56:09** | **NULL**      | 疑似**批量造数/直写库**                   |

`orders` 里带券的订单只有 6 笔，且 `orders.coupon_id` 存的是 **user_coupon.id**（不是券模板 id），
其中 134 / 135 那几张券已经因为订单取消/退款被回退（不在 USED 里）。

结论：

- 代码路径本身是安全的 —— `UserCouponMapper.consumeLocked` 要求
  `status='LOCKED' and lock_order_id = ?`（`marketing-service/.../mapper/UserCouponMapper.java:36-38`），
  正常核销**必然带订单号**；
- 那 8 张 `use_time` 同一秒、且没有订单号的 USED 券，是**绕过业务代码直接写库**留下的脏数据；
- 如果用户看到的正是 user 1/2/7 这批券，那么「过期了却在已使用」的直接原因是**造数**，不是展示口径 ——
  但 1.2 的「过期券不归档」仍然是真缺陷（6 张过期未用券现在谁都看不到）。

## 二、调整方案

分三块：**后端状态口径（P0）→ 前端展示口径（P1）→ 计数与存量数据（P2）**。

### 2.1 后端：四态统一推导 + 显式返回 `expired`（P0）

改 `CouponService.myCoupons()`：不再「终态直接透传、其余在 Java 里补过滤」，而是**统一按「状态 + 有效性」推导四态**：

| Tab        | 归属规则                                                          |
| ---------- | ----------------------------------------------------------------- |
| 未使用     | `status=UNUSED` 且 已生效 且 未过期                               |
| 待生效     | `status=UNUSED` 且 未生效                                         |
| **已过期** | `status=EXPIRED` **或**（`status=UNUSED` 且 已过期） ← 本次新增   |
| 已使用     | `status=USED`（含已过期的）——**终态优先，一张券只出现在一个 Tab** |
| 锁定       | `status=LOCKED`：见 2.5 待拍板                                    |

实现要点：

1. 抽一个 `isExpired(userCoupon, coupon, now)`（复用 `resolveValidity` 已算出的 `expireAt`）；
2. `EXPIRED` 分支的 SQL 从「只查 `status='EXPIRED'`」改成「查 `UNUSED` + `EXPIRED` 两个状态，再按有效期分流」——
   这样**不依赖任何后台任务**也能正确展示，任务停摆不会导致回归；
3. `UserCouponView` 新增 `Boolean expired`（后端算：`status=EXPIRED || (status=UNUSED && 已过期)`），前端不再猜；
4. `usable` 语义**保持不变**（「此刻能不能用」），但要在 DTO 注释里写明，避免再被当成「是否过期」；
5. 新增单测：四态互斥（同一批数据查四个 Tab，并集不重复）。

### 2.2 建议一起做：过期券落库归档（P0 补充）

新增 `CouponExpireSweepJob`（`@Scheduled`，写法对齐现有 `StoredValueOrderTimeoutSweepJob`，分批 500）：

```
把 status='UNUSED' 且已过有效期的券 update 成 'EXPIRED'（where status='UNUSED' 保证幂等）
DAYS  ：now > 领取时间 + 延迟天数 + 有效天数
RANGE ：validity_end 非空且已过
```

- 好处：状态可索引、可统计（现在只能 join 现算 `expired_now`）；
- **展示层不依赖它**（2.1 已自洽），任务停多久用户都不会看到错分类；
- 每批写一条审计汇总，避免逐券审计刷爆 `audit_log`。

### 2.3 前端：过期文案分层（P1）

| 位置                   | 现状                                 | 调整                                                                                           |
| ---------------------- | ------------------------------------ | ---------------------------------------------------------------------------------------------- |
| 券包卡片（已使用）     | 置灰 + 「xx 到期」（过去日期）       | 状态固定「已使用」；到期文案降级为「已于 xx 过期」或直接不显示，**不呈现为过期/警示态**        |
| 券包卡片（已过期）     | 无数据（见 1.2）                     | 显示「已过期」+ 过期时间（2.1 上线后才有意义）                                                 |
| `utils/coupons.js:104` | `expired: usable === false \|\| ...` | 改为读后端 `source.expired`（无该字段时兜底 `status === 'EXPIRED'`），**不再由 `usable` 推断** |
| `coupon-list.js:78-86` | 按 Tab 决定 `usable` / `statusText`  | 保留；`expired` 只用于「已过期」样式，不参与置灰判断                                           |

### 2.4 券张数口径（P2）

`utils/coupons.js` 增加**独立计数缓存** `milkTea:coupons:usable-count`：

- 只有「UNUSED 口径」的拉取（首页 `refreshCouponsFromRemote()`、我的页 `refreshCouponsFromRemote('UNUSED')`）才写它；
- 券包其它 Tab 的拉取**不再污染**该计数；
- 更彻底的做法：直接用 `/users/{id}/coupons?status=UNUSED` 返回的 `list.length`，缓存只作首屏占位。

### 2.5 已确认的口径（2026-10-15 定稿，已按此实现）

1. **LOCKED（下单占用、未支付）**：归「未使用」Tab 展示，卡片标注「订单占用中」，且不可点「去使用」
   （后端对该券返回 `usable=false`）。
2. **「待生效」（PENDING）不计入「优惠券 N 张」**：只统计真正可用的未使用券
   （已生效、未过期、未被订单占用）；后端对 PENDING 返回 `usable=false`，前端计数与下单页选券同时受益。

## 三、存量数据处理

### 3.1 过期未用的券（6 张，UNUSED 且已过有效期）

- 做 2.1 后**不需要动数据**即可正确出现在「已过期」；
- 若同时做 2.2，任务会把它们自然落库为 EXPIRED；
- 两者结果一致，**建议 2.1 + 2.2 一起上**，由任务收敛，避免手工 SQL 绕过审计口径。

### 3.2 无订单的「已使用」脏数据（8 张）

- **先确认来源**：这 8 张的 `use_time` 完全一致（`2026-09-22 18:56:09`），像是发版/演示时批量造的；
  若确认是演示数据，可在**非生产**或经批准后清理（改回 `UNUSED` 或按 2.1 判为 `EXPIRED`），
  并补一条 `audit_log` 说明「存量脏数据修正」；
- **加一条体检 SQL**（建议纳入运维巡检，而不是自动改数）：

```sql
-- 应为 0：已使用但没有订单号的券（正常核销必然带 orderId）
select count(*) from user_coupon where deleted = 0 and status = 'USED' and lock_order_id is null;
```

- 若希望这类脏数据永远不再出现，可在核销写入处再加一道断言（现有 SQL 已足够，属于防御性加固，优先级低）。

## 四、验证标准

### 自动化（新增/加强）

1. `status=EXPIRED` 必须返回「已过期但仍为 UNUSED 的券」；
2. `status=USED` 必须仍返回「已使用且已过期」的券（现有用例 `myCouponsExplicitTerminalStatusReturnsRowsDirectly` 保留，补 `expired=true` 断言）；
3. `status=UNUSED` 不得返回任何已过期券（现有行为，不能回归）；
4. **四态互斥**：同一批数据分别查四个 Tab，并集无重复、无遗漏；
5. `CouponExpireSweepJob`：已过期 → EXPIRED；未过期不动；重复执行幂等；分批生效。

### 手工（小程序）

1. 过期未用的券出现在「已过期」，且不再出现在「未使用」；
2. 已使用且已过期的券在「已使用」，卡片显示「已使用」，**不再呈现为已过期样式/红字**；
3. 「我的」页与首页的券张数：先逛一遍「已使用」Tab 再返回，张数不应变 0；
4. 四个 Tab 各切一次，任意一张券不会同时出现在两个 Tab。

### 生产核对（只读）

`status='EXPIRED'` 的张数应等于「过期未用券」张数；「已过期」Tab 能查到当前那 6 张。

**执行中发现的约束（重要）**

第一次执行时撞上唯一键 `uk_user_coupon_active`：

### 7.6 用户数据隔离（审计 + 修复，2026-10-15）

需求：券与用户是绑定关系，每个用户的券数据必须隔离。
