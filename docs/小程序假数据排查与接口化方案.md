# 小程序端假数据排查与接口化改造方案

> 日期：2026-09-25
> 目标：把小程序端仍在使用假数据的地方，全部改为调用后端接口获取/提交。

---

## 一、排查结论（哪些是假数据、哪些不是）

先明确判定标准：**「假数据」= 业务数据由前端本地伪造/写死，不落库、不调后端**。
据此把小程序端数据分为三类：

### A 类：真正的假数据（需要整改）—— 共 1 个模块

| 模块 | 现状 | 问题 |
|------|------|------|
| **`utils/invest.js`（投资人点位投资申请）** | 提交、列表、详情、统计**全部走 localStorage**（`milkTea:invest-applications`），完全不调后端；`INVESTOR_ID = 'INV-1001'` 写死 | 申请数据不落库，换设备/清缓存即丢；运营后台看不到任何投资申请，无法审核；投资人 ID 写死，无法对应真实用户 |

涉及页面（全部读该本地存储）：

- `pages/role-invest/role-invest.js`（投资点位列表 + 统计）
- `pages/role-invest-apply/role-invest-apply.js`（提交申请表单）
- `pages/role-invest-records/role-invest-records.js`（申请记录）
- `pages/role-invest-detail/role-invest-detail.js`（申请详情）

### B 类：已接后端，仅剩「展示兜底」（不用改，属于合理降级）

这些已通过 `api.js` 调后端，只是接口失败时有本地兜底文案/默认值，
**不是假数据**，属正常 UI 容错：

- 头像默认图 `DEFAULT_AVATAR`（用户未授权时）
- 默认城市 `DEFAULT_CITY_CODE`（定位失败时）
- 分享默认标题/图片 `DEFAULT_SHARE_*`
- 提现/结算规则内置兜底文案（接口失败时保证可读）
- 门店类型 `storeTypes` 兜底枚举（客户端固定枚举）
- 各状态枚举 `INVEST_STATUS_TEXT` / `INCOME_STATUS_TEXT` 等（纯 UI 文案）

### C 类：已彻底接后端（确认无需改）

门店 / 菜单 / 商品 / 订单 / 优惠券 / 储值 / 礼品卡 / 积分 / 签到 / 
会员等级 / 城市 / 运营配置 / 角色 / 工作台 / 收益 / 提现 / 评论 —— 
均已通过 `utils/api.js` 的接口获取与提交，见 `api.js` 中约 80 个接口。

> 历史说明：`data/mock.js` 头部已注明「阶段 C 假数据清理」后只剩 UI 枚举；
> `data/service.js` 也已改为读门店接口。这两处无需再动。

## 二、整改目标：投资申请模块接口化

唯一需要动的是 **投资人点位投资申请**。

### 2.1 关键发现：后端基础设施已就绪

后端已有完整的「角色申请」链路，投资申请可**直接复用**，无需新建表和接口：

| 后端已有 | 位置 | 作用 |
|---------|------|------|
| `role_application` 表 | 已存在（含 user_id / role_type / applicant_name / applicant_phone / extra_form / status / subject_id 等） | 存申请记录 |
| `AppRoleController.apply` | `POST /api/v1/app/roles/apply` | 提交角色申请（前端 `applyBusinessRole` 已接） |
| `AppRoleController.myApplications` | `GET /api/v1/app/roles/applications` | 我的申请记录 |
| `SubjectBindingController.reviewApplication` | `POST /api/v1/admin/subject/binding/application/{id}/review` | 运营审核（通过则写 user_role_grant + app_user.bound_subject_id） |
| `RoleWorkbenchController.investorStores` | `GET /api/v1/app/workbench/investor/{id}/stores` | 投资人已签约的门店 |

> **核心洞察**：投资人投资某门店，本质就是「申请 role_type=investor 并绑定到某个门店 subject」。
> 现有的 `role_application` + 审核链路**天然覆盖这个语义**，只是前端 `invest.js` 绕过了它。

### 2.2 需要补的缺口（后端小改）

现有 `role_application` 的 `apply` 接口设计给「开通角色」用，投资人投资申请有两个差异点需确认/补齐：

| 差异 | 现状 | 需补充 |
|------|------|--------|
| 申请对象是「具体门店」 | `apply` 的 `subjectId` 是可选的、审核时才定 | 投资申请需在**提交时**就指定门店（`subject_id` + `extra_form` 里存点位信息） |
| 申请字段（预算/联系人/备注） | `apply` 已把表单 JSON 序列化进 `extra_form` | **已支持**，只需前端把 budget/contact/phone/remark 传进去 |
| 投资人列表查「全部可投门店」 | `getSpots` 用本地 storeCatalog | 后端 `investorStores` 只返回**已签约**门店，需一个「可投点位列表」接口（或用现有 `fetchStores` + 前端标记状态） |

**方案**：优先**复用 `role_application` 现有链路**，最小改动：

1. 前端 `invest.js` 改为调用 `applyBusinessRole('investor', form)`（api.js 已有），
   form 里带上 `subjectId`（门店 id）+ 预算/联系人/备注；
2. 列表/记录改为调 `fetchRoleApplications()`（api.js 已有）；
3. 审核沿用现有后台审核接口（无需新增）。

唯一需后端确认的是：`apply` 接口当前是否接受 `subjectId` 并在 `role_application.subject_id` 落库。
从 `AppRoleController.apply` 源码看，它**暂未处理 `subjectId`**（只存 role_type + extra_form），
故需给 `apply` 补一行「若 payload 带 subjectId 则写入 subject_id」。

## 三、执行步骤（建议顺序）

### 第 1 步：后端补 `apply` 支持 subjectId

- `AppRoleController.apply`：读取 `payload.get("subjectId")`，非空时在 INSERT 语句带上 `subject_id`。
- 加幂等约束：同一用户对同一门店已有 PENDING/APPROVED 申请则拒绝（现有按 role_type 判重，需改为按 subject_id 判重）。

### 第 2 步：前端 `invest.js` 接口化

- 删掉 `INVEST_STORAGE_KEY` 本地读写；
- `submitApplication` → `applyBusinessRole('investor', form)`；
- `listApplications` / `getApplicationDetail` → `fetchRoleApplications()` + 过滤 role_type=investor；
- `getInvestStats` → 基于后端申请 + `fetchStores` 计算；
- `INVESTOR_ID` 写死 → 从 `getCurrentSubjectId()`（roles.js 已有，读 `/roles/mine` 的绑定主体）取真实投资人主体 id。

### 第 3 步：运营后台审核连通

- 后台「角色申请审核」页已走 `reviewApplication`，投资人申请进入同一队列，
  审核通过即写 `user_role_grant` + `app_user.bound_subject_id` + `biz_subject.bound_user_id`。

### 第 4 步：验证

- 前端提交投资申请 → 后台看到 PENDING → 审核通过 → 前端刷新显示已签约；
- 换设备/清缓存后申请记录仍在（落库）；
- 删掉 localStorage 数据不影响功能。

## 四、影响范围与风险

| 项 | 说明 |
|----|------|
| 改动范围 | 后端 `AppRoleController`（约 5 行）+ 前端 `utils/invest.js`（重构）+ 4 个投资页面（改数据来源） |
| 数据迁移 | **无需**——旧 localStorage 数据本就不是正式数据，清空即可 |
| 风险 | 低——复用已验证的角色申请链路，不新建表/接口 |
| 回滚 | 前端保留旧 invest.js 即可回退（后端只是补 subjectId，向后兼容） |
