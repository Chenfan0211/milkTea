# 修复：绑定经营角色后列表不自动刷新

> 日期：2026-09-25
> 现象：用户列表点「绑定」→ 选经营者类型 → 选具体主体 → 确定，**列表没变化**，手动刷新才显示
> 状态：✅ 已修复并上线

---

## 一、根因：异步 handler 漏了 await（竞态）

`src/views/_shared/AdminListPage.vue` 的 `confirmCascadePicker`（级别联选择确认）：

```js
// ❌ 修复前：没 await 就刷新
pendingCascadeAction.value?.cascadePicker?.handler?.(row, {...});
loadData();   // handler 还在等接口写库，这里就已发出查询 → 读到绑定前的旧数据
```

`bindUserRole` 是**异步**的（内部 `await bindUserRoleApi(...)` 要等后端写库返回），
但不 await 就直接 `loadData()`，于是**刷新请求早于写库完成**，查到的自然是旧数据。

### 为什么「解绑」正常、「绑定」失效？

这是排查时最关键的一条线索 —— 两个按钮走的是**不同的确认路径**：

| 按钮 | 触发路径 | 是否 await | 结果 |
|------|---------|-----------|------|
| 解绑 | `reasonPrompt` → `confirmReason` | ✅ 有 await | 正常刷新 |
| 绑定 | `cascadePicker` → `confirmCascadePicker` | ❌ 漏了 await | 不刷新 |

`confirmPicker` / `confirmReason` 一直都有 await —— 说明这是**遗漏**而非设计缺陷，
靠人工 review 极易漏看（同一文件里三种 handler 写法，只有一种漏了）。

## 二、修复内容

`src/views/_shared/AdminListPage.vue`：

| 函数 | 改动 |
|------|------|
| `confirmCascadePicker` | 改 `async` + `await` handler + `await loadData()`；**加 try/catch**（失败保留弹窗，可改选重试）|
| `confirmGroupPicker` | 同类问题一并修（当前无页面使用，属预防）|
| `handleAction` | 裸 handler 也补 `await`（当前均为同步，属预防）|

> 一次性修完整类问题，而不是只修被报告的那一处 —— 避免「修一个、漏两个」。

| 文件 | 说明 |

## 六、过程记录：一个差点得出错误结论的坑

注入实验后**单独跑**测试通过，**全量跑**却失败 —— 一度怀疑代码又有问题。

**根因**：Maven 增量编译未重新编译已恢复的测试源（`.class` 时间戳比源文件新），
跑的是注入实验时编译的旧 class。删掉旧 `.class` 重跑即通过。

> 这类构建缓存假象会让人得出**相反的错误结论**（既可能误判「修好了」，也可能误判「又坏了」）。
> 注入实验后复验务必确认重新编译。
