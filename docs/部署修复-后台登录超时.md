# 运营后台登录"超时"修复（IP 入口切换）

> 日期：2026-09-23
> 现象：`http://43.136.91.239:8088` 打开后台，点「确认」登录，Network 里 `login` 请求
> 显示 `(canceled)`，耗时约 10.02s，登录无法完成。

## 一、根因（不是后端慢，是请求地址错配）

**关键事实**：后台前端产物里把接口基址**硬编码**为 HTTPS 域名。
（`assets/router-*.js` 内 `VITE_SERVICE_BASE_URL: https://api.wulingshiguang.top`）

而当时的访问链路是：

| 项 | 值 |
|----|----|
| 页面入口 | `http://43.136.91.239:8088/`（纯 HTTP + IP） |
| 前端实际请求的接口 | `https://api.wulingshiguang.top/auth/login` |
| 域名 443 | **未配置证书**（HTTPS 待办） |
| 8088 的 nginx server 块 | **只有静态文件，没有 API 反代** |

于是浏览器去连 `https://api.wulingshiguang.top`（443 无服务/无证书），
握手阶段卡死，最终前端超时放弃 → 表现为 `(canceled)` 约 10s。

**已验证的证据**：

```
POST http://43.136.91.239:8088/auth/login   -> 405 Not Allowed（静态站不代理接口）
POST http://43.136.91.239:8089/auth/login   -> 200 {"code":1001,...} 0.13s（正常）
```

> 结论：这是**部署衔接问题**（入口与构建基址不匹配），与 auth-service 性能无关。

## 二、修复方案（走 IP + 纯 HTTP）

按需求选择「走 IP 地址调用」，即：页面与接口都指向同一台服务器的 IP，
彻底绕开尚未配置的域名与 HTTPS 证书。

**改动 1：新增构建配置 `src/.env.prod-ip`**

```
VITE_SERVICE_BASE_URL=http://43.136.91.239:8089
```

**改动 2：`package.json` 新增脚本**

```
"build:prod-ip": "vite build --mode prod-ip"
```

**改动 3：重新构建并部署到 `/opt/wuling/web`**

```powershell
pnpm build:prod-ip
scp dist -> 服务器 /opt/wuling/web
```

## 三、验证结果

| 项 | 结果 |
|----|------|
| 产物内基址 | `http://43.136.91.239:8089` ✅ |
| 产物内 HTTPS 域名残留 | 0 处 ✅ |
| 8088 页面 | HTTP 200 ✅ |
| `POST :8089/auth/login` | HTTP 200，耗时 **0.13s**（原 10s canceled）✅ |
| auth-service 日志 | `POST /auth/login status=200 cost=96ms` ✅ |
| 跨域预检（Origin=8088） | 200，`Access-Control-Allow-Origin: http://43.136.91.239:8088` ✅ |

## 四、备份与回滚

备份：`/opt/wuling/backup/web-pre-ipfix-<时间戳>.tar.gz`，旧产物保留在 `/opt/wuling/web.old-ipfix`。

回滚：

```bash
rm -rf /opt/wuling/web && mv /opt/wuling/web.old-ipfix /opt/wuling/web
systemctl reload nginx
```

## 五、遗留待办（重要）

| 优先级 | 项 | 说明 |
|--------|----|------|
| **P0** | HTTPS 证书未配置 | 当前走 IP + 明文 HTTP，**登录口令在公网明文传输**，仅可作临时过渡 |
| P1 | 域名入口同样错配 | `wulingshiguang.top`（80）指向后台静态站，同样需按同源相对路径收敛 |
| P1 | 构建基址应收敛为同源 | 长期方案：`VITE_SERVICE_BASE_URL=/`，由 nginx 统一反代，避免入口/基址再次错配 |
| P2 | systemd 遗留单体 | `wuling-server.service` 仍 `active`，与 `wuling-server` 容器抢 8090，应 stop + disable |

# 后台登录错误提示修复（中文 + 水平居中弹窗）

> 日期：2026-09-23
> 需求：登录失败要返回**中文错误信息**，并以**水平居中弹窗**展示。

## 一、根因（两个真实 Bug）

### Bug 1：前端读错字段名，中文错误信息取不到

后端 `Result` 的字段名是 **`message`**：

```json
{"code":1001,"message":"用户名或密码错误","data":null}
```

但前端模板按 **`msg`** 读取（`src/service/request/index.ts` 内
`response.data.msg` / `error.response?.data?.msg`），取到 `undefined`，
中文错误信息无法显示。

**修复**：`shared.ts` 新增 `getBackendMessage(data)`，优先读 `message`、
回退 `msg`；`index.ts` 全部 6 处 `.msg` 引用改为调用该方法；
`src/typings/app.d.ts` 的 `Response` 类型同步为 `message`（`msg` 标记为可选兼容）。

### Bug 2：错误提示是右上角轻提示，不是居中弹窗

原实现用 `window.$message?.error(...)` —— 这是**右上角**的 transient toast，
不符合「水平居中弹窗」要求。

**修复**：`showErrorMsg` 改用 `window.$dialog.error(...)`（水平+垂直居中），
并在 `global.css` 增加 `.error-dialog-center` / `.login-error-dialog-center`
样式保证内容居中、窄屏不溢出。

## 二、改动清单

| 文件 | 改动 |
|------|------|
| `src/service/request/shared.ts` | 新增 `getBackendMessage`；`showErrorMsg` 改为居中弹窗 |
| `src/service/request/index.ts` | 6 处 `response.data.msg` → `getBackendMessage(response.data)` |
| `src/typings/app.d.ts` | `Response.message` 为主字段，`msg` 可选兼容 |
| `src/views/_builtin/login/modules/pwd-login.vue` | 表单校验失败也弹居中弹窗（提示"请输入用户名和密码"） |
| `src/styles/css/global.css` | 新增弹窗居中样式 |

### 登录被锁定（附带问题）

多次失败触发 `LoginAttemptGuard` 防爆破锁定（5 次失败锁 15 分钟），
Redis 键位于 **SMS 命名空间（db1）**：

```
wuling:sms:login:lock:ip:<IP>
wuling:sms:login:fail:user:<用户名>
```

解除方式（仅限运维排查，勿在生产随意执行）：

```bash
docker exec wuling-redis redis-cli -a <REDIS_PASSWORD> -n 1 del \
  "wuling:sms:login:lock:ip:<IP>" "wuling:sms:login:fail:ip:<IP>" "wuling:sms:login:fail:user:admin"
```

# 快捷登录账号入库（V21）

> 日期：2026-09-23
> 需求：登录页「其他账号登录」的 4 个快捷按钮要能真正登录，账号需存到数据库。

## 一、改动前的问题

登录页 4 个快捷按钮（超级管理员 / 运营 / 财务 / 审计）在前端**硬编码**了
`Super` / `Admin` / `Finance` / `Audit` + 口令 `123456`，
但数据库中只有 `admin` 一个账号 → **点击必然登录失败**。

同时发现角色不齐：前端路由（`src/constants/admin.ts`）需要 4 个角色码
`R_SUPER` / `R_OPERATION` / `R_FINANCE` / `R_AUDIT`，
而库中只有 `R_SUPER` 和 `R_ADMIN`（`R_ADMIN` 前端根本未使用，`R_OPERATION` 缺失），
即使用运营账号登录也看不到任何菜单。

## 二、关键约束：username 不区分大小写

`sys_user.username` 的 collation 是 **`utf8mb4_unicode_ci`**（大小写不敏感），
因此 `'Admin'` 与 `'admin'` 在库中**视为同一账号，无法共存**。

> 这是「运营」按钮必须改名的根本原因：
> 原按钮用 `Admin`，实际会命中主账号 `admin`（口令 `Admin@123`），
> 而按钮传的是 `123456` → 口令不匹配 → 登录失败。

**处置**：新建独立账号 **`operator`** 承担「运营」角色，
前端按钮用户名同步由 `Admin` 改为 `operator`，**不动主账号 `admin` 的口令**。

## 三、迁移内容

新增 `server/src/main/resources/db/migration/V21__seed_admin_quick_login_accounts.sql`：

| 步骤 | 内容 |
|------|------|
| 1 | 补角色：`R_OPERATION` / `R_FINANCE` / `R_AUDIT`（`R_SUPER`、`R_ADMIN` 保持不变） |
| 2 | 建账号：`super` / `operator` / `Finance` / `Audit`，口令统一 `123456`（BCrypt `$2a$10`） |
| 3 | 绑角色：super→R_SUPER、operator→R_OPERATION、Finance→R_FINANCE、Audit→R_AUDIT |

**幂等设计**：角色用 `ON DUPLICATE KEY UPDATE code=VALUES(code)`；
账号以 `username` 唯一键去重（只对齐昵称/状态，不覆盖口令）；
绑定用 `NOT EXISTS` 判重后插入。**可重复执行**（已连跑 3 次验证，行数无膨胀）。

## 四、前端配套改动

`src/views/_builtin/login/modules/pwd-login.vue`：

```diff
-    userName: 'Admin',
+    userName: 'operator',
     password: '123456'
```

# 运营后台：规格菜单下线 + 商品接库 + 全页测试数据（V22）

> 日期：2026-09-23

> 追加要求：保留「成本价/平台分佣」两列；测试数据须便于后续测试使用。

## 一、执行中发现并修复的 3 个真实 Bug

### Bug 1（阻塞级）：管理端 token 无法通过 product-service 鉴权

| Token | 签发方 | `type` |
|-------|--------|--------|
| 管理端 | `JwtTokenProvider` | `access` |
| 小程序 | `MiniAppTokenProvider` | `mini` |

`ProductSecurityConfig` 把**小程序拦截器** `MiniAppAuthInterceptor`
（强校验 `type == "mini"`）注册到**管理端路径** `/api/v1/admin/product/**`，
导致后台 token 访问商品接口**必然 401**。

实测：
```
GET /api/v1/admin/crud/productCategories -> 200   （走 server，正确）
GET /api/v1/admin/product/list          -> 401 「无效的令牌」 ❌
```

此前未暴露，因为商品页读的是**本地假数据、从未调用该接口**。

**修复**：`security-common` 新增 `AdminJwtVerifier` / `AdminUser` / `AdminAuthInterceptor`
（校验 `type == access`），product-service 改用它。
排查确认**其它服务无同类误用**（都只保护 `/api/v1/app/**`，用小程序拦截器是正确的）。

### Bug 2：product-service 缺分页插件，列表 total 恒为 0

`server` 有 `MybatisPlusConfig`（分页插件），product-service 没有 →
`selectPage(...).getTotal()` 恒返回 0，后台分页总数始终显示 0。

**修复**：product-service 新增 `MybatisPlusConfig`（MySQL 方言 + 单页上限 500）。

### Bug 3：SQL `LPAD` 截断导致唯一键冲突

`LPAD(o.id, 6, '0')` 对 9 位订单 id（如 `999100009`）会**截断为 6 位**（`999100`），
10 条订单生成同一编号 → `Duplicate entry` 报错。

**修复**：改用 `SUBSTRING(o.order_no, 6)` 派生编号，规避该陷阱。

## 一、核心结论：不是"没接"，而是 3 类缺陷

`store` 的 `add / update / remove / patch` **已内置远端分发**（命中 `REMOTE_RESOURCES` 即走 CRUD 接口）。
真正的缺陷是：

### 缺陷 1：写操作"乐观 UI + 静默失败"

原实现先插入 `id: Date.now()` 的假数据并立即返回，接口失败**仅弹 toast**，
页面已经渲染了这条不存在的数据 → 用户误以为成功。

**修复**：`add / update / remove / patch` 全部改为 **async + 先写库、成功后才更新本地镜像、失败抛出**。
`AdminListPage` 的 `submitModal` / `handleAction` / `confirmImport` 统一 `await` + `catch` 提示。

### 缺陷 2：subjects 字段名/值双重大小写不匹配

| 项 | 后端 | 前端 |
|----|------|------|
| 字段名 | `subjectType` | `type` |
| 值 | `STORE`（大写）| `'store'`（小写）|

**读**：`queryRemote` 已归一化 → 修复了 5 个主体页面列表恒为空。
**写**：新增 `normalizeWritePayload`，提交前把 `type` 转成 `subjectType`（大写）。
**顺带发现**：`loadRemote`（下拉数据源）**没有归一化** → 页面内嵌下拉也全空，
抽出公共 `normalizeRemoteRow` 同时用于 `queryRemote` 与 `loadRemote`。

### 缺陷 3：业务动作是纯本地记账

| 动作 | 原实现 | 修复 |
|------|--------|------|
| `reviewApplication` | 只改本地数组 | 调 `reviewRoleApplication` + 重载 |
| `reviewWithdraw` | 本地扣余额 / 减资金池 | 调 `POST /finance/withdrawals/{id}/review` |
| `executeVerify` | 本地拼核销记录 | 调 `executeVerifyApi` + 重载 |
| `refundOrder` | 本地改状态 + 拼退款单 | 调 `refundOrderApi` + 重载 |
| `reviewComment` | 已接接口但静默失败 | 改 async + 失败抛出 |
| `freezeAccount` / `unfreezeAccount` | 直接改本地余额 | 调对应接口 + 重载 |

# 运营后台：代提现校验 + 绑定双向一致性修复（阶段 4）

> 日期：2026-09-23
> 需求：① 代提现加 userId 校验；② localStorage 旧数据先保留。

## 一、加校验时又发现 2 个真实 Bug

### Bug 1：`user.userId` 字段不存在，导致绑定功能完全失效

`app_user` 表**没有 `userId` 字段**（接口返回 `undefined`），主键就是 `id`。
而代码里两处依赖了它：

| 位置 | 原写法 | 后果 |
|------|--------|------|
| `bindUserRole` | `subject.boundUserId !== user.userId` | 右值为 `undefined` → 判断**恒为 true** → 误报"该经营者已绑定用户" → **绑定功能不可用** |
| `unbindSubjectUser` | `find(u => u.userId === subject.boundUserId)` | 永远找不到 → **解绑静默失败** |

**修复**：统一改用 `id`。

### Bug 2：绑定关系只写单向，主体侧恒为 null

`SubjectBindingController.bindUserRole` 只更新了 `app_user.bound_subject_id`，
**没有反向更新 `biz_subject.bound_user_id`**：

```java
jdbcTemplate.update("update app_user set business_role = ?, bound_subject_id = ? where id = ? ...");
// ← 缺少 biz_subject 侧更新
```

**后果**：
- 用户列表看得到绑定，**主体列表看不到**（`bound_user_id` 恒为 `null`）
- 后台「代发起提现」依赖 `bound_user_id` 取发起人 → **恒判为"未绑定用户"**
- 「绑定/解绑用户」在主体侧同样失效

**修复**：`bindUserRole` 补写 `biz_subject.bound_user_id`，
`unbindUserRole` 同步清空，**保持双向一致**。

> 这也是本轮「加校验」时被顺带发现的 —— 若非加校验，这个不一致会一直潜伏。

## 二、代提现校验（本次需求）

### 原实现的问题

```js
const userId = acc.boundUserId ?? acc.userId ?? 1;   // ← 兜底成 1
```

- `subject_account` 表**不含用户字段**（已核对表结构），`acc.boundUserId` 恒为 `undefined`
- 实际每次都兜底成 **1 号用户** → 提现记录记到错误用户名下，构成**数据污染**

### 现在的校验

1. 从 `biz_subject.bound_user_id` 取该主体的绑定用户（绑定关系真实所在）
2. 未绑定 → 拒绝并提示「请先在主体管理中绑定用户」
3. 用户不存在或已删除 → 拒绝并提示
4. 通过后才调用后端接口
