## 一、P0：支付回调无鉴权（严重，已实证可利用）

### 1.1 漏洞详情

| 项 | 内容 |
|----|------|
| 位置 | `POST /api/v1/app/payments/callback`（`AppOrderController`） |
| 成因 | 接口无任何鉴权，仅凭 `orderNo` + `transactionId` 两个参数即调用 `PaymentService.handleCallback` 将订单置为已支付 |
| 前置 | `SecurityConfig` 中 `/api/v1/app/**` 为 `permitAll`，且该路径**未**纳入 `WebConfig` 的 `MiniAppAuthInterceptor` 保护清单 |

### 1.2 实证过程（修复前）

对真实订单 `WX202609220103260238`（状态 `CREATED/UNPAID`）发起匿名请求：

```
POST /api/v1/app/payments/callback?orderNo=WX202609220103260238&transactionId=FAKE-ATTACK
（无 Authorization 头、无签名）
```

结果：`HTTP 200`，`code=0`，订单变为 `PAID/PAID`，**并返回有效取餐码 `0011`**。

**影响**：攻击者可枚举订单号，把任意订单刷成已支付并取得取餐码，等价于**免费取餐**；
若配合核销，还会触发 `LedgerService` 五方分账，造成资金错账。

> 验证后已将该订单还原为 `CREATED/UNPAID`（`pickup_code`、`pay_time` 置空）。

### 1.3 修复方案：HMAC-SHA256 签名 + 时间戳窗口

新增 `wuling-common` 的 `com.wuling.common.security.PaymentCallbackSigner`：

- 签名串：`orderNo + "\n" + transactionId + "\n" + timestamp`（用 `\n` 分隔，避免字段拼接歧义）
- 算法：HMAC-SHA256，输出小写十六进制
- 比较：`MessageDigest.isEqual` **常量时间比较**，防时序侧信道
- 防重放：时间戳窗口默认 5 分钟（`app.pay.callback-tolerance-ms`）
- 弱密钥防护：密钥不足 32 字节直接拒绝构造

调用方（支付通道 / 网关）需携带 `orderNo`、`transactionId`、`timestamp`、`sign` 四个参数。

### 1.4 修复后验证

| 攻击方式 | 结果 |
|---------|------|
| 完全不带签名参数 | `code=403 回调签名校验失败` |
| 带伪造签名 `sign=deadbeef` | `code=403 回调签名校验失败` |
| 攻击者用自己密钥签名 | `code=403 回调签名校验失败` |
| 篡改订单号（复用他人合法签名） | 拒绝 |
| 超出 5 分钟窗口的旧签名 | 拒绝 |
| **合法签名（服务端密钥）** | `code=0`，订单正确置为 `PAID` 并生成取餐码 |

攻击后订单仍为 `CREATED/UNPAID`，取餐码为空。

### 1.5 顺带修复：缺参返回 500

修复过程中发现：缺少必填参数时抛 `MissingServletRequestParameterException`，
被 `GlobalExceptionHandler` 兜成 `500 服务器内部错误`。
已改为 `@RequestParam(required = false)` + 显式判空，缺参统一按验签失败处理（403），不泄露内部细节。

### 1.6 前端调整

`user-h5/utils/api.js` 原导出 `paymentCallback()` 供联调调用。该接口现为
**服务端到服务端**接口（小程序无法也不应持有签名密钥），已移除该方法的调用能力并补充说明。
经核查，该方法此前**无任何页面实际调用**，移除不影响现有功能。

## 二、P1：JWT 密钥硬编码（已修复）

### 2.1 问题

`application.yml` 原为：

```yaml
jwt:
  secret: ${JWT_SECRET:N1uU6M8tUVZhUGLntH8DFKq4a3WrzrkyIADnGlEmr5c=}
```

该默认值写在仓库里，**等同于公开密钥**——任何人可离线签发合法 token，
冒充管理端（`type=access`）或小程序用户（`type=mini`）。

> 补充说明：该默认值本身解码后为 32 字节，满足 HS256 长度要求，
> 因此**不是**「弱长度」问题，而是「密钥已公开」问题。

### 2.2 修复

1. `application.yml` 去掉默认值：`secret: ${JWT_SECRET:}`
2. 新增 `JwtSecretValidator`，在 `JwtTokenProvider` / `MiniAppTokenProvider`
   构造时执行**启动期强校验**（fail-fast）：
   - 非空
   - 合法 Base64
   - 解码后 ≥ 32 字节（HS256 要求）
3. 错误信息给出生成建议：`openssl rand -base64 32`
4. `application-dev.yml` 提供**本地开发专用**示例密钥（生产 profile 无任何默认值）

### 2.3 验证

| 场景 | 结果 |
|------|------|
| 不注入 `JWT_SECRET` 启动 | **拒绝启动**，日志明确提示所需环境变量与生成方式 |
| 用仓库旧默认密钥伪造管理端 token | `HTTP 401 {"code":8888,"message":"无效的令牌"}` |
| 正常登录 | `code=0`，受保护接口正常返回 |
| 空值 / 非 Base64 / 16 字节短密钥 | 均在启动期拒绝 |

# 第二轮：P2 / P3 安全加固

> 日期：2026-09-22
> 范围：登录限流、审计日志（P2）、密钥启动校验与生产配置（P3）

## 七、P2：登录接口限流（防口令爆破）

### 7.1 问题

`/auth/login` 无任何失败次数限制，攻击者可无限次提交口令。

### 7.2 修复：双维度失败锁定

新增 `wuling-common` 的 `com.wuling.common.security.LoginAttemptGuard`：

- **策略与存储解耦**：`Store` 接口注入，生产用 Redis（多实例共享计数），测试用内存实现；
- **双维度计数**：「用户名 + 来源 IP」，任一维度达阈值即锁定；
- 策略：连续失败 **5 次** → 锁定 **15 分钟**；失败计数窗口 15 分钟；
- 登录成功立即清零该维度计数；
- **为什么加 IP 维度**：只按用户名锁定会让攻击者故意失败来锁死他人账号（DoS）。

`LoginGuardConfig` 提供 Redis 实现，落于 `RedisNamespace.SMS`（该命名空间定位即「验证码与限流计数」）。

### 7.3 验证

| 步骤 | 结果 |
|------|------|
| 连续 5 次错误口令 | `1001 用户名或密码错误` |
| 第 6 次 | `1003 登录失败次数过多，请 15 分钟后再试` |
| 锁定后使用**正确口令** | `1003` 仍被拒绝 |
| 清除锁定后正确口令 | `code=0` 正常登录 |

### 7.4 实施中发现的缺陷（已修复）

`RedisStore` 初版写入 key 时**漏了命名空间前缀**，导致：

- key 落到裸空间（`login:lock:user:admin`），与 SMS 的 `wuling:sms:*` 规范不一致；
- 破坏「按前缀隔离与清理」的约定，多服务环境下可能与其他模块同名 key 冲突。

已改为统一经 `RedisNamespace.SMS.key(...)` 补前缀，实测 key 形如
`wuling:sms:login:lock:user:operator`，与 SMS 模块一致。

## 八、P2：关键操作审计日志

### 8.1 问题

`audit_log` 表早已存在，但只有管理端一个手工写入口；
**资金与鉴权类操作**（支付回调、提现审核、登录失败）完全没有留痕，事后无法追溯。

### 8.2 修复：AuditLogService

新增 `server` 的 `com.wuling.common.audit.AuditLogService`，设计要点：

- **审计失败绝不影响主流程**：整体 try-catch，写失败只记 `warn`，不污染业务事务；
- **敏感值不落库**：口令、令牌一律不写；手机号等由调用方保证已脱敏；
- 提供 `record(...)` 与 `recordChange(...)`（带变更前后快照）两个入口；
- 超长值按列宽截断，避免单条超长导致整条记录失败。

### 8.3 埋点位置

| 位置 | 动作 | 记录内容 |
|------|------|---------|
| 支付回调 - 验签失败 | `PAY / CALLBACK_REJECT` | 订单号、失败原因 |
| 支付回调 - 验签通过 | `PAY / CALLBACK_OK` | 订单号、交易号、金额 |
| 登录失败 | `AUTH / LOGIN_FAIL` | 用户名、原因、IP |
| 登录失败达阈值 | `AUTH / LOGIN_FAIL_LOCKED` | 用户名、IP |
| 锁定期间尝试登录 | `AUTH / LOGIN_BLOCKED` | 剩余锁定秒数、IP |
| 提现审核 | `WITHDRAW / APPROVE` 或 `REJECT` | 提现单号、**状态变更前后**、原因 |
| 提现标记失败 | `WITHDRAW / MARK_FAILED` | 提现单号、状态变更前后、原因 |

### 8.4 验证（实测写入记录）

```
#1~#4 admin|AUTH|LOGIN_FAIL        reason=用户名或密码错误  ip=127.0.0.1
#5    admin|AUTH|LOGIN_FAIL_LOCKED reason=用户名或密码错误  ip=127.0.0.1
#6~#8 admin|AUTH|LOGIN_BLOCKED     reason=账号或来源已锁定，剩余 899 秒
      SYSTEM|PAY|CALLBACK_REJECT   target=WX-TEST-AUDIT reason=回调签名校验失败
```

### 8.5 配套索引（V13）

原表仅有 `idx_audit_log_create_time`，按 module/action/operator 过滤会全表扫描。
新增 `V13__audit_indexes.sql`（幂等）：
`idx_audit_log_module_action`、`idx_audit_log_operator`、`idx_audit_log_target`。

## 九、P3：密钥启动校验与生产配置

### 9.1 微信密钥启动校验

`WxAuthService` 原仅在**请求时**才报错「未配置 WX_APP_SECRET」——
意味着配置缺失的实例仍会对外提供服务，直到有人尝试登录才暴露。

现改为**启动期校验**，与 JWT 保持一致：

- `app.wx.require-secret`（默认 `true`）→ 缺失密钥直接拒绝启动；
- `application-dev.yml` 设 `false`，便于本地无密钥联调；
- `application-prod.yml.example` 显式 `true`。

**验证**：强制 `require-secret=true` 且不提供密钥 →

```
IllegalStateException: 未配置微信小程序密钥 app.wx.app-secret（环境变量 WX_APP_SECRET）。
小程序登录依赖该密钥换取 openid，缺失时无法登录，服务拒绝启动。
```

### 9.2 生产配置模板（补齐）

`application-prod.yml.example`（可提交；真实 `application-prod.yml` 仍被 `.gitignore` 排除）：

- 所有敏感项无默认值，缺失即 fail-fast；
- **关闭 MyBatis SQL 日志**：原 `StdOutImpl` 会把全部 SQL 与参数（含手机号）打印进日志，改为 `NoLoggingImpl`；
- 收紧 actuator：仅暴露 `health`，`show-details: never`；
- 补齐 Hikari / Lettuce 连接池参数外置。
