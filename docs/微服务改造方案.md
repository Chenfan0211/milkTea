### 2.2 服务划分清单

| 服务 | 来源包 | 核心职责 | 独立库 | 拆分难度 |
|------|--------|---------|--------|---------|
| `gateway` | 新增 | 统一入口、路由、JWT 前置校验、限流 | 无 | 低 |
| `auth-service` | `auth` | 管理端登录、角色权限、Token 签发/校验 | `wuling_auth` | 低 |
| `user-service` | `user` + `subject` | 小程序用户、微信登录、短信、主体/门店/绑定 | `wuling_user` | 中 |
| `product-service` | `product` + `system` | 商品、分类、规格、上架、字典 | `wuling_product` | 低 |
| `trade-service` | `trade` | 订单、支付、核销、退款 | `wuling_trade` | 高 |
| `marketing-service` | `marketing` | 优惠券、积分、礼品卡、储值、评论 | `wuling_marketing` | 中 |
| `finance-service` | `finance` | 分账、台账、结算、提现 | `wuling_finance` | **最高** |
| `file-service` | 新增 | 上传、校验、病毒扫描、对象存储 | `wuling_file` | 中 |

**拆分铁律**：

1. **`finance-service` 必须独立库**——它是资金账本，不能被其他域的事务牵连。
2. **`trade` ↔ `finance` 不跨服务强事务**——核销后通过 MQ 事件触发分账，用「本地消息表 + 对账」保证最终一致。
3. **公共能力下沉 `wuling-common`**——`Result`、异常、工具、MQ 基类，禁止业务代码复制。

### 2.3 技术选型（贴合现有栈，不引入过重组件）

| 能力 | 选型 | 理由 |
|------|------|------|
| 网关 | Spring Cloud Gateway | 与 Spring Boot 3 同源，无额外技术栈 |
| 注册 / 配置 | Nacos | 国产、成熟、中文资料全 |
| 服务调用 | OpenFeign | 声明式，改造量小 |
| 熔断限流 | Sentinel | 网关 + 服务双层防护 |
| 链路追踪 | Micrometer Tracing（观察期）→ SkyWalking | 排查并发问题必需 |
| 分布式锁 | Redisson | 直接复用现有 Redis |
| 分布式事务 | **不用强事务**：本地消息表 + MQ + 幂等 + 对账 | 资金场景最终一致更稳 |

### 2.4 实施路线（5 期，每期可独立上线）

#### 第 0 期：安全加固（不拆服务，1 周）
> **强烈建议优先做这一期**，理由见第五章「决策建议」。

- 抽取 `SqlGuard`，给所有动态 SQL 加**代码级白名单强制校验**
- 补 `split_snapshot(order_id)` 唯一索引（详见 4.3）
- 资金/库存操作改**原子 SQL + 行锁**
- 建立并发集成测试基线

#### 第 1 期：模块化改造（1–2 周，零业务风险）
- `server/` 改为 Maven 多模块：`wuling-common` + 各 `*-service`
- **代码不动，只挪包 + 依赖隔离**（此时仍可单体启动）
- 引入 gateway + Nacos，让单体挂在网关后（绞杀者模式）

#### 第 2 期：拆独立服务（2–3 周）
- 先拆最独立的：`auth-service`、`file-service`（新增）
- 数据库按域分库，Flyway 按库拆 migration

#### 第 3 期：拆业务服务（3–4 周）
- 拆 `product` / `marketing` / `user`
- 引入 Sentinel 限流、SkyWalking 链路追踪

#### 第 4 期：拆核心交易（4 周+）
- 拆 `trade` / `finance`（最难，涉及资金一致性）
- 上 MQ 事件驱动 + 每日对账任务

## 三、SQL 注入防护方案

### 3.1 现状实测结论

**已验证：当前代码没有可利用的 SQL 注入点。** 但存在结构性隐患。

#### ✅ 已做到的部分

| 位置 | 做法 | 评价 |
|------|------|------|
| 绝大多数 Mapper | MyBatis-Plus `LambdaQueryWrapper`，全参数化 | ✅ 安全 |
| 所有 `@Select` 注解 | 全部使用 `#{}` 预编译占位符 | ✅ 安全 |
| 所有 `last(...)` 调用 | 全部是常量（`for update` / `limit 1`），无用户输入拼接 | ✅ 安全 |
| `CrudService` 表名字段名 | 来自 `CrudRegistry` 静态白名单 | ✅ 安全 |
| `AdminAuthQueryController` | 表名/排序是硬编码字面量，`where` 用 `?` 占位 | ✅ 安全 |

#### 🟡 结构性隐患（三点）

**隐患 1：`CrudService` 的动态拼接集中在一处，缺兜底校验**

文件：`server/src/main/java/com/wuling/system/crud/CrudService.java`

```java
// page() 方法
where.append(" and ").append(column).append(" like ?");   // column 已比对 searchable 白名单
...
String sql = "select * from " + def.table() + where
        + " order by " + def.orderBy() + " limit ? offset ?";   // table/orderBy 来自静态注册表
```

`column` 经 `camelToSnake()` 转换后**只与 `def.searchable()` 比对**，逻辑正确；
`def.table()` / `def.orderBy()` 来自 `CrudRegistry` 静态常量，当前安全。

**风险**：一旦有人给 `CrudRegistry` 增加「从数据库或配置读取的 `orderBy`」，拼接口立刻失守。缺少**独立的标识符校验层**兜底。

**隐患 2：`AdminAuthQueryController.pageOf()` 方法签名允许任意字符串进 SQL**

文件：`server/src/main/java/com/wuling/auth/controller/AdminAuthQueryController.java`

```java
private PageResult<Map<String, Object>> pageOf(String table, String where, List<Object> args,
                                              String orderBy, long current, long size) {
    Long total = jdbcTemplate.queryForObject("select count(*) from " + table + where, ...);
```

当前所有调用点都传字面量常量，**无实际注入**。但方法签名「任意 String 都能进」，属于**结构性隐患**——任何后续调用若传入变量即失守。

**隐患 3：无统一防护层，新增代码无强制约束**

项目约定「表名/列名必须来自白名单」只写在注释里，靠人工保证。新增代码没有编译期或测试期约束。

### 3.2 修复方案：SqlGuard 白名单强制校验层

**目标**：把「靠人工保证」改为「代码级强制」。任何 SQL 标识符（表名、列名、排序）拼接前必须过 `SqlGuard`。

```java
package com.wuling.common.sql;

import java.util.Set;
import java.util.regex.Pattern;

/**
 * SQL 标识符安全网关。
 * 铁律：任何拼进 SQL 的表名/列名/排序字段，必须先过这里。
 */
public final class SqlGuard {

    /** 合法标识符：小写字母开头，仅含小写字母、数字、下划线，最长 64 */
    private static final Pattern IDENT = Pattern.compile("^[a-z][a-z0-9_]{0,63}$");

    /** 排序方向白名单 */
    private static final Set<String> DIRECTIONS = Set.of("asc", "desc");

    private SqlGuard() {
    }

    /** 校验单个标识符（表名、列名） */
    public static String ident(String name) {
        if (name == null || !IDENT.matcher(name).matches()) {
            throw new IllegalArgumentException("非法 SQL 标识符: " + name);
        }
        return name;
    }

    /** 校验并组装 order by 子句，格式："col1 asc, col2 desc" */
    public static String orderBy(String clause) {
        if (clause == null || clause.isBlank()) {
            throw new IllegalArgumentException("排序子句不能为空");
        }
        StringBuilder sb = new StringBuilder();
        for (String part : clause.split(",")) {
            String[] tokens = part.trim().split("\\s+");
            if (tokens.length != 2 || !DIRECTIONS.contains(tokens[1].toLowerCase())) {
                throw new IllegalArgumentException("非法排序子句: " + clause);
            }
            sb.append(ident(tokens[0].toLowerCase()))
              .append(' ').append(tokens[1].toLowerCase()).append(", ");
        }
        return sb.substring(0, sb.length() - 2);
    }
}
```

**改造点**：

| 文件 | 改造 |
|------|------|
| `CrudService` | `def.table()` → `SqlGuard.ident(def.table())`；`def.orderBy()` → `SqlGuard.orderBy(def.orderBy())` |
| `AdminAuthQueryController` | `pageOf()` 内 `table` / `orderBy` 过 `SqlGuard`；长期建议删掉该通用方法，改为明确方法 |
| `CrudRegistry` | 增加**启动期自检**：注册资源时校验所有 table/writable/searchable/orderBy 合法 |

**长期措施**：

1. **禁用 `JdbcTemplate` 拼接**——引入 ArchUnit 测试，扫描到 `jdbcTemplate.query*(非字面量)` 即失败。
2. **MyBatis-Plus 禁用 `apply()` / `last()` 传变量**——ArchUnit 检测 `last(` 参数非 final 常量。
3. **所有查询优先 `LambdaQueryWrapper`**，禁止 `QueryWrapper` 手写列名字符串。

## 四、并发安全方案（**当前最严重隐患**）

### 4.1 问题总览

| # | 位置 | 问题模式 | 风险等级 | 后果 |
|---|------|---------|---------|------|
| 1 | `LedgerService.ensureAccount()` | 查→无则插，**无唯一约束兜底**（实际库有唯一键，但异常未捕获重试） | 🟡 中 | 并发首次开户时报异常 |
| 2 | `LedgerService.executeSplit()` | 查快照→无则插，**`split_snapshot(order_id)` 无唯一索引** | 🔴 高 | **重复分账，资金翻倍** |
| 3 | `WithdrawalService.apply()` | 读余额→校验→扣减→`updateById`，**无行锁无 CAS** | 🔴 高 | **并发超额提现** |
| 4 | `CouponService.receive()` | `stock - 1` 读改写 | 🔴 高 | **优惠券超发** |
| 5 | `PointsService.exchange()` | `stock - 1` + 扣币读改写 | 🔴 高 | **积分商品超兑** |
| 6 | `StoredValueService.recharge()` | `balance + amount` 读改写 | 🔴 高 | **充值金额丢失更新** |
| 7 | `PointsService.change()` | `points + amount` 读改写 | 🔴 高 | **积分余额错乱** |
| 8 | `OrderService.nextOrderNo()` | 时间戳 + 随机数，无唯一键兜底（库中 `order_no` 已有唯一键 ✅） | 🟢 低 | 冲突时插入报错 |
| 9 | `LedgerService` / `WithdrawalService` 用 `@Version` 实体 | 乐观锁生效，但**冲突异常未捕获重试** | 🟡 中 | 偶发失败而非自动串行化 |

### 4.2 关键代码位置（实测行号）

**问题 2：重复分账** — `LedgerService.executeSplit()`

```java
SplitSnapshot exists = splitSnapshotMapper.selectOne(...);   // 先查
if (exists != null) { return exists; }
// ... 中间有大量计算，并发窗口很大 ...
splitSnapshotMapper.insert(snapshot);                         // 再插，无唯一约束兜底
```

数据库现状：`split_snapshot` 只有 `UNIQUE KEY uk_split_snapshot_no (snapshot_no)` 和
普通索引 `KEY idx_split_snapshot_order (order_id)`。**`order_id` 不是唯一索引**——两笔并发核销同一订单，会生成两条快照。

**问题 3：超额提现** — `WithdrawalService.apply()` 第 75–77 行

```java
account.setAvailableBalance(available - amount);      // 读出来的 available 可能已过期
account.setFrozenBalance(... + amount);
subjectAccountMapper.updateById(account);             // version 冲突时抛异常，但无重试
```

### 4.3 修复方案（四层防御）

#### 第 1 层：数据库唯一约束（兜底，最可靠）

新增 Flyway migration `V11__concurrency_safety.sql`：

```sql
-- 修复：同一订单只能有一份分账快照（防重复分账）
ALTER TABLE split_snapshot
    DROP INDEX idx_split_snapshot_order,
    ADD UNIQUE KEY uk_split_snapshot_order (order_id);

-- 修复：主体账户按主体唯一（已存在，此处确认）
-- UNIQUE KEY uk_subject_account_subject (subject_id) 已存在于 V1
```

> 注意：加唯一索引前需先清理历史重复数据，否则 migration 失败。

#### 第 2 层：原子 SQL（消除读-改-写）

**库存类**（优惠券、积分商品）：

```java
// CouponMapper 新增
@Update("update coupon set stock = stock - 1 where id = #{id} and stock > 0 and deleted = 0")
int deductStock(@Param("id") Long id);

// CouponService.receive() 改造
if (couponMapper.deductStock(couponId) == 0) {
    throw new BusinessException(ResultCode.BAD_REQUEST, "优惠券已领完");
}
```

**余额类**（储值、积分、资金账户）：

```java
// 冻结：原子扣可用 + 原子加冻结，条件保证不超提
@Update("update subject_account set available_balance = available_balance - #{amount}, " +
        "frozen_balance = frozen_balance + #{amount}, version = version + 1 " +
        "where subject_id = #{subjectId} and available_balance >= #{amount} and deleted = 0")
int freeze(@Param("subjectId") Long subjectId, @Param("amount") long amount);
```

**核心优势**：`where ... and stock > 0` / `where ... and available_balance >= #{amount}`
把「校验 + 扣减」合并为**单条原子语句**，由 MySQL 行锁保证串行，彻底消除竞态。

#### 第 3 层：行锁（适用于必须先读后算的场景）

已有正确范例——`OrderService.lockForUpdate()`：

```java
public Order lockForUpdate(String orderNo) {
    return orderMapper.selectOne(new LambdaQueryWrapper<Order>()
            .eq(Order::getOrderNo, orderNo).last("for update"));   // ✅ 正确
}
```

**推广到**：`WithdrawalService.apply()` 先锁账户行，`LedgerService.executeSplit()` 先锁订单行。

#### 第 4 层：乐观锁冲突重试 + 幂等

```java
// 统一重试模板（冲突时重试 3 次，指数退避）
@Retryable(retryFor = OptimisticLockingFailureException.class, maxAttempts = 3,
           backoff = @Backoff(delay = 50, multiplier = 2))
public void settlePaid(Withdrawal w, SubjectAccount account) { ... }
```

配合已有基础设施：
- `MqIdempotent`（基于 Redis SETNX）已实现消息幂等消费 ✅
- 新增 `idempotent` 表：`biz_type + biz_no` 唯一索引，防重复提交

### 4.4 分布式并发治理（拆分后）

| 场景 | 方案 |
|------|------|
| 抢券 / 秒杀 | Redis 预扣 + Lua 原子脚本 + MQ 异步落库 |
| 订单幂等 | 客户端 token + 服务端幂等表（唯一索引） |
| 资金扣减 | 原子 SQL + 行锁 + 每日对账 |
| 跨服务一致性 | 本地消息表 / MQ publisher confirm |
| 缓存一致性 | 先更新 DB 再删缓存 + 延迟双删 |
| 全局限流 | 网关 Sentinel + Redis 令牌桶 |

## 五、文件病毒注入防护方案

### 5.1 现状：无攻击面，但需前瞻建设

**实测结论**：`server/` 中**没有任何 `MultipartFile` 或文件上传接口**。
`MiniAppAuthService.updateAvatar()` 只是把前端上传后拿到的 URL 字符串存库：

```java
public Map<String, Object> updateAvatar(Long userId, String avatar) {
    if (!StringUtils.hasText(avatar)) { throw new BusinessException(...); }
    AppUser user = requireUser(userId);
    user.setAvatar(avatar);        // 仅存 URL 字符串，不处理文件
    appUserMapper.updateById(user);
    ...
}
```

**含义**：
- ✅ 当前**不存在**文件病毒注入攻击面；
- ⚠️ 但头像 `avatar` 字段**未做 URL 白名单校验**——前端可传任意 URL（含恶意域名），存在**SSRF / 内容注入**的次要风险；
- 🔴 一旦新增商品图、评论图、资质证照上传，必须**一次性把防护做对**，否则直接引入病毒面。

### 5.2 立即修复：avatar URL 白名单

```java
// 只允许本站对象存储域名 + 相对路径
private static final Pattern AVATAR_URL =
        Pattern.compile("^(https://cdn\\.wulingshiguang\\.top/|/assets/)[\\w./-]+$");

if (!AVATAR_URL.matcher(avatar).matches()) {
    throw new BusinessException(ResultCode.BAD_REQUEST, "头像地址不合法");
}
```

### 5.3 新增 file-service 时的完整防护流程

```
上传请求
   │
   ▼
① 网关层：限流 + 请求体大小限制（图片 ≤5MB，文档 ≤10MB）
   │
   ▼
② 扩展名白名单：jpg/jpeg/png/webp/gif（**不信扩展名**）
   │
   ▼
③ Magic Bytes 校验：读文件头真实类型，与扩展名交叉验证
   │   jpg=FFD8FF  png=89504E47  gif=47494638  webp=52494646..57454250
   │
   ▼
④ 图片二次编码：ImageIO 重绘（剥离嵌入脚本、EXIF、Polyglot 载荷）
   │
   ▼
⑤ 重命名：UUID + 时间戳（防路径穿越、防覆盖）
   │
   ▼
⑥ 写入对象存储 OSS/COS（**非 Web 根目录，无执行权限**）
   │
   ▼
⑦ 异步 ClamAV 病毒扫描（状态：PENDING_SCAN）
   │
   ├─ 通过 → 标记 USABLE，返回访问 URL
   └─ 不通过 → 移入隔离区 + 告警 + 记录用户/IP
```

**核心原则：上传即不可信。** 扫描通过前，文件一律不可访问（返回 403）。

**技术选型建议**：

| 能力 | 选型 |
|------|------|
| 对象存储 | 腾讯云 COS（与服务器同在腾讯云，内网免流量） |
| 病毒扫描 | ClamAV（Docker 部署，`clamd` 常驻 + 异步调用） |
| Magic Bytes | Apache Tika 或自研 `FileTypeDetector` |
| 图片重编码 | JDK `ImageIO`（`BufferedImage` → 重新 `write`） |

## 七、风险与决策建议

### 7.1 关键前提（重要）

⚠️ **项目当前处于演示阶段**：

- 小程序接口全放行（`SecurityConfig` 中 `/api/v1/app/**` 为 `permitAll`）
- 支付是 Mock（`MockPaymentGateway`）
- 数据库口令为弱口令（见密码管理）
- JWT secret 硬编码在 `application.yml`

微服务化会把 **1 个进程 → 8 个进程 + 注册中心 + 网关**，运维复杂度显著上升。

### 7.2 建议的执行顺序

```
第一步（强烈建议）：第 0 期安全加固
   └─ 理由：并发问题是"定时炸弹"，与是否微服务无关，必须优先解决
            工作量小（约 1 周），可独立验证，风险低

第二步：第 1 期模块化 + 网关（零业务风险）
   └─ 理由：只挪包不改逻辑，为后续拆分铺路

第三步：第 2–3 期拆独立域与业务域
   └─ 理由：边界清晰，改造可控

第四步：第 4 期拆 trade / finance
   └─ 理由：涉及资金一致性，必须最后做，且需配套对账
```

**核心判断**：**先止血（SQL/并发），再拆服务。** 微服务不是目的，安全与一致性才是。

### 7.3 风险清单

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| 分库后跨库 JOIN 失效 | 部分查询需重写 | 拆库前梳理 JOIN，改为服务聚合 |
| 分布式事务复杂度 | 资金不一致 | 只做最终一致 + 每日对账兜底 |
| 运维复杂度上升 | 故障排查难 | 先上链路追踪再拆核心域 |
| 团队学习成本 | 交付变慢 | 分 5 期渐进，每期可回滚 |
| 历史数据重复 | 唯一索引加不上 | migration 前先跑清理脚本 |
