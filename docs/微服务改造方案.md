> **与规划的两处偏离**：
> 1. **subject 不拆服务**：其被 `finance/LedgerService` 在 `@Transactional` 内调用，
>    远程化会引入「事务内网络调用」的资金风险。只做端口解耦（第 12 期）。
> 2. **system 不拆**：`CrudController` 的 43 个资源跨所有域，网关无法按 path 参数路由。
> 3. **数据库仍共享**：生产为单库 `wuling`，各服务共用连接。
>    隔离方案见 `docs/数据库隔离方案.md`，尚未执行。

**拆分铁律**：

1. **`finance-service` 必须独立库**——它是资金账本，不能被其他域的事务牵连。
2. **`trade` ↔ `finance` 不跨服务强事务**——核销后通过 MQ 事件触发分账，用「本地消息表 + 对账」保证最终一致。
3. **公共能力下沉 `wuling-common`**——`Result`、异常、工具、MQ 基类，禁止业务代码复制。

| 能力 | 选型 | 理由 |
|------|------|------|
| 网关 | Spring Cloud Gateway | 与 Spring Boot 3 同源，无额外技术栈 |

### 2.4 实施路线（5 期，每期可独立上线）

#### 第 0 期：安全加固（不拆服务，1 周）

- `server/` 改为 Maven 多模块：`wuling-common` + 各 `*-service`

- 引入 gateway + Nacos，让单体挂在网关后（绞杀者模式）

#### 第 2 期：拆独立服务（2–3 周）

#### 第 3 期：拆业务服务（3–4 周）

#### 第 4 期：拆核心交易（4 周+）
- 拆 `trade` / `finance`（最难，涉及资金一致性）
- 上 MQ 事件驱动 + 每日对账任务

## 三、SQL 注入防护方案

### 3.1 现状实测结论

**已验证：当前代码没有可利用的 SQL 注入点。** 但存在结构性隐患。

#### ✅ 已做到的部分

| 位置 | 做法 | 评价 |
|------|------|------|
| 绝大多数 Mapper | MyBatis-Plus `LambdaQueryWrapper`，全参数化 | ✅ 安全 |
| 所有 `@Select` 注解 | 全部使用 `#{}` 预编译占位符 | ✅ 安全 |
| 所有 `last(...)` 调用 | 全部是常量（`for update` / `limit 1`），无用户输入拼接 | ✅ 安全 |
| `CrudService` 表名字段名 | 来自 `CrudRegistry` 静态白名单 | ✅ 安全 |
| `AdminAuthQueryController` | 表名/排序是硬编码字面量，`where` 用 `?` 占位 | ✅ 安全 |

#### 🟡 结构性隐患（三点）

**隐患 1：`CrudService` 的动态拼接集中在一处，缺兜底校验**

文件：`server/src/main/java/com/wuling/system/crud/CrudService.java`

```java
// page() 方法
where.append(" and ").append(column).append(" like ?");   // column 已比对 searchable 白名单
...
String sql = "select * from " + def.table() + where
        + " order by " + def.orderBy() + " limit ? offset ?";   // table/orderBy 来自静态注册表
```

`column` 经 `camelToSnake()` 转换后**只与 `def.searchable()` 比对**，逻辑正确；
`def.table()` / `def.orderBy()` 来自 `CrudRegistry` 静态常量，当前安全。

**风险**：一旦有人给 `CrudRegistry` 增加「从数据库或配置读取的 `orderBy`」，拼接口立刻失守。缺少**独立的标识符校验层**兜底。

**隐患 2：`AdminAuthQueryController.pageOf()` 方法签名允许任意字符串进 SQL**

文件：`server/src/main/java/com/wuling/auth/controller/AdminAuthQueryController.java`

```java
private PageResult<Map<String, Object>> pageOf(String table, String where, List<Object> args,
                                              String orderBy, long current, long size) {
    Long total = jdbcTemplate.queryForObject("select count(*) from " + table + where, ...);
```

当前所有调用点都传字面量常量，**无实际注入**。但方法签名「任意 String 都能进」，属于**结构性隐患**——任何后续调用若传入变量即失守。

**隐患 3：无统一防护层，新增代码无强制约束**

项目约定「表名/列名必须来自白名单」只写在注释里，靠人工保证。新增代码没有编译期或测试期约束。

### 3.2 修复方案：SqlGuard 白名单强制校验层

**目标**：把「靠人工保证」改为「代码级强制」。任何 SQL 标识符（表名、列名、排序）拼接前必须过 `SqlGuard`。

```java
package com.wuling.common.sql;

import java.util.Set;
import java.util.regex.Pattern;

/**
 * SQL 标识符安全网关。
 * 铁律：任何拼进 SQL 的表名/列名/排序字段，必须先过这里。
 */
public final class SqlGuard {

    /** 合法标识符：小写字母开头，仅含小写字母、数字、下划线，最长 64 */
    private static final Pattern IDENT = Pattern.compile("^[a-z][a-z0-9_]{0,63}$");

    /** 排序方向白名单 */
    private static final Set<String> DIRECTIONS = Set.of("asc", "desc");

    private SqlGuard() {
    }

    /** 校验单个标识符（表名、列名） */
    public static String ident(String name) {
        if (name == null || !IDENT.matcher(name).matches()) {
            throw new IllegalArgumentException("非法 SQL 标识符: " + name);
        }
        return name;
    }

    /** 校验并组装 order by 子句，格式："col1 asc, col2 desc" */
    public static String orderBy(String clause) {
        if (clause == null || clause.isBlank()) {
            throw new IllegalArgumentException("排序子句不能为空");
        }
        StringBuilder sb = new StringBuilder();
        for (String part : clause.split(",")) {
            String[] tokens = part.trim().split("\\s+");
            if (tokens.length != 2 || !DIRECTIONS.contains(tokens[1].toLowerCase())) {
                throw new IllegalArgumentException("非法排序子句: " + clause);
            }
            sb.append(ident(tokens[0].toLowerCase()))
              .append(' ').append(tokens[1].toLowerCase()).append(", ");
        }
        return sb.substring(0, sb.length() - 2);
    }
}
```

**改造点**：

| 文件 | 改造 |
|------|------|
| `CrudService` | `def.table()` → `SqlGuard.ident(def.table())`；`def.orderBy()` → `SqlGuard.orderBy(def.orderBy())` |
| `AdminAuthQueryController` | `pageOf()` 内 `table` / `orderBy` 过 `SqlGuard`；长期建议删掉该通用方法，改为明确方法 |
| `CrudRegistry` | 增加**启动期自检**：注册资源时校验所有 table/writable/searchable/orderBy 合法 |

**长期措施**：

1. **禁用 `JdbcTemplate` 拼接**——引入 ArchUnit 测试，扫描到 `jdbcTemplate.query*(非字面量)` 即失败。
2. **MyBatis-Plus 禁用 `apply()` / `last()` 传变量**——ArchUnit 检测 `last(` 参数非 final 常量。
3. **所有查询优先 `LambdaQueryWrapper`**，禁止 `QueryWrapper` 手写列名字符串。

## 四、并发安全方案（**当前最严重隐患**）

### 4.1 问题总览

| # | 位置 | 问题模式 | 风险等级 | 后果 |
|---|------|---------|---------|------|
| 1 | `LedgerService.ensureAccount()` | 查→无则插，**无唯一约束兜底**（实际库有唯一键，但异常未捕获重试） | 🟡 中 | 并发首次开户时报异常 |
| 2 | `LedgerService.executeSplit()` | 查快照→无则插，**`split_snapshot(order_id)` 无唯一索引** | 🔴 高 | **重复分账，资金翻倍** |
| 3 | `WithdrawalService.apply()` | 读余额→校验→扣减→`updateById`，**无行锁无 CAS** | 🔴 高 | **并发超额提现** |
| 4 | `CouponService.receive()` | `stock - 1` 读改写 | 🔴 高 | **优惠券超发** |
| 5 | `PointsService.exchange()` | `stock - 1` + 扣币读改写 | 🔴 高 | **积分商品超兑** |
| 6 | `StoredValueService.recharge()` | `balance + amount` 读改写 | 🔴 高 | **充值金额丢失更新** |
| 7 | `PointsService.change()` | `points + amount` 读改写 | 🔴 高 | **积分余额错乱** |
| 8 | `OrderService.nextOrderNo()` | 时间戳 + 随机数，无唯一键兜底（库中 `order_no` 已有唯一键 ✅） | 🟢 低 | 冲突时插入报错 |
| 9 | `LedgerService` / `WithdrawalService` 用 `@Version` 实体 | 乐观锁生效，但**冲突异常未捕获重试** | 🟡 中 | 偶发失败而非自动串行化 |

### 4.2 关键代码位置（实测行号）

**问题 2：重复分账** — `LedgerService.executeSplit()`

```java
SplitSnapshot exists = splitSnapshotMapper.selectOne(...);   // 先查
if (exists != null) { return exists; }
// ... 中间有大量计算，并发窗口很大 ...
splitSnapshotMapper.insert(snapshot);                         // 再插，无唯一约束兜底
```

数据库现状：`split_snapshot` 只有 `UNIQUE KEY uk_split_snapshot_no (snapshot_no)` 和
普通索引 `KEY idx_split_snapshot_order (order_id)`。**`order_id` 不是唯一索引**——两笔并发核销同一订单，会生成两条快照。

**问题 3：超额提现** — `WithdrawalService.apply()` 第 75–77 行

```java
account.setAvailableBalance(available - amount);      // 读出来的 available 可能已过期
account.setFrozenBalance(... + amount);
subjectAccountMapper.updateById(account);             // version 冲突时抛异常，但无重试
```

### 4.3 修复方案（四层防御）

#### 第 1 层：数据库唯一约束（兜底，最可靠）

新增 Flyway migration `V11__concurrency_safety.sql`：

```sql
-- 修复：同一订单只能有一份分账快照（防重复分账）
ALTER TABLE split_snapshot
    DROP INDEX idx_split_snapshot_order,
    ADD UNIQUE KEY uk_split_snapshot_order (order_id);

-- 修复：主体账户按主体唯一（已存在，此处确认）
-- UNIQUE KEY uk_subject_account_subject (subject_id) 已存在于 V1
```

> 注意：加唯一索引前需先清理历史重复数据，否则 migration 失败。

#### 第 2 层：原子 SQL（消除读-改-写）

**库存类**（优惠券、积分商品）：

```java
// CouponMapper 新增
@Update("update coupon set stock = stock - 1 where id = #{id} and stock > 0 and deleted = 0")
int deductStock(@Param("id") Long id);

// CouponService.receive() 改造
if (couponMapper.deductStock(couponId) == 0) {
    throw new BusinessException(ResultCode.BAD_REQUEST, "优惠券已领完");
}
```

**余额类**（储值、积分、资金账户）：

```java
// 冻结：原子扣可用 + 原子加冻结，条件保证不超提
@Update("update subject_account set available_balance = available_balance - #{amount}, " +
        "frozen_balance = frozen_balance + #{amount}, version = version + 1 " +
        "where subject_id = #{subjectId} and available_balance >= #{amount} and deleted = 0")
int freeze(@Param("subjectId") Long subjectId, @Param("amount") long amount);
```

**核心优势**：`where ... and stock > 0` / `where ... and available_balance >= #{amount}`

## 五、文件病毒注入防护方案

### 5.1 现状：无攻击面，但需前瞻建设

**实测结论**：`server/` 中**没有任何 `MultipartFile` 或文件上传接口**。
`MiniAppAuthService.updateAvatar()` 只是把前端上传后拿到的 URL 字符串存库：

```java
public Map<String, Object> updateAvatar(Long userId, String avatar) {
    if (!StringUtils.hasText(avatar)) { throw new BusinessException(...); }
    AppUser user = requireUser(userId);
    user.setAvatar(avatar);        // 仅存 URL 字符串，不处理文件
    appUserMapper.updateById(user);
    ...
}
```

**含义**：
- ✅ 当前**不存在**文件病毒注入攻击面；
- ⚠️ 但头像 `avatar` 字段**未做 URL 白名单校验**——前端可传任意 URL（含恶意域名），存在**SSRF / 内容注入**的次要风险；
- 🔴 一旦新增商品图、评论图、资质证照上传，必须**一次性把防护做对**，否则直接引入病毒面。

### 5.2 立即修复：avatar URL 白名单

```java
// 只允许本站对象存储域名 + 相对路径
private static final Pattern AVATAR_URL =
        Pattern.compile("^(https://cdn\\.wulingshiguang\\.top/|/assets/)[\\w./-]+$");

if (!AVATAR_URL.matcher(avatar).matches()) {
    throw new BusinessException(ResultCode.BAD_REQUEST, "头像地址不合法");
}
```

### 5.3 新增 file-service 时的完整防护流程

```
上传请求
   │
   ▼
① 网关层：限流 + 请求体大小限制（图片 ≤5MB，文档 ≤10MB）
   │
   ▼
② 扩展名白名单：jpg/jpeg/png/webp/gif（**不信扩展名**）
   │
   ▼
③ Magic Bytes 校验：读文件头真实类型，与扩展名交叉验证
   │   jpg=FFD8FF  png=89504E47  gif=47494638  webp=52494646..57454250
   │
   ▼
④ 图片二次编码：ImageIO 重绘（剥离嵌入脚本、EXIF、Polyglot 载荷）
   │
   ▼
⑤ 重命名：UUID + 时间戳（防路径穿越、防覆盖）
   │
   ▼
⑥ 写入对象存储 OSS/COS（**非 Web 根目录，无执行权限**）
   │
   ▼
⑦ 异步 ClamAV 病毒扫描（状态：PENDING_SCAN）
   │
   ├─ 通过 → 标记 USABLE，返回访问 URL
   └─ 不通过 → 移入隔离区 + 告警 + 记录用户/IP
```

**核心原则：上传即不可信。** 扫描通过前，文件一律不可访问（返回 403）。

**技术选型建议**：

| 能力 | 选型 |
|------|------|
| 对象存储 | 腾讯云 COS（与服务器同在腾讯云，内网免流量） |
| 病毒扫描 | ClamAV（Docker 部署，`clamd` 常驻 + 异步调用） |
| Magic Bytes | Apache Tika 或自研 `FileTypeDetector` |
| 图片重编码 | JDK `ImageIO`（`BufferedImage` → 重新 `write`） |

## 七、风险与决策建议

### 7.1 关键前提（重要）

⚠️ **项目当前处于演示阶段**：

- 小程序接口全放行（`SecurityConfig` 中 `/api/v1/app/**` 为 `permitAll`）
- 支付是 Mock（`MockPaymentGateway`）
- 数据库口令为弱口令（见密码管理）
- JWT secret 硬编码在 `application.yml`

微服务化会把 **1 个进程 → 8 个进程 + 注册中心 + 网关**，运维复杂度显著上升。

### 7.2 建议的执行顺序

```
第一步（强烈建议）：第 0 期安全加固
   └─ 理由：并发问题是"定时炸弹"，与是否微服务无关，必须优先解决
            工作量小（约 1 周），可独立验证，风险低

第二步：第 1 期模块化 + 网关（零业务风险）
   └─ 理由：只挪包不改逻辑，为后续拆分铺路

第三步：第 2–3 期拆独立域与业务域
   └─ 理由：边界清晰，改造可控

第四步：第 4 期拆 trade / finance
   └─ 理由：涉及资金一致性，必须最后做，且需配套对账
```

**核心判断**：**先止血（SQL/并发），再拆服务。** 微服务不是目的，安全与一致性才是。

### 7.3 风险清单

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| 分库后跨库 JOIN 失效 | 部分查询需重写 | 拆库前梳理 JOIN，改为服务聚合 |
| 分布式事务复杂度 | 资金不一致 | 只做最终一致 + 每日对账兜底 |
| 运维复杂度上升 | 故障排查难 | 先上链路追踪再拆核心域 |
| 团队学习成本 | 交付变慢 | 分 5 期渐进，每期可回滚 |
| 历史数据重复 | 唯一索引加不上 | migration 前先跑清理脚本 |

**已实现的安全校验**（`FileTypeValidator` + `UploadValidationService`）：

1. 大小限制（默认 5MB，`app.file.max-size-bytes`）；

#### 网关设计要点

1. **统一入口**：网关接管原 8080，单体后端退到 8090（生产只监听内网）。

2. **服务名寻址**：路由用 `lb://wuling-xxx`，不写死 IP，便于水平扩容。
3. **鉴权策略（fail-safe）**：采用「默认需鉴权 + 白名单放行」而非反向。

4. **剥离伪造身份头**：网关先移除外部传入的 `X-User-Id` / `X-Token-Type`，
   再写入自己解析的值，防止客户端伪造身份绕过下游校验。
5. **纵深防御**：网关只校验签名与有效期；业务归属仍由下游服务校验（网关非唯一防线）。

#### 版本踩坑（重要，供后续参考）

**问题**：Spring Cloud `2023.0.4` 的 `spring-cloud-gateway-server 4.1.6` 调用了

- 升级到 4.1.9 无效（同样需要 6.2），说明 4.1.x 系列后续版本都基于 6.2 编译。

**解决**：Spring Cloud 版本降到 **2023.0.3**（对应 gateway 4.1.5），
与 Spring Boot 3.3.5 + Framework 6.1.14 匹配，实测路由正常。

#### 10.7.3 关键修复：开发 / 生产环境隔离

**问题**：本地开发经 SSH 隧道连接**生产 Nacos**，导致：

```
wuling-server 注册表：
  172.16.0.16:8080   <- 生产服务器（隧道不可达）
  127.0.0.1:8090     <- 本地开发

网关按服务名轮询 -> 命中生产实例 -> 超时
实测：直连 3/3 成功，经网关 2/3 成功（约 1/3 超时）
```

**根因**：与「生产事故」同源 —— **开发与生产共用基础设施**。

| 时间 | 共用项 | 后果 |
|------|--------|------|
| 第 0 期 | MySQL（13306 隧道） | 误迁移生产库（V11/V12/V13） |
| 第 4 期 | Nacos（18848 隧道） | 服务发现互相污染，路由超时 |

**修复方案**：本地开发**不连生产 Nacos**，改为静态路由。

```yaml
# 各服务 application-dev.yml
spring:
  cloud:
    nacos:
      discovery:
        enabled: false        # 本地单实例，服务发现无意义

# gateway application-dev.yml：路由改静态 URI
spring:
  cloud:
    gateway:
      routes:
        - id: auth-route
          uri: http://127.0.0.1:8081
        - id: file-service
          uri: http://127.0.0.1:8082
        - id: legacy-server
          uri: http://127.0.0.1:8090
```

**为什么不禁用生产注册**：生产仍是多实例 + Nacos 服务发现（扩容需要），
只隔离开发侧。

**验证**：修复后经网关连续 10 次请求 **10/10 成功**（修复前约 1/3 超时）；
Nacos 注册表中不再出现本地实例。

#### 10.8.3 跨服务解耦：兑换核销改用 MQ

**问题**：`trade.VerifyService` 核销兑换码时需调用 `marketing.PointsService.verifyExchange`
（兑换单 `ExchangeOrder` 归属 marketing）。marketing 拆出后，直接依赖变成跨服务耦合。

**方案**（按你的要求，用 MQ 做跨服务处理）：

```
trade.VerifyService                marketing.ExchangeVerifyConsumer
       │                                        ▲
       │ 发布「兑换核销」事件                    │ 消费并更新兑换单状态
       └──────────► RabbitMQ ───────────────────┘
           wuling.marketing.exchange-verify
```

**新增 MQ 拓扑**（`MqConstants` + `RabbitConfig`）：

| 项 | 值 |
|----|----|
| 队列 | `wuling.marketing.exchange-verify.queue` |
| 路由键 | `wuling.marketing.exchange-verify` |
| 死信 | `...queue.dlq`（由 DLX 自动接管） |

**一致性模型：最终一致**

- trade 侧核销记录**先落库**（门店据此放行），不阻塞业务；
- marketing **异步**把兑换单置为 `VERIFIED`；
- 失败自动重试（`app.mq.max-retry`，默认 3 次），超限转死信；
- **幂等**由 `MqIdempotent`（Redis SETNX）基于 messageId 保证；
- 消费者额外捕获「已核销」业务异常并视为**成功**，
  避免已完成的消息被反复重试。

#### 10.8.5 ⚠️ 生产事故：MySQL 公钥检索失败（已修复）

**现象**：验证阶段发现生产接口全部返回 `500`。

**根因**：MySQL 8 的 `caching_sha2_password` 插件在**非 SSL 连接**下首次认证
需获取服务端公钥，要求 JDBC url 带 `allowPublicKeyRetrieval=true`。
我在**第三轮加固轮换口令**时用了 `ALTER USER`，该操作重设了认证插件，
而生产 url 缺少该参数 —— 加上 Hikari 连接池耗尽后新建连接即失败。

#### 10.10.3 实施中踩到的四个坑

**坑 1：`PaymentSignConfig` 下沉后所有服务被强制要求密钥**

把 `PaymentSignConfig` 从 server 移到 `wuling-common` 后，
**每个服务**启动都要求 `PAY_CALLBACK_SECRET`，导致 marketing-service 启动失败。

**修正**：改为 `@ConditionalOnProperty(name = "app.pay.enabled", havingValue = "true")`，
只有声明支付能力的服务（trade-service）才加载。fail-fast 语义保留 ——
一旦声明 `enabled=true` 却未注入密钥，仍然拒绝启动。

**坑 2：`/internal/**` 被 Spring Security 拦截**

server 的 `SecurityConfig` 中 `anyRequest().authenticated()` 把 `/internal/**` 也拦了，
导致 trade 调用返回 401。

**修正**：各服务显式放行 `/internal/**` 并注明安全前提（仅回环 + 不经网关）。

**坑 3：trade-service 缺少 JWT 过滤器，管理端接口全部 401**

server 有 `JwtAuthenticationFilter`（来自 auth 包）填充 SecurityContext，
trade-service 没有，于是 `anyRequest().authenticated()` 拒绝了所有管理端请求。

**修正**：网关已做 JWT 前置校验（`GatewayAuthFilter`），
下游服务**不应重复校验**。trade / marketing 显式放行 `/api/v1/admin/**`，
前提是「仅监听 127.0.0.1 且必须经网关访问」。

**坑 4：trade-service 缺少拦截器注册**

与第 5 期的 marketing 同样问题：Spring Security 放行了 `/api/v1/app/**`，
但没有 `MiniAppAuthInterceptor` 精确拦截需登录的接口。

**修正**：新增 `TradeSecurityConfig`，与 server / marketing 同一模型。

### 10.11 第 8 期：资金对账任务（已完成）

#### 10.11.1 为什么必须补对账

第 6 期把分账/冲正改为 MQ 事件后，资金链路变成**最终一致**：

```
trade 核销 → 落库核销记录 → 发 MQ 分账事件 → finance 消费 executeSplit
```

失败路径（**当时无任何机制能发现**）：

| 失败点 | 症状 |
|--------|------|
| 消息发送失败（Broker 不可用） | 订单已核销，但无分账快照 |
| 消费重试 3 次后进死信 | 同上 |
| 消费者宕机期间积压 | 暂时无快照（延迟恢复） |
| 退款冲正消息丢失 | 订单已退款，但台账仍 PENDING（**存在重复结算风险**） |

**这是当时架构中唯一没有兜底的资金环节** —— 静默不一致比显式报错更危险。

#### 10.11.2 设计原则：只发现，不自动改账

`ReconcileService` 检查三类问题，**只写入 `reconcile_issue` 并告警，绝不自动修复**。

**理由**：资金修复涉及五方账目（平台/门店/渠道/投资人/供应商），
自动改账的风险（改错、重复补记）高于人工介入成本。
发现 → 告警 → 人工确认 → 必要时手工补偿，是更稳妥的路径。

#### 10.11.3 三类检查

| 检查项 | 判定 | 异常类型 |
|--------|------|---------|
| 已核销但无分账快照 | `orders.status in (VERIFIED,COMPLETED)` 且 `split_snapshot` 无记录 | `MISSING_SPLIT` |
| 已退款但未冲正 | `orders.status = REFUNDED` 且存在 `settlement_record.status = PENDING` | `MISSING_REVERSE` |
| 分账金额不一致 | 快照五方之和 ≠ 订单实付金额 | `SPLIT_AMOUNT_MISMATCH` |

> 第三项虽在 `executeSplit` 写入时已有 `total_check` 自检，
> 但独立复核能发现「写入后数据被改动」等异常，属于纵深防御。

#### 10.11.4 幂等与调度

**幂等**：同一 `(issueType, orderNo)` 在 `OPEN` 状态下不重复记录 ——
否则每小时对账会产生大量重复告警，淹没真实信号。

**调度**：`ReconcileJob` 每小时第 10 分钟执行（避开整点的结算任务）。

- 小时级而非天级：资金不一致发现得越早，人工介入成本越低
  （尤其「未分账」场景下各方还没动钱，处理窗口更大）；
- 可通过 `app.reconcile.enabled=false` 临时关闭；
- cron 可用 `app.reconcile.cron` 覆盖。

**配套索引** `V14__reconcile_indexes.sql`：

| 索引 | 用途 |
|------|------|
| `idx_reconcile_type_order_status` | `recordOnce` 去重查询 |
| `idx_reconcile_status` | `openIssues` 列表 |

#### 10.12.2 告警通道设计

**背景**：告警的"发送方式"会变（日志 → 邮件 → 机器人），
但"何时告警"是业务逻辑。因此抽 `AlertChannel` 接口，当前只有一个实现：

```java
public interface AlertChannel {
    enum Level { CRITICAL, WARNING, INFO }
    void send(Level level, String title, String detail, String bizKey);
    String channelName();
}
```

**当前实现 `LogAlertChannel`** 做三件事，弥补"纯日志容易被忽视"的短板：

1. 写独立告警文件 `/opt/wuling/logs/alerts.log`（不混在业务日志里）；
2. 同步打 ERROR 日志（CRITICAL 级别），便于日志采集系统捕获；
3. 维护标记文件 `ALERT_PENDING`，供运维脚本快速判断。

**接口约定：告警失败绝不影响业务** —— 所有实现必须自行吞掉异常。
否则一次发送失败可能回滚掉「对账已发现异常」这一事实。

#### 10.12.3 邮件告警的调研结论（重要）

按需求调研了邮件通道，发现**生产环境暂不可行**：

### 10.13 第 10 期：死信队列监控（已完成）

#### 10.13.1 先发现并修复了一个真实缺陷

实现监控前先核对生产 RabbitMQ 队列，发现 **3 个死信队列根本不存在**：

| 业务队列 | DLQ 常量 | 生产队列是否存在 |
|---------|---------|----------------|
| `wuling.order.timeout.queue` | `..._DLQ` | ✅ |
| `wuling.payment.success.queue` | `..._DLQ` | ✅ |
| `wuling.settlement.notify.queue` | `..._DLQ` | ✅ |
| `wuling.finance.split.queue` | `FINANCE_SPLIT_DLQ` | ❌ **缺失** |
| `wuling.finance.reverse.queue` | `FINANCE_REVERSE_DLQ` | ❌ **缺失** |
| `wuling.marketing.exchange-verify.queue` | `EXCHANGE_VERIFY_DLQ` | ❌ **缺失** |

**根因（我在第 5、6 期引入）**：新增业务队列时只在队列上配置了
`x-dead-letter-routing-key`，**却忘了声明对应的 DLQ 队列与绑定**。

**后果**：消费失败重试超限后 `nack(requeue=false)`，
消息因目标路由不存在而被 RabbitMQ **静默丢弃** —— 且这几个队列承载的正是
**资金链路**（分账 / 冲正 / 兑换核销）。运维连「哪些消息失败了」都查不到，
只能靠对账（小时级）事后倒推。

**修复**：补齐 3 个 DLQ 的 `Queue` + `Binding` 声明。生产已验证 6 个 DLQ 全部存在。

#### 10.13.2 监控设计

新增 `DlqMonitor`，每 5 分钟检查 6 个 DLQ：

| 情形 | 动作 |
|------|------|
| 队列有消息（≥ 阈值） | 发 **CRITICAL** 告警 |
| **队列不存在** | 发 **WARNING** —— 这一条正是为捕获上面那类漏声明 |
| 从堆积回落到阈值内 | 发 INFO（确认恢复） |
| 连续多轮堆积 | **只在首次告警**（去重，避免刷屏淹没真实信号） |

**频率为何高于对账**：DLQ 堆积是「消费失败」的**即时信号**，
而对账是「账目不一致」的**事后验证**。前者能提前暴露问题，
便于在资金受影响前介入（如分账未执行期间又触发结算）。

**配置**：

```yaml
app:
  mq:
    dlq-monitor:
      enabled: true      # 可临时关闭
      threshold: 1       # 有 1 条即告警
      cron: "0 */5 * * * ?"
```

**实现要点**：用 `AmqpAdmin.getQueueInfo` 查询（不修改队列）；
`@ConditionalOnClass(AmqpAdmin.class)` 保证缺少 amqp 依赖时不加载。

#### 10.13.3 测试：两处「测试有效性」的自我修正

#### 10.14.3 ⚠️ 实施中发现：`RabbitConfig` 导致无 MQ 的服务启动失败

**问题**：user-service 正确地去掉了 `amqp` 依赖（它不需要 MQ），
但启动报错：

```
NoClassDefFoundError: org/springframework/amqp/support/converter/MessageConverter
  Failed to introspect Class [com.wuling.common.mq.RabbitConfig]
```

**原因**：`RabbitConfig` 位于 `wuling-common`（amqp 为 optional 依赖）。
虽然我给类加了 `@ConditionalOnClass`，但 Spring 在**条件评估阶段**仍需
内省该类的 `@Bean` 方法签名（含 `MessageConverter` 等 AMQP 类型），
此时类加载器找不到这些类 —— `@ConditionalOnClass` 对此无能为力。

**修复**：在**不需要 MQ 的服务**（user / auth / file）中，
用 `@ComponentScan.excludeFilters` 排除 `RabbitConfig`：

```java
@SpringBootApplication
@ComponentScan(basePackages = "com.wuling",
        excludeFilters = @ComponentScan.Filter(type = FilterType.ASSIGNABLE_TYPE,
                classes = com.wuling.common.mq.RabbitConfig.class))
```

> 经验：`@ConditionalOnClass` 只能防"类不存在"，
> 防不住"类的**方法签名**引用了不存在的类"。后者必须在扫描阶段排除。

### 10.15 第 12 期：subject 端口解耦 + server 死代码审计（已完成）

#### 10.15.1 决策：subject 不拆为独立服务

对 subject 域做了拆分可行性复核后，**决定不拆**，只做端口解耦。

**核心原因：资金事务安全**

| 依赖方 | 调用位置 | 拆分后果 |
|--------|---------|---------|
| `finance/LedgerService` | **`@Transactional` 内**（5 处） | 事务内发起网络调用 → 事务时长被网络 RTT 放大、连接池被占满、下游抖动导致**资金事务回滚** |

分账是资金核心路径，把主体查询远程化会把「本地读表」变成「跨服务网络调用」，
引入的可用性风险远大于拆分收益。故 subject 保留在 server 内。

#### 10.15.2 已做：端口解耦（为将来拆分留出口）

新增 `SubjectQueryPort` + `LocalSubjectQueryAdapter`，把 4 处跨域直接依赖改为依赖接口：

| 依赖方 | 改动 |
|--------|------|
| `finance/LedgerService` | 5 处调用改走 port |
| `finance/RoleWorkbenchService` | `channelStores`/`investorStores` 返回值改为 `List<Map>`（不再暴露实体） |
| `product/ProductQueryService` | 1 处调用改走 port |

解耦后：`product` 域对 subject 的依赖仅剩 `SubjectQueryPort` 一个接口 —— 这为第 13 期拆分扫清了障碍。

> 说明：`common/internal/InternalQueryController` 仍直接用 mapper，属正常的「内部 API 适配层」。

#### 10.15.3 死代码审计（结论：无可安全删除项）

#### 10.16.5 实施中发现的 3 个问题

**问题 1：SecurityFilterChain 缺失导致全部 401**

product-service 引入了 `spring-boot-starter-security` 但未提供 `SecurityFilterChain`，
Spring Security 默认策略「所有请求需认证」生效，把 `/internal/**` 和
`/actuator/health` 一并拦成 401，导致 trade 下单校验失败、探活失败。

→ 修复：新增 `SecurityConfig`，显式放行 `/internal/**` 与 `/actuator/health`。
（其他服务都已有此配置，product-service 是新建时遗漏。）

**问题 2：profile 缺 `app.jwt.access-token-ttl` 导致启动失败**

`application-dev.yml` 的 `app.jwt` 块与主配置合并时，主配置缺
`access-token-ttl` / `refresh-token-ttl`，`MiniAppTokenProvider` 注入失败：

```
Could not resolve placeholder 'app.jwt.access-token-ttl'
```

→ 修复：主配置补齐两个 ttl（与 user-service 保持一致）。

**问题 3：`@LoadBalanced` 无法处理字面 IP（本地联调）**

本地 dev 的 `app.internal.*-base` 写的是 `http://127.0.0.1:8091`，
而 `@LoadBalanced` 会把 host 当作 serviceId 去 Nacos 解析，报：

```
Service Instance cannot be null, serviceId: 127.0.0.1
```

→ 修复：新增 `app.internal.direct-connect` 开关。
本地置 `true` 时用**不带 `@LoadBalanced`** 的 builder，按字面 IP 直连；
生产缺省 `false`，仍走服务发现。

> 这暴露了一个历史盲区：**trade 的跨服务调用在本地 dev 从未真正跑通过**
> （此前只验证了 server 侧）。本次修好后才完成端到端联调。
