# 慧养智萃茶机对接（设备状态 + 胶囊冲泡记录）

> 对接方：杭州智萃谷健康科技有限公司
> 通道：阿里云轻量消息队列（原 MNS）**普通队列**，消费端常驻长轮询（非 HTTP 回调）
> 本文档性质：对接方案 + 实施记录。代码已落地，MNS 真机联调待对方提供密钥后执行（见第 7 节）。

---

## 1. 一句话说明

对方把「设备在线状态」和「胶囊冲泡记录」推到阿里云 MNS 队列；本项目的 `server` 服务内常驻一个
消费端把消息拉下来，规范化后转投内部 RabbitMQ，再由业务消费者落库；运营后台在
**主体管理 → 设备管理 / 冲泡记录** 两个页面查看与维护。

## 2. 报文结构（对方口径）

对方给出的事实：

| 项          | 值                                                                    |
| ----------- | --------------------------------------------------------------------- |
| messageBody | **Base64 编码的 JSON**                                                |
| 外层结构    | `{ "messagetype": "status" \| "upload", "payload": "<JSON 字符串>" }` |
| payload     | 注意是**字符串**形式的 JSON，需要二次解析                             |
| 消费方式    | 普通队列长轮询，消费端要一直开着实时消费                              |

`messagetype=status`（设备状态）：

```json
{
  "deviceSN": "ZPDS2512090086G",
  "baseCreateTime": "2026-03-10 19:32:25",
  "status": "ONLINE",
  "deviceName": "869978072404913"
}
```

`messagetype=upload`（胶囊冲泡记录）：

```json
{
  "teaCode": 209,
  "teaName": "欧米伽-3植物乳",
  "customer": 90000001,
  "madeDay": "20251021",
  "serialNumber": 408,
  "baseCreateTime": "2026-03-10 21:16:04",
  "deviceName": "869978072404913",
  "deviceSN": "ZPDS2512090086G"
}
```

### 关键缺口：报文里没有门店

消息里只有 `deviceSN` / `deviceName`，**没有任何门店字段**。因此必须先有本地设备台账，
再把设备绑定到门店，消息才能归属到门店。为此做了两件事：

1. 未登记过的 `deviceSN` **自动建档**（`store_subject_id` 为空 = 未绑定门店），保证历史数据不丢；
2. 台账建成后由运营在后台绑定门店，一台设备同一时刻只归属一家门店，一家门店可绑定多台设备。

### 字段口径细节（实测踩点）

| 细节                                                  | 处理方式                                                                                                                              |
| ----------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| 附件 xlsx 写 `seriaNumber`，报文示例写 `serialNumber` | 解析时两种键名都兼容，落库统一为 `serial_number`                                                                                      |
| `teaCode` / `customer` / `serialNumber` 是数字        | 统一按文本落库，避免类型漂移                                                                                                          |
| payload 内含 `\r\n` 转义                              | Jackson 解析，不影响字段提取                                                                                                          |
| 时间 `yyyy-MM-dd HH:mm:ss`                            | 同时兼容 `yyyy-MM-dd'T'HH:mm:ss`、`yyyy/MM/dd`、`yyyyMMddHHmmss`；按 Asia/Shanghai 原样落库，不做时区换算                             |
| 缺 `deviceSN` 或 `baseCreateTime`                     | 视为坏报文：留档 `device_message_error` 后丢弃，**不用当前时间兜底**（否则重复投递会变成两条记录）                                    |
| 状态值大小写                                          | 统一转大写（ONLINE/OFFLINE），避免 `online` 与 `ONLINE` 混用导致状态判断失效                                                          |
| 报文乱序（MQ 重试/重复投递）                          | 状态报文以「当前状态的确立时间」为水位线，比它更早的**整条丢弃**（不改状态、不改确立时间、不写流水）；`last_report_time` 只前进不后退 |

## 3. 消费链路（为什么加一层 RabbitMQ）

```
阿里云 MNS 普通队列
   ↓ MnsPoller（应用内常驻线程，长轮询 30s）
规范化信封 DeviceMessageEnvelope
   ↓ MqProducer（发布确认成功后才删除 MNS 消息）
内部队列 wuling.device.message.queue（死信 → wuling.device.message.queue.dlq）
   ↓ DeviceMessageConsumer（继承 AbstractMqConsumer：幂等 / 延迟重试 / 死信 / 手动 ACK）
device_info / device_brew_record / device_status_log
```

可靠性口径：

| 场景                            | 行为                                                                           |
| ------------------------------- | ------------------------------------------------------------------------------ |
| 转投 RabbitMQ 失败              | **不删除** MNS 消息，可见性超时后由 MNS 重投（at-least-once）                  |
| 报文解析失败 / 未知 messagetype | 写 `device_message_error` 留档后删除，避免坏消息在 MNS 里无限重投并刷满日志    |
| 落库失败                        | 消费失败 → 延迟重试 → 超过 `app.mq.max-retry` 进 DLQ，运维可从死信队列取回重放 |
| 重复投递                        | `MqIdempotent`（按 messageId）+ 业务唯一键双保险                               |

业务唯一键（兜底去重）：

- 冲泡记录：`(device_sn, base_create_time, tea_code, serial_number)`
- 状态流水：`(device_sn, base_create_time)`

## 4. 数据模型（Flyway `V75__device_management.sql`）

| 表                     | 用途          | 关键点                                                                                                                                       |
| ---------------------- | ------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| `device_info`          | 设备台账      | `device_sn` 唯一；`device_name` 在未删除台账中唯一；`store_subject_id` 为当前归属（可空=未绑定）；在线状态与最近上报由消息维护，运营不可手改 |
| `device_store_binding` | 绑定历史      | 换绑 = 旧记录写 `UNBIND` + 新记录写 `BIND`（同一事务）；门店名存**快照**                                                                     |
| `device_brew_record`   | 冲泡记录      | 门店为**写入时刻快照**（设备换绑后历史记录仍指向当时门店）                                                                                   |
| `device_status_log`    | 在线/离线流水 | 仅状态**变化**时写入，避免高频上报把表撑爆；原始 payload 留档（V78）                                                                         |
| `device_message_error` | 异常报文留档  | 解析失败/未知类型原样留档，便于事后核对与重放                                                                                                |

> 说明：后台通用 CRUD 的查询固定带 `deleted = 0`，故每张表都带 `deleted` 列。

### 5.1 门店侧（小程序，只读）

门店经营角色在小程序里同样能看到这两块数据，但**只能看**：台账维护（新增 / 绑定 / 解绑 / 删除 / 改名）仍归运营后台，
门店侧不开放写操作 —— 设备与门店的归属关系直接决定后续记录落在哪家门店，错绑的代价远高于门店自助绑定的收益。

| 页面     | 路径                                              | 能力                                                                                                                                                                 |
| -------- | ------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 设备管理 | `packageRole/role-devices/role-devices`           | 本店设备清单（别名/编码、设备ID、在线状态、最近上报）、共 N 台 · 在线 M 台、进入自动拉取 + 手动/下拉刷新                                                             |
| 冲泡记录 | `packageRole/role-brew-records/role-brew-records` | 本店冲泡记录（上报时间、茶品、设备、客户代码、序列号、生产日期），默认近 7 天、可切近 30 天，**关键词搜索**（输入停顿 300ms 自动查，键盘搜索键立即查），触底加载更多 |

> 新增角色功能时必须在这里登记一次，否则点击会落到兜底提示「该功能待接入」——
> 2026-10-16 就踩过：两处各写了一份 routeMap，只改了工作台那份，「我的 → 设备管理」点了弹提示。
> `scripts/role-function-pages.test.mjs` 现在会遍历三类角色的全部入口做校验。

接口（小程序 JWT 鉴权，路径落在 `/api/v1/app/workbench/store/{storeSubjectId}/**`，由网关 `/api/v1/**` 兜底进入 server）：

| 接口                      | 说明                                                                                                                                                            |
| ------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET .../devices`         | 本店设备分页（固定 `bound` 口径，只返回当前绑定本店的设备；`size` 上限 50）                                                                                     |
| `GET .../devices/summary` | 本店设备概览 `{ total, online }`（头部数字不能拿分页条数估算）                                                                                                  |
| `GET .../brew-records`    | 本店冲泡记录分页，支持 `keyword`（多字段模糊搜索）/ `deviceSn`（编码精确，兼容保留）/ `from` / `to`（`yyyy-MM-dd`，含当天；内部换算成次日 00:00:00 开区间上界） |

搜索口径（`keyword`）：在**茶品名 / 茶品编码 / 设备编码 / 设备ID / 设备别名 / 客户代码 / 序列号**上做 OR 模糊匹配，
与时间范围可叠加；服务端 trim 后按 50 字符截断，并把 `%`、`_`、`\` 转义（`like ? escape '\'`），
因此输入单个 `%` 不会变成全表匹配。实现上两处必须注意：

- **统计与列表 SQL 共用同一段 `FROM + LEFT JOIN device_info`**：别名是匹配字段之一，统计语句缺 join 会直接报错；
- 别名用 `coalesce(d.alias, '')` 比较，否则「设备台账缺失/已删除」的记录会被悄悄排除出结果集。

页面上原来的「设备筛选」chip 行已删除（它依赖设备接口，且横向 `scroll-view` 缺显式高度在 Skyline 下会被压扁裁切），
改由搜索框输入别名或编码来筛设备。

> **横滚容器必须写高度**：Skyline 下横向 `scroll-view` 不会按内容撑开，必须显式 `height`（参考门店选品页
> `.products-tabs-scroll { height: 76rpx; overflow: hidden }`）。`scripts/role-device-pages.test.mjs` 已加仓库级守卫；
> 另有 4 个既有页面（`exchange-records`、`role-income-records`、`role-invest-records`、`role-withdraw-records` 的分类 chip 行）
> 属同类遗留隐患，已在守卫里登记为已知项，待单独排期修复。

越权防护（三条同时生效，缺一不可）：

1. `/api/v1/app/workbench/**` 已注册小程序鉴权拦截器，无 token 直接 401；
2. 控制器内 `CurrentUser.require()` 兜底（路径注册漏配时不会「默认放行」）；
3. `StoreOperatorService#canOperate(userId, storeSubjectId)` 校验归属，不通过返回 403 `无权查看该门店数据`；
   该判定与内部接口 `/internal/store-operator-check` **共用同一份实现**（原先写在 `InternalQueryController` 里，现收敛到服务里，避免两边口径漂移）。

口径提醒：冲泡记录按**写入时刻的门店快照**（`store_subject_id`）过滤，与后台一致 —— 设备解绑或换绑后，历史记录仍归属当时门店。

### 5.2 队列自检：区分「对方没推」与「我们没收到」

设备数据唯一来源是对方推送到阿里云 MNS 队列的报文，因此「后台列表空」有两种完全不同的原因，
而在应用侧两者同形（都是零数据、零报错）。自检把队列自身的计数与消费端状态暴露出来，用来区分：

| 现象                                | 判定                                                   | 处置                                     |
| ----------------------------------- | ------------------------------------------------------ | ---------------------------------------- |
| 可见消息 0、最近收到：无            | 队列里根本没有消息（对方没推，或推到了别的队列/账号）  | 按 9.1 的清单与对方核对                  |
| 可见消息 > 0、最近收到：无/很久以前 | 消息在队列里积压，消费端没消费                         | 查 `Mns 轮询异常` 日志、AK/SK 与队列权限 |
| `ok=false` + 原因                   | 队列属性查询本身失败（队列不存在 / 无权限 / 网络超时） | 按原因核对队列名、账号授权与出网策略     |

- 接口：`GET /api/v1/admin/device/queue-status`（默认走 10 分钟缓存，`?refresh=1` 强制实时查询）；
  返回 `enabled / running / connected / queueName / ok / error / activeMessages / inactiveMessages /
delayMessages / lastPollTime / lastMessageTime / forwardedCount / failedCount / lastError` 等字段，
  **不含任何密钥**。
- 界面：运营后台「主体管理 → 设备管理」页顶部一行状态 + 「自检」按钮（失败标红）。
- 日志：消费端每 10 分钟自动自检一次，打一条 `MNS 队列自检 queue=... 可见消息=...`，
  异常时为 WARN。即使没人打开后台，也能从日志判断对方是否在推。
- 口径提醒：`failedCount` 只统计**转投/解析失败**，轮询连不上只记错误摘要、不计入失败数 ——
  否则一段时间内的连接问题会让「到底丢没丢消息」变得无法判断。

### 5.3 演示数据（联调 / 对外演示）与清理

```powershell

# 1) 先投 1 条状态报文：消费端自动建档（未绑定门店）

# 2) 在后台「设备管理」把该设备绑定到目标门店（别名/备注建议带「演示」字样）

#       先投记录再绑店，门店侧页面永远看不到这些记录。

# 3) 再投冲泡记录：BaseTime 决定归属时间，SerialStart 决定序列号起点
```

### 5.4 上线坑位：前端旧构建会让「菜单可点但没反应」

## 6. 配置与环境变量

`server/src/main/resources/application.yml` 新增 `app.mns.*`，默认**关闭**：

| 环境变量               | 含义                 | 默认    |
| ---------------------- | -------------------- | ------- |
| `MNS_ENABLED`          | 是否启用 MNS 消费端  | `false` |
| `MNS_ENDPOINT`         | 队列 endpoint        | 空      |
| `MNS_QUEUE`            | 队列名               | 空      |
| `MNS_AK` / `MNS_SK`    | AccessKeyId / Secret | 空      |
| `MNS_WAIT_SECONDS`     | 长轮询等待秒数       | `30`    |
| `MNS_ERROR_BACKOFF_MS` | 轮询异常退避         | `15000` |

行为约定：

- `MNS_ENABLED=false`：消费端不启动，应用照常运行，其余功能不受影响；
- `MNS_ENABLED=true` 但缺 AK/SK/endpoint/queue：**拒绝启动**（fail-fast），
  避免出现「以为在消费、其实一条都没收到」的静默故障；
- 密钥只从部署侧注入（`/opt/wuling/app/secrets.env`），不写入仓库。

依赖：`com.aliyun.mns:aliyun-sdk-mns:1.3.1`（版本锁在父 POM）+ 显式引入的 JAXB 2.x 栈。
**坑位说明**：MNS SDK 用 `javax.xml.bind`（JAXB 2.x）解析错误响应，而 JDK 17 已移除 JAXB、
Spring Boot 3.3.x BOM 管理的又是 4.x（jakarta 命名空间），被顶替后一旦对方返回错误
（密钥错/无权限/队列不存在）就会抛 `NoClassDefFoundError`，连错误原因都看不到。
因此父 POM 排除了 SDK 的 jaxb 传递依赖，`server/pom.xml` 显式锁定
`jaxb-runtime 2.3.6 + jakarta.xml.bind-api 2.3.3 + jakarta.activation-api 1.2.2 + txw2 2.3.6`，
并由 `MnsSdkJaxbCompatibilityTest` 在 CI 阶段守住这条链路。

## 9. 排障速查

| 现象                                                | 首要排查点                                                                                                                          |
| --------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| 后台设备列表没有新设备                              | 先看「设备管理」页顶部队列自检：可见消息 0 = 对方没推（按 9.1 核对）；> 0 = 我们没消费（查 `MNS` 日志与 AK/SK 权限）                |
| 有设备但门店列一直「未绑定」                        | 是否在后台绑定过门店（报文不含门店，不会自动归属）                                                                                  |
| 冲泡记录比设备侧少                                  | 查 `device_message_error`（坏报文）与 `.dlq`（落库失败超限）                                                                        |
| 门店改名后历史记录还是旧名                          | 预期行为：冲泡记录/状态流水存的是**写入时刻**的门店名快照；设备列表的门店名是实时 join                                              |
| 门店被删除后绑定历史里还有门店名                    | 预期行为：门店删除只影响设备列表的实时 join（显示「未绑定」），绑定历史/冲泡记录/状态流水保留**写入时刻**的门店名快照，便于事后回溯 |
| 解绑后立刻又回来了                                  | 消息带的是设备当前绑定，解绑只影响**之后**的消息归属                                                                                |
| 删除设备后它又回到列表                              | 不会：台账删除后同一个 SN 的上报只落事实表、**不重建台账**。要恢复请用「新增设备」填同一 `deviceSN`（复用原行，不会产生第二行）     |
| 冲泡记录还在增加，但设备列表里找不到这台设备        | 该设备台账已被删除：上行数据仍按事实留档（无门店归属），状态流水不再写入；需要归属门店请重新新增并绑定                              |
| 最近上报时间不动了                                  | 该字段**只前进不后退**（防 MQ 重试乱序把时间改小）；`status` 与 `upload` 都算一次上报                                               |
| 设备状态和实际不符（疑似旧报文）                    | 比「当前状态确立时间」更早的状态报文会被整条丢弃，日志出现 `忽略过期的设备状态报文`；同一秒的报文仍按后到者生效                     |
| 想知道谁删了哪台设备、为什么删                      | 「系统管理 → 审计日志」筛选 模块=设备 / 操作类型=删除：操作对象是设备编码、备注是删除原因；恢复操作同样有 `恢复` 记录               |
| 启动报缺少 MNS 配置                                 | 把 `MNS_ENABLED` 置 false，或补齐 4 项配置（fail-fast 是刻意设计）                                                                  |
| 日志出现 `NoClassDefFoundError: javax/xml/bind/...` | JAXB 依赖被 BOM 顶替，检查 `server/pom.xml` 的 4 个 JAXB 依赖是否被改动/移除                                                        |

### 9.1 队列零消息时：与对方核对清单

后台「设备管理 → 自检」显示「可见消息 0、最近收到：无」时，说明**队列里没有消息**，
按下面顺序逐条确认（前 3 条占绝大多数）：

1. **对方是否真的在推**：对接方（杭州智萃谷）侧的发送端是否已开启、是否有定时任务在跑；
2. **推的是不是这个队列**：对方配置的 endpoint / 队列名 / 账号，是否与我们的一致
   （我们当前是 `MNS_ENDPOINT` + `MNS_QUEUE` 注入的那一套，见第 6 节）；
3. **有没有在线设备**：对方是否真有在跑的茶机（设备不上报就不会有任何报文，
   此时「零消息」是正常现象，不是故障）；
4. **推送范围**：是否只推 `status`、没推 `upload`（或反之）；
5. **是否有其他消费者**：同一个队列是否还有别的消费端在抢消息（MNS 是「消费即删除」，
   被别处消费掉的消息我们永远看不到）；
6. **报文样例与附件**：对方承诺的 xlsx 报文附件仓库内没有（见第 12 节），
   建议索要一份用于字段比对；
7. **凭证与权限**：队列属性查询若返回 `ok=false`，先按错误信息核对 AK/SK 权限与出网策略
   （`server` 容器需能出公网访问 MNS endpoint）。

## 12. 待核对：与对方原始报文附件逐字段比对（2026-10-15 记录）

仓库内**没有**对方提供的 xlsx 报文附件，本文档的字段清单是对接沟通的转录，
因此无法排除附件里还有未转录的字段。已做的兜底：

- `status` 与 `upload` 两类报文都把原始 payload 原样留档
  （`device_status_log.raw_payload`，V78；`device_brew_record.raw_payload`，V75）——
  对方新增字段时历史数据可回溯，且不影响现有链路与去重口径；
- 解析失败的报文一律进 `device_message_error`（含 Base64 原文），不会静默丢弃。

拿到附件后按下表逐字段核对，缺什么补什么（解析 → 落库 → 单测 → 必要时加迁移）：

| 报文     | 当前已实现字段                                                                                                                                |
| -------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `status` | `deviceSN` / `deviceName` / `status` / `baseCreateTime`                                                                                       |
| `upload` | `teaCode` / `teaName` / `customer`(`customerCode`) / `madeDay` / `serialNumber`(`seriaNumber`) / `baseCreateTime` / `deviceName` / `deviceSN` |

除字段外，建议一并确认的通道细节：Base64 与明文的实际取值方式、队列可见性超时与最大重试次数、
签名版本（v1/v4；对方若要求 https 需升级 SDK）、单条消息大小上限、是否有顺序保证
（当前实现按「最近上报只前进」处理乱序，但不按时间丢弃过期状态）。
