# 限流与网关防护实践

> 场景：网关层全局限流，防止单个来源（IP）刷爆后端。
> 核心思路：基于 Redis 固定窗口计数，按「路径分组 + 来源」维度限流；
> 限流数据落独立 db 便于监控清理；429 判定时打完整上下文日志便于定位误伤。

## 一、核心思路

```
请求进来
  ├─ 解析来源（优先 X-Forwarded-For 第一个，兜底 RemoteAddress）
  ├─ 拼限流 key = 前缀 + 路径分组 + 来源
  ├─ Redis INCR key
  │    ├─ 首次（count==1）→ 设 TTL（固定窗口）
  │    └─ 判断 count <= 阈值 → 放行
  ├─ 超阈值 → 打完整日志 → 返回 429
  └─ Redis 异常 → fail-open 放行（限流组件故障不能拖垮网关）
```

关键点：
1. **限流维度不能只按 IP**——同一出口 IP 会共享大量真实用户，纯 IP 维度必然误伤。
   加「路径分组」维度（或用户 id）隔离不同业务，避免「一个来源高频访问不同接口被总闸误伤」。
2. **限流数据落独立 db**——与业务缓存、登录态隔离，方便 `redis-cli -n N` 监控清理。
3. **429 判定必须打完整上下文**——db、key、来源、路径、当前计数、阈值，缺一不可，否则分不清「误伤」还是「真超限」。
4. **fail-open**——Redis 挂了放行，而不是全部 429。

## 二、可复制的代码骨架

### 显式声明限流专用连接（独立 db）

```java
@Configuration
public class RateLimitGlobalFilter {

    @Bean
    public ReactiveStringRedisTemplate rateLimitRedisTemplate(
            @Value("${app.rate-limit.redis-db:4}") int database,
            ReactiveRedisConnectionFactory factory) {
        if (factory instanceof LettuceConnectionFactory lettuce) {
            LettuceConnectionFactory clone = new LettuceConnectionFactory(
                    lettuce.getStandaloneConfiguration(), lettuce.getClientConfiguration());
            clone.setDatabase(database);          // 独立 db，与业务隔离
            clone.setShareNativeConnection(false);
            clone.afterPropertiesSet();
            log.info("[限流] 独立连接已创建 database={}", database);
            return new ReactiveStringRedisTemplate(clone);
        }
        // cluster 模式仅支持 db0，退化为默认连接（key 前缀已保证隔离）
        return new ReactiveStringRedisTemplate(factory);
    }
}
```

### 限流过滤器（GlobalFilter）

```java
@Component
class RateLimitGlobalFilter implements GlobalFilter, Ordered {

    private static final long QPS = 200;
    private static final long WINDOW_SECONDS = 1;
    private static final String KEY_PREFIX = "app:ratelimit:";

    private final ReactiveStringRedisTemplate redis;
    private final int database;

    @Override
    public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
        String path = exchange.getRequest().getURI().getPath();
        String ip = resolveIp(exchange);
        String group = pathGroup(path);          // 路径分组维度
        String key = KEY_PREFIX + group + ":" + ip;

        return redis.opsForValue().increment(key)
                .flatMap(count -> {
                    if (count != null && count == 1L) {
                        return redis.expire(key, Duration.ofSeconds(WINDOW_SECONDS))
                                .then(Mono.just(count));
                    }
                    return Mono.just(count);
                })
                .flatMap(count -> {
                    long c = count == null ? 0L : count;
                    if (c <= QPS) {
                        return chain.filter(exchange);
                    }
                    // 429 判定：完整上下文，便于定位误伤
                    log.warn("[限流] 触发 429 database={} key={} ip={} path={} count={} qps={}",
                            database, key, ip, path, c, QPS);
                    return tooManyRequests(exchange);
                })
                .onErrorResume(e -> {
                    log.warn("[限流] Redis 异常，放行 database={} key={} err={}",
                            database, key, e.getMessage());
                    return chain.filter(exchange);   // fail-open
                });
    }

    @Override
    public int getOrder() {
        return -60; // 早于鉴权(-50)，晚于日志(-100)
    }

    /** 来源解析：优先 XFF 第一个，兜底 RemoteAddress */
    private static String resolveIp(ServerWebExchange exchange) {
        String forwarded = exchange.getRequest().getHeaders().getFirst("X-Forwarded-For");
        if (forwarded != null && !forwarded.isBlank()) {
            return forwarded.split(",")[0].trim();
        }
        if (exchange.getRequest().getRemoteAddress() != null
                && exchange.getRequest().getRemoteAddress().getAddress() != null) {
            return exchange.getRequest().getRemoteAddress().getAddress().getHostAddress();
        }
        return "unknown";
    }

    /** 路径分组：取第一段粗粒度分组，既隔离业务又避免 key 爆炸 */
    private static String pathGroup(String path) {
        if (path == null || path.isBlank() || path.equals("/")) return "root";
        String[] seg = path.split("/");
        return seg.length > 1 && !seg[1].isBlank() ? seg[1] : "root";
    }

    private static Mono<Void> tooManyRequests(ServerWebExchange exchange) {
        ServerHttpResponse response = exchange.getResponse();
        response.setStatusCode(HttpStatus.TOO_MANY_REQUESTS);
        response.getHeaders().setContentType(MediaType.APPLICATION_JSON);
        String body = "{\"code\":429,\"message\":\"请求过于频繁，请稍后重试\",\"data\":null}";
        DataBuffer buffer = response.bufferFactory()
                .wrap(body.getBytes(StandardCharsets.UTF_8));
        return response.writeWith(Mono.just(buffer));
    }
}
```

## 三、关键决策与权衡

| 决策点 | 选择 | 理由 |
|--------|------|------|
| 限流维度 | 路径分组 + 来源（而非纯 IP） | 纯 IP 会误伤共享出口的多个真实用户 |
| Redis 故障 | fail-open 放行 | 限流是防护不是依赖，故障不能放大成全站 429 |
| 落库 | 独立 db | 便于 `-n N` 监控、清理，与业务隔离 |
| 窗口 | 固定窗口（INCR + 首次设 TTL） | 简单可控，够用 |
| 顺序 | 晚于日志、早于鉴权 | 日志能记录被限流的请求，限流先于鉴权拦截 |
| 日志 | 429 打完整上下文 | 分得清「误伤」还是「真超限」，可精确定位 db/key |

## 四、定位 429 的操作方法

```bash
# 复现 429 时，日志会打印完整 key 与 db
# [限流] 触发 429 database=4 key=app:ratelimit:api:1.2.3.4 ip=1.2.3.4 path=/api/xxx count=201 qps=200

# 定位 Redis（-n 4 即 db4）
redis-cli -n 4 KEYS 'app:ratelimit:*'            # 看所有限流 key
redis-cli -n 4 TTL  'app:ratelimit:api:1.2.3.4'  # 窗口剩余秒数
redis-cli -n 4 DEL  'app:ratelimit:api:1.2.3.4'  # 手动解除某来源限流
```

## 五、验证方法

- 用 `ab` / `wrk` 对同一路径短时间打超过阈值请求，观察 429 与日志。
- 手动停掉 Redis 再请求，应照常放行（fail-open）。
- 确认限流 key 落在独立 db，而非业务 db0。
