# 缓存优化实践

> 场景：读多写少、且「查询 + 组装」成本高的数据（典型如首页聚合数据、详情页、配置项）。
> 核心思路：Redis 缓存优先，未命中回源 DB 并写回；缓存不可用或损坏时 fail-open 回源，绝不让缓存拖垮主链路。

## 一、核心思路

```
请求进来
  ├─ 读缓存（try）→ 命中且可反序列化 → 直接返回（跳过 N 次 DB 查询 + 大对象组装）
  ├─ 未命中 / 缓存损坏 / Redis 挂了（catch 返回 null）→ 回源 DB 组装
  └─ 组装完成后写回缓存（try，失败静默）→ 返回
```

关键点：

1. **读、写、反序列化三处全部 try-catch 吞掉异常**——缓存是「加速器」不是「依赖」，任何一步失败都不能影响业务返回。
2. **TTL 兜底**——即使主动失效漏了，数据也会在 TTL 后自动过期，避免脏数据永久残留。
3. **主动失效**——写操作（增删改）后显式 `delete` 缓存 key，而非只依赖 TTL。

## 二、可复制的代码骨架

```java
import com.fasterxml.jackson.databind.ObjectMapper;
import org.springframework.data.redis.core.StringRedisTemplate;

@Service
public class CatalogQueryService {

    private final ObjectMapper objectMapper;
    private final StringRedisTemplate redis; // 通过命名空间管理器取（见 04 文档）

    private static final String CACHE_KEY = "catalog:all";
    private static final Duration CACHE_TTL = Duration.ofMinutes(5);

    public CatalogDTO getCatalog() {
        // 1. 缓存优先
        String cached = safeGet(CACHE_KEY);
        if (cached != null) {
            CatalogDTO hit = parse(cached, CatalogDTO.class);
            if (hit != null) {
                return hit; // 命中直接返回，跳过 3 次 DB 查询 + 组装
            }
        }

        // 2. 回源 DB 组装（原有逻辑）
        CatalogDTO result = buildFromDb();

        // 3. 写回缓存（失败不影响返回）
        safeSet(CACHE_KEY, result);
        return result;
    }

    // ---------- 三个安全封装：全部 fail-open ----------

    private String safeGet(String key) {
        try {
            return redis.opsForValue().get(key);
        } catch (Exception e) {
            return null; // Redis 不可用 → 回源 DB
        }
    }

    private void safeSet(String key, Object value) {
        try {
            String json = objectMapper.writeValueAsString(value);
            redis.opsForValue().set(key, json, CACHE_TTL);
        } catch (Exception e) {
            // 序列化或 Redis 失败 → 静默忽略，业务照常返回
        }
    }

    private <T> T parse(String json, Class<T> clazz) {
        try {
            return objectMapper.readValue(json, clazz);
        } catch (Exception e) {
            return null; // 缓存数据损坏 → 回源
        }
    }

    // ---------- 主动失效：写操作后调用 ----------

    public void evictCache() {
        try {
            redis.delete(CACHE_KEY);
        } catch (Exception e) {
            // 删除失败可忽略，TTL 兜底
        }
    }
}
```

```java
// 泛型集合反序列化必须用 TypeReference，否则会得到 LinkedHashMap 列表
private List<MenuDTO> parseList(String json) {
    try {
        return objectMapper.readValue(json,
            new TypeReference<List<MenuDTO>>() {});
    } catch (Exception e) {
        return null;
    }
}
```

### 带 id 的详情缓存（key 加维度前缀）

```java
private static final String DETAIL_PREFIX = "catalog:detail:";

public DetailDTO getDetail(String id) {
    String key = DETAIL_PREFIX + id;
    String cached = safeGet(key);
    if (cached != null) {
        DetailDTO hit = parse(cached, DetailDTO.class);
        if (hit != null) return hit;
    }
    DetailDTO result = buildDetailFromDb(id);
    safeSet(key, result);
    return result;
}

public void evictDetail(String id) {
    try { redis.delete(DETAIL_PREFIX + id); } catch (Exception ignored) {}
}
```

## 三、关键决策与权衡

| 决策点         | 选择                          | 理由                             |
| -------------- | ----------------------------- | -------------------------------- |
| 缓存挂了怎么办 | fail-open 回源 DB             | 缓存是加速器，不是依赖；宁慢不挂 |
| 缓存数据损坏   | 反序列化 catch 返回 null 回源 | 脏缓存不污染返回                 |
| 失效策略       | 主动 delete + TTL 兜底        | 双保险，防漏删                   |
| TTL 时长       | 5 分钟                        | 读多写少数据，兼顾新鲜度与命中率 |
| 序列化格式     | JSON（ObjectMapper）          | 可读、通用、跨语言               |

## 四、适用 / 不适用

**适用**：

- 数据读多写少、单次查询 + 组装成本高（多次 DB 查询、大对象、复杂计算）
- 允许短暂数据不一致（TTL 窗口内）

**不适用（慎用缓存）**：

- 强一致性要求的数据（余额、订单状态）——缓存会导致读到旧值
- 写多读少的数据——缓存命中率低还引入失效复杂度

```bash
# 第一次请求：应看到回源 DB 的日志，然后写缓存

# 验证 fail-open：停掉 Redis 再请求，接口应照常返回（回源 DB）
```
