# 易宝支付对接：部署与配置说明

> 适用版本：批次 1–3（入驻 / 分账 / 提现 / 押金）。
> 批次 4（易宝收款）尚未启用，`app.pay.collect-channel` 未落地。

## 一、铁律：不要改 `PAY_CHANNEL`

**`PAY_CHANNEL` 与全部 `WXPAY_*` 一律保持原值。**

原因：微信支付的 Bean 全部由 `app.pay.wxpay.channel=wxpay` 条件装配，
而退款/查单/二次支付都依赖这些 Bean 按历史支付单回原通道：

```java
// RefundService.java
gatewayResolver.forPayment(payment).refund(...)      // payment.channel = WXPAY
// PaymentGatewayResolver.java
throw new IllegalStateException("支付记录通道不可用，请人工核查");
```

一旦把 `PAY_CHANNEL` 改成别的值，`WechatPayGateway` Bean 消失，
**所有历史微信订单的退款会立即失败**。易宝使用完全独立的开关。

## 二、启用易宝需要注入的环境变量

### server 模块

| 变量 | 必填 | 说明 |
|---|---|---|
| `YEEPAY_CHANNEL` | 是 | 填 `yeepay` 才启用；留空则一个易宝 Bean 都不装配 |
| `PAYOUT_CHANNEL` | 是 | 出款通道：`yeepay` / `wxpay` / `mock` |
| `COLLECT_CHANNEL` | 是 | 收款通道：`wxpay` / `yeepay`（新订单） |
| `APP_SENSITIVE_KEY` | 是 | 敏感字段加密密钥（Base64 的 32 字节）。**用于加密商户私钥**，缺失时后台无法保存私钥 |

可选：`YEEPAY_NOTIFY_BASE_URL`（默认 `https://api.wulingshiguang.top`）、`YEEPAY_SANDBOX`（默认 `false`）。

**易宝的 appKey / 商编 / 私钥已改为数据库可配置**，不再需要环境变量，见下节。

### 易宝配置在运营后台维护

配置存在 `platform_profile.pay_config`（JSON）：

| 接口 | 用途 |
|---|---|
| `GET /api/v1/admin/platform/yeepay` | 读取配置（**私钥不回显**，只返回 `privateKeyConfigured`） |
| `PUT /api/v1/admin/platform/yeepay` | 保存配置（私钥加密后落库） |

需填 5 项：

| 字段 | 敏感级别 | 从哪拿 |
|---|---|---|
| `appKey` | 明文 | 易宝开放平台 → 应用管理 |
| `merchantNo` | 明文 | 服务商主商编，签约时分配 |
| `platformMerchantNo` | 明文 | 平台商商编（**未开通则平台份额无法分账**） |
| `privateKey` | **加密存储** | 开放平台 → 密钥管理下载 |
| `yopPublicKey` | 明文 | 易宝平台公钥，留空则由 SDK 远程拉取 |

**私钥处理细节**：

- 后台传明文，服务端用 AES-256-GCM 加密后落库（密文带 `v1:` 前缀）
- 私钥留空表示「不修改」，运营只改商编时不必重新粘贴
- PEM 头尾（`-----BEGIN PRIVATE KEY-----`）与换行在保存时自动清洗
- **接口永不返回私钥**（连密文都不返回），避免有后台权限即可导出密钥
- 若 `APP_SENSITIVE_KEY` 变更过，旧密文无法解密，需重新保存私钥

**生效方式：重启 trade-service**。配置在 `ApplicationReadyEvent` 时通过 `GET /internal/platform/yeepay-config` 拉取（私钥在该接口解密后下发，因为 SDK 签名需要明文）。

### trade-service 其他可调参数

| 变量 | 说明 |
|---|---|
| `YEEPAY_DIVIDE_INTERVAL_MS` | 分账间隔毫秒，默认 2500（易宝要求 2-3 秒） |
| `YEEPAY_HTTP_TIMEOUT_MS` | HTTP 超时，默认 8000 |
| `PAYOUT_RECONCILE_CRON` | 提现补偿任务 cron，默认 `0 */5 * * * ?` |

## 二点五、易宝收款（小程序支付）

### 两步下单，无法省略

易宝官方《小程序支付》指引明确「小程序支付对接聚合统一下单接口」，且「小程序内只能使用小程序支付」。故必须走两步：

1. `POST /rest/v1.0/trade/order` —— 建单，返回 `token`。
   **必须传 `fundProcessType=DELAY_SETTLE`**，钱才进「待分账账户」，
   否则无法后续分账给经营者。
2. `POST /rest/v1.0/aggpay/pre-pay` —— 用 token 换小程序唤起参数。
   `payWay=MINI_PROGRAM` + `channel=WECHAT` + `scene=ONLINE`
   + `appId` + `userId`(openid) + **`userIp`（必填，无豁免）**。

这里的「聚合支付」指「一个接口适配多渠道」，不代表必须开通支付宝/银联。本项目只用 `channel=WECHAT`。

### `userIp` 由服务端解析

`aggpay/pre-pay` 的 `userIp` 标注「是」（必填）。由 `AppOrderController#resolveClientIp` 从请求头解析：

优先级：`X-Forwarded-For` 首个非内网地址 > `X-Real-IP` > `remoteAddr`。

**需确认网关透传**：Spring Cloud Gateway 默认追加 `X-Forwarded-For`。若网关未配置，需在过滤器补上，否则取到的是内网地址。

### 需要在易宝后台配置

- **小程序 AppID**：易宝要拿你的 AppID + openid 去微信下单，未配置会报「商户产品未开通」
- **微信小程序支付产品**：确认 `payWay=MINI_PROGRAM` 对应权限已开通

这不是向微信报备，是易宝侧的一次性配置。

### 支付与清算的两个通知

| 通知 | 路径 | 用途 |
|---|---|---|
| 支付结果 | `/api/v1/app/yeepay/notify/pay` | 入账（复用与微信相同的 `settlePaid`） |
| 清算结果 | `/api/v1/app/yeepay/notify/clearing` | 置清算成功 + 触发分账 |

**易宝要求「清算成功后才能分账/退款」**。核销可能早于清算，此时分账被门禁标记为 `PENDING_CLEARING`，等清算通知到达再补分。

### 收款通道独立开关

```bash
COLLECT_CHANNEL=wxpay    # 新订单走哪个通道：wxpay | yeepay
```

**绝不能改 `PAY_CHANNEL`**：它一旦变成 `yeepay`，微信 Bean 消失，历史微信订单退款会直接失败（`forPayment` 抛「支付记录通道不可用」）。

`COLLECT_CHANNEL` 只控制新订单；退款与查单仍按 `payment.channel` 回原通道。

## 二点六、分账与退款

### 平台份额先分走

平台主体（`biz_subject.subject_type='PLATFORM'`）没有入驻记录，但**它就是平台商本身**，分账时 `ledgerNo` 直接用 `YEEPAY_PLATFORM_MERCHANT_NO`。

这样平台份额能与已入驻经营者的份额在同一批 `divide/apply` 里一起分走，**不必等所有经营者都入驻**——否则订单会长期卡在「部分分账」，平台现金流被冻结。

未入驻的经营者份额仍留在待分账账户（`unSplitAmount`），入驻后由 `catchUpDivides` 补分。

### 退款归集（divideBackDetail）

易宝的 `trade/refund` **自带** `divideBackDetail` 参数，一次请求完成「归集 + 退款」。不需要先调独立的 `divide/back`。

三种情况可在同一数组里混合（官方示例即如此）：

```json
[
  {"ledgerNo":"10080028707","amount":1.20,"divideDetailNo":"1010202408010000013288965686"},
  {"ledgerNo":"10080028770","divBackAccountType":"DIVIDE_ACCOUNT"}
]
```

**两条互斥约束**：
- 归集明细（带 `divideDetailNo`）**不得**带 `divBackAccountType`
- 收单商户明细（带 `divBackAccountType`）**不得**带 `amount`，且最多一条

| 订单状态 | 处理 |
|---|---|
| 完全未分账 | `divideBackDetail` 不传，直接从待分账账户退（最简单） |
| 部分分账 | 已分账传 `divideDetailNo` + 未分账传 `DIVIDE_ACCOUNT` |
| 全部分账 | 全部传 `divideDetailNo` |
| 已提现 | 归集失败 → 平台垫付 + 记 `DIVIDE_BACK_FAILED` 对账异常追偿 |

**技术前提**：归集需要明细级 `yeepay_divide_detail_no`（V119 新增列）。分账成功后从 `divide/apply` 响应解析并按 `ledgerNo` 回写。若响应不含该字段，该笔退款将无法归集，会记 error 日志。

## 三、生成 `APP_SENSITIVE_KEY`

必须 32 字节随机数，Base64 编码：

```bash
# Linux / macOS
openssl rand -base64 32

# Windows PowerShell
$bytes = New-Object byte[] 32
[System.Security.Cryptography.RandomNumberGenerator]::Create().GetBytes($bytes)
[Convert]::ToBase64String($bytes)
```

**未配置时不会「降级为明文」**：入驻提交与结算卡绑定会直接报错
`敏感字段加密未配置（APP_SENSITIVE_KEY），拒绝明文入库`。
这是刻意的 fail-closed —— 宁可拒绝入库，也不让身份证号裸奔落盘。

密钥轮换：密文格式带 `v1:` 前缀，新增 v2 解密分支即可，历史数据无需重写。

## 四、易宝后台需要配置的回调地址

| 通知 | 地址 |
|---|---|
| 入网结果通知 | `https://api.wulingshiguang.top/api/v1/app/yeepay/notify/merchant` |
| 结算结果通知 | `https://api.wulingshiguang.top/api/v1/app/yeepay/notify/settle` |
| **支付结果通知** | `https://api.wulingshiguang.top/api/v1/app/yeepay/notify/pay` |
| **清算结果通知** | `https://api.wulingshiguang.top/api/v1/app/yeepay/notify/clearing` |

**应答格式**：必须回写纯文本大写 `SUCCESS`（不是 JSON）。
否则易宝按 5/10/15/30/240/600/2700/3600/14400 秒重试 9 次。

## 五、灰度上线顺序

1. **先只开入驻**（不碰钱）
   ```
   YEEPAY_CHANNEL=yeepay
   PAYOUT_CHANNEL=wxpay        ← 出款仍走微信
   ```
   让经营者提交资料、完成入驻与签署、绑定结算卡。
   此时提现仍走微信通道，对现有流程零影响。

2. **小范围真实提现**
   ```
   PAYOUT_CHANNEL=yeepay
   ```
   先给 1–2 个内部主体开，跑小额真实提现，验证：
   - 分账是否在核销后自动完成（查 `settlement_record.divide_status`）
   - 提现审核通过后结算是否到卡
   - 回调是否能正常收敛提现状态

3. **放量**
   确认无误后对全部经营者开放。

**回滚**：把 `PAYOUT_CHANNEL` 改回 `wxpay` 即可，无需改代码重新部署。
注意：已用易宝提现过的单据仍会按 `withdrawal.payout_channel` 走原通道查询。

## 六、上线前必须确认的商务事项

见 [易宝对接-商务确认清单.md](./易宝对接-商务确认清单.md)。其中三条是**阻塞项**：

1. 经营者子商户结算方式必须配成 **自助结算**（配成 T1 会自动到卡，绕过运营审核）
2. 平台商子商户已开通，且能拿到平台商商编
3. 平台商与经营者子商户均已开通分账产品（`SHARE`）

## 七、已知风险与运维关注点

| 风险 | 表现 | 处置 |
|---|---|---|
| 分账滞留 | `settlement_record.divide_status = PENDING_ONBOARD` 长期不变 | 说明收款方未入驻。需催办入驻；钱在平台待分账账户是安全的 |
| 提现卡在 PROCESSING | 结算回调丢失 | `PayoutReconcileJob` 每 5 分钟主动查单；超 24 小时未确认会打 CRITICAL 日志 |
| 退款平台垫付 | `DivideRefundService` 记 `分账归还失败（已继续退款，平台垫付）` | 需运营向经营者追偿；根因通常是经营者已把子商户余额提走 |
| 押金抵扣 | 退款从押金扣除 | 查 `deposit_record` 台账，`reason` 字段写明订单号与退款单号 |
| 敏感密钥缺失 | 入驻/绑卡报「拒绝明文入库」 | 注入 `APP_SENSITIVE_KEY` |

V119 的回填逻辑：按 `order_no` 关联 `payment.channel` 补 `fund_channel`，

`clearing_status` 历史数据统一置 `SUCCESS`（微信无清算概念）。

只有 V113 涉及既有大表加列并回填 `order_no`，其余为纯新增或小表加列。
