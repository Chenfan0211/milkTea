# 商城团长归属、分佣与运营后台整合调整方案

> 方案日期：2026-11-16；代码调整日期：2026-11-17。数据库迁移及发布尚未执行。

## 一、目标与现状

商城订单按用户的有效团长归属分佣，团长本人购买享团长价且不拿本单佣金；无团长订单的分销差额归平台。每笔新商城订单都固定记录下单时的团长归属，并在运营后台展示。商城订单不进入「待核销池」。主体管理增加「团长管理」，财务中心将团长作为经营方显示。

现有基础：`user_leader` 保存用户归属，`orders.leader_user_id / leader_subject_id` 保存订单快照，商城下单和完成分账已区分团长本人、有归属与无归属；团长创建、列表、解除及人工归属接口已存在。现有 `referrerId` 仅用于注册推荐关系 `app_user.referrer_id`，不会建立 `user_leader`；已注册用户打开分享链接也不会自动归属。后台商城订单页缺分账展示，后台待核销池分页查询缺订单类型过滤，财务部分角色文案缺团长。

## 二、统一业务规则

| 下单用户 | 有效归属             | 成交价              | 订单团长快照                            | 完成后的分销佣金             |
| -------- | -------------------- | ------------------- | --------------------------------------- | ---------------------------- |
| 普通用户 | 其他团长             | SKU 售价 + 分销佣金 | 该团长用户 ID、主体 ID；类型 `OTHER`    | 给快照团长主体               |
| 团长本人 | 自己（有效身份优先） | SKU 售价            | 自己的团长用户 ID、主体 ID；类型 `SELF` | 0，不给自己或原归属团长      |
| 普通用户 | 无团长               | SKU 售价 + 分销佣金 | 团长两项 ID 为 `NULL`；类型 `PLATFORM`  | 并入平台，不建立虚构团长账户 |

- 用户最多有一个有效归属团长。团长本人即使此前归属其他团长，下单仍按 `SELF` 处理；不强制在 `user_leader` 中插入指向自己的记录。
- 自动归属采用「首次有效绑定生效」：已绑定有效团长的用户打开其他团长分享链接，不自动改绑；后台人工调整可以改绑。原团长失效后，用户可通过新的有效分享链接重新绑定。并发点击也只能留下一个有效归属。
- 订单创建时以服务端解析的身份和归属为准，将团长用户 ID、团长主体 ID、归属类型写入 `orders`，同时保留商品的价格、成本、分销佣金单价快照。订单创建后改绑或团长停用不改旧订单；完成与退款均按订单快照处理。
- 团长停用后不能生成新绑定或成为新订单归属；停用前已创建订单仍可按原快照结算和退款。团长主体及资金账户保留，避免历史流水失去归属。
- 历史订单没有明确归属类型时显示「历史归属未记录」，不按用户当前团长关系回填或重算。

## 三、分享链接到归属的链路

1. 为商城首页、商品详情补充分享参数：`referrerId` 表示分享者用户 ID，继续用于现有注册邀请关系；另用独立参数携带**有效团长用户 ID**。分享者是团长时带自己；分享者是普通用户且已归属团长时带其归属团长；分享者无团长时不带团长 ID。邀请关系与佣金归属是两种独立数据，不能复用同一个字段。
2. 小程序在冷启动与直接打开商城分享页时保存待处理团长 ID。游客可先浏览；注册或登录成功后调用需登录的归属接口。已注册用户打开链接也调用同一接口。
3. 接口从登录态取得当前用户 ID，校验链接中的团长用户、主体、授权状态均有效，拒绝自己绑定自己、无效 ID 与停用团长。已有有效绑定返回原归属而不覆盖；后台人工设置仍可调整。接口写入需幂等，并记录绑定来源（分享/后台）和时间。
4. 客户端仅在服务端确认归属后清除待处理参数。有效分享链接的归属请求暂时失败时保留参数并重试；结算前再次确认，不能静默把该单按「无团长」提交。无团长参数或参数无效的自然流量照常下单，归平台。
5. `referrerId` 的现有注册邀请奖励链路继续独立运行。分享链接参数均视为不可信输入；最终订单归属只能由服务端查询有效关系得出，不能直接采信下单请求中的团长 ID。

## 四、数据与服务调整

- 沿用 `orders.leader_user_id / leader_subject_id`。在下一版数据库迁移中增加订单归属类型字段（`OTHER / SELF / PLATFORM`，旧数据允许为空），使无团长 `NULL` 与旧订单缺失数据可区分。下单接口和后台订单 DTO 返回这三个字段。
- `user_leader` 保持一用户最多一条关系；补充绑定来源，并在自动绑定接口中实现「首次有效绑定」和并发幂等。读取归属时同时验证团长主体及授权仍有效；只验证 `user_leader.deleted=0` 不够。
- 商城商品报价、购物车结算与创建订单共用团长身份口径。团长本人订单的 `order_item.distribution_commission=0`；普通用户保留下单时佣金单价。完成分账保持平台、供应商、团长三方守恒；无团长时团长金额为 0，差额归平台。
- 退款保留原分账快照，另按原订单商品和团长快照冲正，不能用退款时的新归属或新 SKU 价格计算。

## 五、运营后台调整

### 商城管理 → 商城订单

- 列表操作增加「分账明细」，详情增加同一信息：订单团长 ID、团长名称、归属类型、各商品佣金单价及件数、实付、供应商、团长、平台和合计校验。
- 未完成订单标为「待分账」，不把当前规则试算值显示为实际收入。完成订单读实际分账快照；部分或全部退款时同时展示原分账、冲正和当前净额，金额以账务流水为准。
- 无团长订单显示「未绑定团长，佣金归平台」；团长本人订单显示「本人团长价，本单团长佣金 0」。

### 主体管理 → 团长管理

- 新增独立菜单，展示团长主体 ID、团长用户 ID、名称、关联用户、状态与账户余额；支持从现有用户设为团长、查询归属用户、后台人工归属/改绑，以及停用团长。
- 停用采用保留历史主体与账户的方式；停用后的归属关系不再用于新订单。停用前提示仍未完成订单、待结算金额和当前归属人数，不删除历史订单与流水。
- 原「用户管理」的归属团长操作保留，与团长管理共用后端规则。

### 交易中心 → 待核销池

- 后台订单分支的列表 SQL 和总数 SQL 同时限定 `o.order_type='STORE'`；积分兑换分支保持原口径。搜索商城订单号也不得返回商城订单。商城发货、收货与自动完成继续走商城履约状态机。

### 财务中心

- 资金池、经营方账户、资金流水、提现管理的角色名称及适用筛选项增加 `LEADER → 团长`，资金流水账户名称显示「团长账户」。分账快照现有团长金额继续展示，并与商城订单明细核对。
- 这里的「团长角色」指财务经营方类型；后台登录账号的 `R_FINANCE` 等菜单权限不因此改变。对账异常池没有经营方角色列，不新增无意义的角色列。

## 六、实施顺序与验收

1. 先补分享链接、登录后自动归属及团长有效性/并发校验，保证新订单归属正确。
2. 增加订单归属类型与 DTO 字段，核对团长本人、归属其他团长、无团长三种下单和完成分账。
3. 修正后台待核销池过滤；增加团长管理与商城订单分账明细。
4. 补齐财务角色映射、账户名称、筛选与退款净额展示，再做逐单对账。

验收样例至少覆盖：新用户和已注册用户点分享链接、普通用户转发其团长链接、重复/并发打开不同团长链接、后台改绑、团长自购、无团长自然搜索下单、团长停用前后订单、下单后改绑、部分及全额退款。逐单核对 `orders` 归属、`order_item` 佣金、`split_snapshot`、`settlement_record`、`fund_flow` 与账户余额；核对后台待核销池不含商城订单。管理端执行类型检查与构建，小程序变更后执行 `npm run check` 和项目图标检查，后端执行相关单元与集成测试。真实迁移、支付和退款需在目标环境单独验收。
