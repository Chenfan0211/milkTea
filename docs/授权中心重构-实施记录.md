## 三、验证过程中发现并修复的两个真实 Bug

这两个都是**执行成功但数据错误**的静默故障，靠"能跑通"完全发现不了。

### Bug 1（严重）：菜单树被完全拍平

**现象**：迁移执行后 53 条菜单**全部** `parent_id = 0`，授权中心子菜单变成顶级菜单。

**根因**：迁移里写成

```sql
INSERT INTO sys_menu (...)
SELECT s.code, IFNULL(p.id, 0), ...
FROM tmp_menu_seed s
LEFT JOIN sys_menu p ON p.code = s.parent_code   -- ← 看的是 INSERT 之前的快照
```

同一条 `INSERT` 里刚插入的父节点，对自身的 `LEFT JOIN` **不可见**，于是 `p.id` 恒为 `NULL`。

**修复**：改为「先插父节点（`WHERE s.parent_code IS NULL`），再插子节点（`JOIN sys_menu p`）」两步。
修复后：10 个顶级目录 + 43 个子节点，层级正确。

**加锁**：`AdminRbacGuardTest#menuParentLinkMustUseTwoPhaseInsert`
反向断言"不得出现 `INSERT INTO sys_menu ... LEFT JOIN sys_menu`"，防止回归。

### Bug 2：运营角色越权拿到「功能开关」菜单

**现象**：`R_OPERATION` 拿到了 `system_feature`（功能开关），但前端 `adminRouteMeta` 里它归属 `audit`。

**根因**：排除条件用模糊匹配 `m.code NOT LIKE 'system_audit%'`，
而 `system_feature` 既不等于 `'system'` 也不匹配 `'system_audit%'`，被漏网。

**修复**：改为**显式黑名单**（`m.code NOT IN (...)`）。
理由：菜单 code 是人工维护的标识，模糊匹配会在新增菜单时静默失效；
显式名单下，新增菜单默认归运营，若要给别的角色必须显式登记 ——
失败方向从"意外获得权限"（危险）变成"菜单不显示"（安全）。

**修复后**：`R_OPERATION` 泄漏 0 条，可见的系统类菜单只剩 数据字典 / 城市管理 / 运营配置。
