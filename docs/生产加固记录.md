## ⚠️ 一、生产事故复盘（必须先读）

### 1.1 事故经过

在执行本轮加固时，生产服务 `wuling-server` **中断约 18 分钟**（11:26–11:44）。

### 1.2 直接原因

加固流程需重启服务以加载新配置。重启时 Flyway 校验失败：

```
Migration checksum mismatch for migration version 3
-> Applied to database : -84453698
-> Resolved locally    : 1524040594
```

### 1.3 根本原因（两层）

**第一层：开发隧道直连生产库（架构缺陷）**

`application-dev.yml` 中 `jdbc:mysql://127.0.0.1:13306/wuling` 经 SSH 隧道
`-L 13306:127.0.0.1:3306` **直连生产 MySQL**。

后果：**第 0 期与 P2 期间的 Flyway 迁移（V11/V12/V13）实际应用到了生产库**。

证据（生产库 `flyway_schema_history` 时间戳）：

| 版本 | 应用时间 | 归属 |
|------|---------|------|
| V1–V10 | 2026-09-21 19:57–23:13 | 原生产部署 |
| V11 tencent map config | 2026-09-22 **02:19:41** | ⚠️ 开发期误操作 |
| V12 concurrency safety | 2026-09-22 **02:20:02** | ⚠️ 开发期误操作 |
| V13 audit indexes | 2026-09-22 **10:19:29** | ⚠️ 开发期误操作 |

**第二层：迁移文件与已部署 jar 不一致**

- 生产 jar 构建于 `01:07`，其内 V3 的 Flyway checksum = `1524040594`
- 仓库 V3 在 `01:59` 被修改（安全清理提交 `88a4cd7`），checksum = `-84453698`
- 服务在 `01:07` 启动时校验通过并持续运行；**只要不重启就不会暴露**
- 本次加固重启，校验重新执行，问题才显性化

> 结论：问题**早已存在**（DB 与 jar 的迁移版本不一致），重启只是让它显性化。

### 1.4 处置过程

1. 备份现场（配置、systemd 单元、nginx、数据库 `mysqldump`）→ `/opt/wuling/backup/hardening-20260922-112720`
2. 回滚 systemd 单元与配置
3. 定位 checksum 差异，用 `update flyway_schema_history set checksum=...` 对齐
4. 部署与 DB 迁移状态匹配的**最新构建 jar**（含 V1–V13）
5. 修复加固配置中的 `management.server.port` 与 `server.port` 冲突
6. 服务恢复，全接口验证通过

### 1.5 经验教训（已落入规范）

| 问题 | 改进 |
|------|------|
| 开发隧道直连生产库 | **开发库必须独立**；确需连生产时禁用 Flyway（`spring.flyway.enabled=false`） |
| 迁移文件改动未同步部署 | 修改已上线的迁移文件属**禁忌**；应新增版本号而非改历史 |
| 无发布前 checksum 校验 | 部署前应比对 `flyway_schema_history` 与 jar 内迁移 |
| 无回滚演练 | 加固前先备份并验证可回滚 |

## 二、已完成的生产加固

### 2.1 后端不再直接暴露公网（P0）

| 项 | 加固前 | 加固后 |
|----|--------|--------|
| 监听地址 | `*:8080`（公网可达） | `127.0.0.1:8080`（仅本机） |
| 访问路径 | 可绕过 nginx 直连 | 必须经 nginx 反代 |

**验证**：`http://43.136.91.239:8080/...` → 已不可达；经 8089 正常。

**意义**：消除明文 HTTP 传输 JWT/口令、绕过统一限流与审计的攻击面。

### 2.2 actuator 信息泄露收敛（P0）

**加固前**：`/actuator/health` 返回完整组件详情，泄露：
- 数据库类型（MySQL）
- **磁盘路径**（`/opt/wuling/app`）与剩余空间
- Redis 版本 `7.4.11`、RabbitMQ 版本 `3.13.7`

**加固后**：仅返回 `{"status":"UP"}`

```yaml
management:
  endpoints:
    web:
      exposure:
        include: health        # 移除 info（会泄露构建信息）
  endpoint:
    health:
      show-details: never      # 原为 always
      show-components: never
```

### 2.3 JWT 密钥轮换（P0）

**问题**：生产 `application-prod.yml` 仍使用仓库公开的默认密钥
`N1uU6M8tUVZhUGLntH8DFKq4a3WrzrkyIADnGlEmr5c=`，**任何人都可伪造 admin token**。

**处置**：
- 用 `openssl rand -base64 32` 生成新密钥（32 字节，满足 HS256）
- 移入 `secrets.env`（权限 600）
- **验证**：用旧默认密钥伪造的 token → `401` 拒绝；正常登录 → `code=0`

> 影响：已签发的 token 全部失效，用户需重新登录（当前仅 1 个管理账号）。

### 2.4 中间件口令轮换（P0）

| 组件 | 加固前 | 加固后 |
|------|--------|--------|
| MySQL root | `root123` | 24 位随机 |
| MySQL wuling | `wuling123` | 24 位随机 |
| Redis | `wuling123` | 24 位随机 |
| RabbitMQ | `wuling123` | 24 位随机 |

- 轮换前已 `mysqldump` 全量备份至 `/opt/wuling/backup/db/`
- 已同步更新 `docker-compose.yml`，重启后仍生效
- 均只监听 `127.0.0.1`，未公网暴露

### 2.5 密钥外部化（P1）

**加固前**：`WX_APP_SECRET` 明文写在 systemd 单元
`Environment="WX_APP_SECRET=cc1c9957..."` —— 任何可读 systemd 配置或 `ps` 的用户均可获取。

**加固后**：

```ini
EnvironmentFile=/opt/wuling/app/secrets.env   # 权限 600，仅 root 可读
```

`secrets.env` 集中管理：`JWT_SECRET` / `MYSQL_PASSWORD` / `REDIS_PASSWORD` /
`RABBITMQ_PASSWORD` / `PAY_CALLBACK_SECRET`。

`application-prod.yml` 中所有敏感项**无默认值**，缺失即 fail-fast 拒绝启动。

### 2.6 日志与错误信息收敛

| 项 | 加固前 | 加固后 |
|----|--------|--------|
| MyBatis SQL 日志 | `StdOutImpl`（打印全部 SQL 与参数，含手机号） | `NoLoggingImpl` |
| 错误响应 | 可能含堆栈 | `include-stacktrace: never` |
| 根日志级别 | — | `WARN`（业务包仍 `INFO`） |
| 日志轮转 | 无限制 | 50MB/文件，保留 30 个，总量上限 1GB |

### 2.7 其他加固

- **Nacos 端口收紧**：`8848/9848/9849` 均只监听 `127.0.0.1`（与 MySQL/Redis/RabbitMQ 一致）
- **请求体限制**：`max-http-form-post-size: 2MB`，缓解内存型攻击
- **Hikari 连接泄漏检测**：`leak-detection-threshold: 60000`
- **systemd 沙箱**（已写入单元文件，当前未启用，见待办）：`NoNewPrivileges` /
  `PrivateTmp` / `ProtectSystem` / `ProtectHome` 等

## 四、回滚方式

```bash
# 现场备份
/opt/wuling/backup/hardening-20260922-112720/
  ├── application-prod.yml       # 原生产配置
  ├── wuling-server.service      # 原 systemd 单元
  ├── nginx-conf.d/              # 原 nginx 配置
  ├── docker-compose.yml         # 原 compose
  └── server.jar.old             # 原 jar（仅含 V1–V10）

# 数据库备份
/opt/wuling/backup/db/wuling-before-pwrotate.sql.gz

# 回滚步骤
cp <备份>/wuling-server.service /etc/systemd/system/wuling-server.service
cp <备份>/application-prod.yml  /opt/wuling/app/application-prod.yml
cp <备份>/server.jar.old        /opt/wuling/app/server.jar
systemctl daemon-reload && systemctl restart wuling-server
```

> ⚠️ 回滚口令需同时还原 MySQL/Redis/RabbitMQ 密码，否则服务无法连接。
